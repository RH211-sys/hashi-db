# 并发注意事项

## 一、并发设计

### 1. 总体模型

- **读并发 + 写串行 + 磁盘单线程**
- 读任务由线程池多线程并发执行（读读并发，甚至利用多核并行）
- 写任务由单个写线程串行执行（保证先后访问 cache 的 `unordered_map`）
- 磁盘任务单个线程串行执行（频率低，天然串行，简化逻辑）

### 2. 锁的划分

| 对象 | 锁 | 保护范围 | 说明 |
| --- | --- | --- | --- |
| Cache | 一把写者优先读写锁（`shared_mutex` 变体） | `cache_db`、`curSize`等 | 读：读锁（共享，并发）；写：写锁（独占，串行） |
| Disk | 不需要锁 | `inDisk`、`delDisk`、文件等 | 只有磁盘单线程碰它们，天然串行 |
| ThreadPool | 内部锁 | 任务队列、stop/busy 标记等 | 只保护队列本身，不管任务执行 |

### 3. 读写互斥的原因

即使读和写操作的数据不同，也不能同时进行——`unordered_map` 扩容 rehash 时迭代器失效，并发读写同一结构会产生数据竞争（崩溃/数据错乱）。

### 4. 写者优先

有写者排队时，新读者不允许插队（写优先），保证读到的数据时效性高。

### 5. 读写差距阈值（防读饥饿）

写者优先会导致读饥饿（读任务被写任务无限推迟）。解决：限定读写任务处理数量差距上限（如 5）。差值超过阈值时，暂停写操作，放行一批读任务（批大小 = 线程池线程数，即并发完成 n 次读操作），完成后再恢复写。

### 6. 跨对象访问规则

- 磁盘线程访问 cache 必须走同一把读写锁（刷盘拷贝脏数据、导出回填缓存）
- 刷盘标准流程：锁 cache → 拷贝脏数据快照 → 解锁 → 写盘（减少锁持有时间）
- 代码组织上的双向隔离（逻辑不变，视觉解耦）：Disk 内分纯磁盘区（无锁）与缓存交互区（锁集中于此）；Cache 内分纯缓存区（锁保护）与磁盘交互区（提交任务、future 等待）

### 7. 磁盘线程执行原则

磁盘线程自身执行磁盘 IO 时必然阻塞（毫秒级），这无所谓——关键是不能把慢传导给读写路径。三条原则：

- **磁盘写（持久化/刷盘/重写）**：提交任务立即返回，调用者不等待；写盘全程锁外执行（锁内只拷贝脏数据快照）
- **磁盘读（读未命中）**：提交任务返回 `std::future`，只有发起该次读的上层线程 `future.get()` 阻塞等待结果，其他读任务不受影响
- **磁盘线程访问 cache_db**（拷贝脏数据/回填缓存）：短暂持锁，微秒级；真正的磁盘 IO 全程锁外

效果：读被磁盘挡住的时刻只有"拷贝/回填"那微秒级瞬间，磁盘 IO 的慢是隔离的，不阻塞任何读写路径。

### 8. CRUD 与磁盘的交互流程

- selData 读未命中：提交磁盘读任务 → 上层 `future.get()` 阻塞等结果 → 回填缓存前重新校验 key（可能已被并发修改/删除）→ 校验通过才回填
- 持久化接口（persisVar/flushDisk/reWrite）：提交任务立即返回，不阻塞
- 定时调度归上层（管理层），本层不内建定时器

### 9. 已知代价

- 写回缓存的丢数据窗口：宕机丢未刷盘数据，设计内接受

## 二、为什么不用 以下模型（之前设计过的模型）

- 为何不用"缓存任务多线程并发写"

原因：写操作必须串行——`unordered_map` 结构竞争 + rehash 迭代器失效决定了同一时刻只能有一个写者。多线程写需要锁互斥，效果 ≈ 单线程串行，还多了锁竞争和上下文切换开销。

- 为何不用"缓存全串行（Redis 单线程模型）"

原因：全串行把读读也串行化，丢弃多核读并行。读多写少场景下，读并发有实际吞吐收益；写串行已满足结构安全，没有必要让读也付出串行代价。

- 为何不用"无锁设计（时间戳比较 / 布尔状态）"

原因：①比较与写入不原子，检查和写入不是原子操作——两个写者都通过判断后同时改 map 仍会结构竞争；②无法用单个 bool 表达"正在读的读者数量"，需要读者计数，计数 + 原子操作即读写锁的底层；③无锁只是把互斥换成原子操作自担风险，对内存微秒级操作收益为零。

- 为何不用"读优先"

原因：①读优先导致读的时效性不高——经常读到旧数据，尽管读的频率一般大于写，读到的却可能是旧值，时效性问题无法通过上限解决；②写者饥饿（脏数据刷不下去）虽可设上限兜底，但仅是次要原因。现设计采用写者优先：读必新（有写排队时新读者不插队）+ 读写差距阈值兜底（读不饿死），两者同时解决。

- 为何不用"线程池登记 map（线程池新增unordered_map<变量名，task*>）"

原因：登记表本身是新的共享结构，要多一把锁；存裸指针有悬空风险（任务销毁后表项未清）。收益小，复杂度高。

- 为何不用"磁盘多线程 + 文件锁"

原因：磁盘 IO 频率低，单线程天然串行，省掉文件写锁与 inDisk/delDisk 的全部锁；多线程写文件还要处理偏移量竞争、fsync 并发，收益为零。

- 为何不用"锁内做磁盘 IO"

原因：磁盘 IO 是毫秒级，锁内写盘会长时间阻塞所有读写。正确做法：锁内拷贝脏数据快照，解锁后写盘。

- 进行增删改后，当追加写进行增操作，删除中间数据，那么中间会产生空洞，会造成空间浪费，为何不维护一个“空洞链表”，连接磁盘存储的空洞，以减少空间浪费，减少重写频率

原因：`空洞链表`本身要持久化(文件头或单独索引区),崩溃恢复更复杂；每次写都要读空洞头部确认大小、找合适的洞,且洞可能比数据大,分裂后产生**更小的洞**(碎片化)；唯一的效益就是降低重写频率，但是每次`增删改`却要动态维护`空洞链表`；复杂度较高，且重写频率本身就比较低了，`空洞链表`反而会增加磁盘IO的频率

## 三、注意事项

1. 锁不嵌套：持读锁/写锁期间不得再取锁（死锁），锁内不再调用会取锁的函数
2. 磁盘线程回填缓存、拷贝脏数据必须走同一把读写锁
3. 读未命中回填前重新校验 key（可能已被并发修改/删除）
4. 读写差距阈值（如 5）与批大小（线程池线程数）做成可配置参数
5. 持久化接口返回值只表示"任务提交成功"，不是操作码
6. 定时调度归上层，本层不内建定时器
