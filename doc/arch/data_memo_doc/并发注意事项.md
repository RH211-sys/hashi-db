- ## 一、总体模型:内存并发 + 磁盘串行

  - **Cache**:允许并发访问(多个 CRUD 线程并行)
  - **Disk**:单线程串行执行(任务队列 + 单一消费者),即 `ThreadPool(1)`
  - 依据:单写者消除磁盘全部内部竞态(文件写入、偏移量、inDisk/delDisk);Redis 的 BIO 后台线程同款思路

  ## 二、锁的划分

  | 对象       | 锁                       | 保护范围                             | 说明                                                         |
  | ---------- | ------------------------ | ------------------------------------ | ------------------------------------------------------------ |
  | Cache      | 一把 `std::shared_mutex` | `cache_db`、`curSize`                | 读:`shared_lock`;写:`unique_lock`;粗粒度,一次 CRUD 只取一次锁,锁内更新所有临界资源 |
  | Disk       | **不需要锁**             | `inDisk`、`delDisk`、`curSize`、文件 | 只有磁盘单线程碰它们,天然串行                                |
  | ThreadPool | 内部锁                   | 任务队列、stop/busy 标记             | 只保护队列本身,不管任务执行                                  |

  `磁盘处理`频率比较低，用`单线程`正合适，且简化代码逻辑，降低复杂度

  ## 三、跨对象访问规则
  
  - **磁盘线程访问 cache 必须守 cache 锁**(磁盘线程是 cache 的访问者之一):刷盘拷贝脏数据、导出回填缓存,都在 cache 锁内完成
  - **刷盘标准流程**:锁 cache → 拷贝脏数据快照 → 解锁 → 写盘(减少锁持有时间,可行性分析原话)
  - **代码组织上的双向隔离**(逻辑不变,视觉解耦):
    - Disk 内分两区:纯磁盘区(无锁,算偏移/写记录/重写)+ 与缓存交互区(锁集中于此,拷贝脏数据/回填)
    - Cache 内分两区:纯缓存区(CRUD,锁保护)+ 与磁盘交互区(提交任务、future 等待)

  ## 四、CRUD 与磁盘的交互流程
  
  - **selData 读未命中**:提交磁盘读任务,返回 `std::future` → 上层 `future.get()` 阻塞等结果 → **回填缓存前重新加锁校验 key**(可能已被并发修改/删除)→ 校验通过才回填
  - **future.get() 阻塞是必要的**:查不到结果不能返回,同步语义，契合`磁盘同步`的逻辑
  - **持久化接口(persisVar/flushDisk/reWrite)**:提交任务立即返回,不阻塞
  - **定时调度归上层**(管理层定时调 deleteExpired 等),本层不内建定时器

  ## 五、已知代价与待定项
  
  - **写回缓存的丢数据窗口**:宕机丢未刷盘数据,设计内接受(Redis everysec 同款代价)
  - **待定:读写饥饿约束** —— `读优先`会导致写饥饿(写任务无限推迟,脏数据刷不下去),需限定`任务处理数量差距上限`(如连续 N 读后强制处理写、或时间片轮转),**等并发设计收尾再定**
  - **待定(可选优化)**:写任务合并——队列中多个单变量持久化任务合并为一次批量写
  - **未落地**:锁成员还没加进代码,实现时补
