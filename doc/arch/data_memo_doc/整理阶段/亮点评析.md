## 1. 架构与并发设计的亮点

### 1.1 线程模型："职责单一" + "磁盘单线程 = 天然无锁区"

四类执行者各管一摊：**写线程**（缓存写串行 + 淘汰）、**读池**（命中读并发）、**磁盘线程**
（索引 + 文件 IO 串行）、**调用方**（唯一可阻塞）。最关键的一招是：

> **把 inDisk、文件句柄、空洞索引全部收进磁盘单线程** —— 这些数据结构之间不需要任何锁，
> 因为永远只有一把"锁"：单线程本身。

多数并发缓存项目用多线程 + 细粒度锁保护索引，本项目反其道：**用线程隔离代替锁**。
代价是磁盘 IO 串行（成为后续瓶颈），收益是正确性推理成本极低——
删除、覆盖、压缩、空洞登记之间的顺序关系是"程序顺序"，不是"锁序"。
这是典型的"先求正确、再在证据指引下放宽"（读并行 v2 才引入跨线程读）。

### 1.2 续延链："只投递不等待"（AsyncResult）

一次 addData 被拆成：写线程查缓存 → 磁盘线程查磁盘索引 → 写线程插入——三段在两条队列间
交替投递，段间共享同一个 `shared_ptr<promise>`。为什么这是亮点：

- **慢 IO 不占死执行者**：若写线程同步等待磁盘任务，它被一条毫秒级文件 IO 占住的期间，
  后面所有微秒级写请求全部排队——吞吐崩塌、尾部暴涨。拆段后写线程每次只做微秒级活，
  "谁真正需要结果谁阻塞（调用方）"。
- **正确性兜底做全**：段体异常统一 `set_exception`、线程停止时 `fallback()`，
  保证调用方 `get()` 永不永久等待——线程池吞异常 + 未兑现 promise 是这类代码最常见的坑。
- 这也保住了最重要的好性质：**命中读路径完全不受磁盘慢任务影响**（读池线程永不碰磁盘 IO）。

### 1.3 两套"写优先 + 防饿"的调度记账

- **WritePrefMutex（缓存表锁）**：写者优先（有写者排队则新读者不插队），同时用
  `readSubWrite` 记账（读任务 − 写任务）：读跑飞（≥上界且无写者等）清账重来；
  写跑飞（≤下界）则放行一批 `batchSize` 个读者插队。**双向防饿**只用了两个阈值 + 一个批名额，
  没有复杂的公平队列。
- **磁盘线程双队列差距调度**：缓存任务（快）默认优先，`taskGap` 顶到上缘且有磁盘任务时让位一个，
  落到下缘清零——慢磁盘 IO 既不饿死快任务，也不被无限积压的快任务饿死。

两者是同一个思想的两个实例：**用"任务差记账"这种廉价状态机实现优先级 + 无饿死**，而非重量级公平调度。

### 1.4 临界区最小化的惯例

锁内只做"查 / 指针交换 / 记账"，一切可能慢的动作（序列化、写文件、析构旧实体、淘汰）
都放到锁外：`modData` 锁外先算好新实体大小、锁内只换 `shared_ptr`；淘汰"采样在共享锁内、
淘汰执行在独占锁内、删前再校验"。这是让读写锁真正能并发的原因——临界区短到微秒级。

## 2. 磁盘文件设计的亮点

### 2.1 86B 自描述定长头 + "删除即空洞"

记录头 = 校验码 + dataSize + 时间 + 类型 + 名字，**活记录与空洞段共用同一格式**，
顺序扫描永远 `offset += 86 + dataSize`。删除 = 把首字节改成 `CHECK_DELETED`（1 字节写），
整个旧记录成为可跳读、可复用的洞段。洞头实际只写 code + dataSize 共 5B（跳读只依赖这两字段）。

这一设计的优雅之处：**空洞是"文件里显式自描述的对象"，不是内存里维护的链表**——
内存索引（holes）丢了可以重扫文件重建，文件本身永远自洽。早期否决"内存链表 + 读洞头"
的决策被 A+ 方案正面超越。

### 2.2 空洞 best-fit 复用与切洞边界规则

- 索引用 `multiset<(容量, 偏移)>`，`lower_bound` 取**不小于需求的最小洞**（best-fit）。
  不用 max-heap（大洞会被反复切碎，很快没有能装 MB 级大记录的洞）；
  不用 first-fit（小洞堵前部、碎片加剧）。
- **边界规则是这份设计的"数学内核"**：剩余 ≥86 才能切洞登记；`0 < 剩余 < 86` 时
  剩余区无法表达成任何合法段（合法段最小 86 逻辑字节），硬覆盖会让顺序扫描错位，
  所以**回退追加**而不是硬塞。规则虽小，却是"文件永远自描述"得以成立的保证。
- 结果（场景2，read70/write30）：追加字节 **15.3GB → 6.0GB（−61%）**，自动压缩
  **41 次/4.0s → 16 次/1.5s（~5% duty）**，P999 13.9ms → 7.1ms，场景末洞只剩 20 段/4MB。

### 2.3 两段式校验码 + 批 flush：崩溃一致性的"最小但够用"

每条记录先整条写 `CHECK_BROKEN`，写毕回写 `CHECK_VALID`；顺序扫描把 BROKEN 段当残尾**截断文件**。
配合"删除标记/记录随所在写任务批 flush"的可见性规则，崩溃窗口只丢"正在写的一条"，
且重建规则唯一（截断到残尾）。没有 WAL、没有 fsync 风暴——用**可截断的日志结构**换掉了
通用 DB 的重日志协议，对这个场景是正确取舍。

### 2.4 两阶段原地压缩：根治"写覆盖读"，且不用 tmp 文件

自动压缩曾几乎全失败（fail 6348/6351），定位到根因：原地从 0 紧凑重写时，若中途写入
"变大的缓存记录"，写游标会越过后面还没读的旧记录（写覆盖读）。方案：

- **阶段A** 只搬"缓存没有/干净"的记录——读旧写新**长度不变**，写游标永远 ≤ 读游标；
- **阶段B** 缓存脏 key 最后写——旧区已无可读记录，写多大都安全；
- **阶段C** 全新数据追加；末尾 `resize_file` 截断。

不用 tmp 文件 = 峰值磁盘占用只有一份文件（用户明确的空间取舍），而"按长度不变先搬、
可变的后写"是让原地重写安全的最小充分条件——比"搬完再替换文件"少一倍的 IO 峰值。

### 2.5 零拷贝序列化链

- 序列化：`VecBuf/VecStream` 让 cereal **直接写进记录缓冲**，免 stringstream→string→vector 两轮整块拷贝；
- 反序列化：只读内存流 `MemInBuf` 让 cereal **直接在读出的字节区解析**；
- 实体：写入时移进堆一次，命中/回填/返回全部共享 `shared_ptr<any>`（只拷指针）。
- 效果：单条磁盘读 avg 由 ~1,480µs 降到 ~750µs 以下；命中读路径完全零拷贝。

## 3. 缓存侧的亮点

### 3.1 全局采样淘汰：给"无 LRU 链表"一个理论依据

缓存淘汰通常默认 LRU 链表，但本项目做了再思考：**unordered_map + 全局采样 + 大顶堆**，
在写线程内阻塞执行到容量达标。亮点在于：

- 命中路径零链表维护（并发读锁内只刷一个 relaxed 原子时间戳），避免链表节点的
  跨核写与锁放大；
- 淘汰质量靠 `evictScore` 撑：`档位 × 档距(30) + ln(dataSize)`——时间分档而非连续时间
  （对访问频率的鲁棒度量），档距 30 > 任何合理 ln(size) 上限，**跨档不可能靠大小翻盘**，
  冷数据永远先于热数据；同档内再偏删大 key（腾空间最快）；
- "采样与淘汰之间数据会变"用**删前独占锁内重校验**解决，无需跨轮大锁。

这是"牺牲一点淘汰精确性、换取并发与实现简单"的教科书式交换，且用评分公式把误差控住了。

### 3.2 updateTime 原子化：一行类型改动消掉一个隐蔽 UB

共享读锁允许多读者并发进入，而命中路径在锁内写 `updateTime`——多线程并发写同一非原子字段，
这是数据竞争 UB，不是"性能问题"。改成 `std::atomic<long long>`（µs、relaxed）后：
**并发写变安全，且 relaxed 无任何屏障开销**。小而准的正确性修复，行为零漂移。

### 3.3 惰性过期：三个判定点，不养清理线程

过期检查全部寄生在既有路径上：命中时查（过期返回 EXPIRED + 两条平级清理防复活）、
磁盘读回后查（过期直删索引不回填）、淘汰开头顺带全扫批量清。没有专门的过期线程，
TTL 语义（过期不算 miss）与统计口径一并定义清楚——**功能寄生在流量路径上**，省一整类后台任务。

## 4. 工程方法上的亮点（可能才是最大的亮点）

### 4.1 观测先行：先装"仪表"再动手

本项目优化的第一步不是改代码，而是**装观测**：序列化/文件写/flush/读的阶段计时、
miss 去向分类、失败现场抽样打印（`[SEL-FAIL]`/`[REWRITE-FAIL]`）、队列深度与 worker busy%。
所有结论都由数据支撑，不做猜测式优化。

### 4.2 三次"百思不解"全靠证据破案

1. **读盘 9%~18% 成功率的谜**：失败现场打印出 `offset=-2139695632, fileLen>2GiB` →
   一眼定位 int 偏移溢出 → 全链路 64 位化；
2. **压缩反复失败的谜**：fail 6348/6351 + "小 offset 读头失败"集中在文件顶到上限时 →
   推理出原地压缩"写覆盖读" → 两阶段方案根治（改动前先有失败现场证据）；
3. **"读并行提效"的假设**：备份版本实测**恶化**、被回退 → 得到重要教训：并行不是搬线程池，
   需要整套同步协议（索引并发读安全、发布时序、压缩互斥），废弃稿因此写成完整设计。
   这个"试错并如实记录"的过程本身是项目最值钱的部分。

### 4.3 基准真实性工程

- **1:3:5 编排**：对照 Redis Enterprise Auto Tiering 容量模型
  （RAM ≥ 20% 值、闪存 ≥ 总量 + 写放大余量）缩放，并区分"适用/不适用"场景（Pika 为反例）；
- **纯读档限定热子集 ≤0.7×缓存**：意识到 1:3 全数据集读 = 磁盘冷读（测的是磁盘不是缓存），
  主动把"内存命中读"与"冷读/命中率"语义分开；
- 写尺寸削顶档（4K~1M 同量级）、缓慢注入模拟数据集增长、`WRITE_INFLIGHT` 制造稳态在途写、
  蓄水池采样算延迟分位——**每一个数字都能解释它代表什么场景**。

### 4.4 探针治理与文档即实验记录

- 探针（计时/分类/失败现场）完成使命后统一 `#if 0` 保留源码、正式输出收敛为
  QPS / P99 / 命中率三行——"Release 删除测试点代码"是明确的分支动作而非顺手删代码；
- 每轮优化都写成"动机/现象 → 改动 → 证据 → 遗留"的记录文档（优化1、空洞删除段设计、
  读并行设计(废弃)），收尾时有架构总结、算法与策略、亮点评析三篇相互引用的文档——
  **决策可追溯，是这类项目最稀缺的资产**。

## 5. 性能结论

正式版 Release（详细档，多轮波动取同量级，详见 `测试/正式版Release.md`）：

| 场景 | 结果 |
|---|---|
| 缓存充足：read-only | **819k QPS**，P50 5 / P99 90µs，命中 100% |
| 缓存充足：read70/write30 | **394k QPS**，P99 603µs，读命中 100% |
| 缓存充足：write-only | **157k QPS**，P99 635µs |
| 缓存爆满 1:3:5：read-only（热子集） | **855k QPS**，P50 5 / P99 85 / P999 355µs，命中 99.9991% |
| 缓存爆满 1:3:5：read70/write30 | **125k QPS**，P99 3.8ms / P999 7.1ms，命中 96.38%，miss 100% file-ok |
| 缓存爆满 1:3:5：write-only | **52k QPS**，P99 3.8ms，写 24.4GB/30s |
| 命中率 2x / 3x | **48k / 38k QPS**，命中 89.2% / 84.2% |

关键读法：满盘热子集命中读 **85.5 万 QPS**（缓存充足 81.9 万，多轮 64~85 万），与 Redis 生产量级同档、
加网络层后即"差不多"；1:3:5 满盘下混合场景仍有 12.5 万 QPS 且命中率 96%+、miss 读 100% 成功、
自动压缩 16 次仅 1.45s（文件 7,991MB→2,172MB）；空洞复用把写放大与压缩频率打下来后，
**瓶颈已明确转移到磁盘单线程的 miss 串行读**（read70·30 中磁盘线程 busy 97.9%、读占 20.2s/30s，avg 212µs），
这是设计使然，也是读并行 v2 的切入点。

## 6. 诚实的边界（知道"止"在哪里也是亮点）

- **loader 未实现**（冷启动重建 inDisk + 空洞索引）——测试全新建库不需要，生产前必须补；
- **读并行 v2 未做**——v1 的失败证明这需要整套协议而非搬线程；
- 写放大（淘汰整版本追加 + 全量压缩）是"追加日志 + 整文件压缩"的结构成本；
- 压缩单次占住磁盘线程上百 ms 仍是 P999 尾巴来源。

这些"未完成项"与亮点一样被如实记录，正是第 4.4 条文档文化的延续——
**一个知道自己边界在哪、每一步都有证据的存储层**，是本次项目真正的交付物。
