## 0. 项目定位与总策略的起点

### 0.1 这个项目想做什么（为什么是"缓存中间件 + 磁盘"）

用户口径（收尾时补充）：
1. 通过做数据库项目加深对开发与操作系统底层原理的理解；
2. 部分设计学习 Redis，同时结合其它开源思路做"本地化"，锻炼能力；
3. 市面上未找到**支持自定义数据类型**的缓存中间件；
4. **Redis 是单线程，想做一个"更适应读多、写不被读拖累"的缓存中间件**（这一点直接催生了本文 1 章的线程模型选型）；
5. 让简历更有竞争力。

需求列表（`设计阶段/需求列表.md`）最初只是：ADD/GET/DEL/MOD + 持久化 + 导出 + 自定义类型注册。
架构设计（`架构设计.md`）把形态定为两个模块：缓存模块（CRUD 高频区）+ 磁盘模块（持久化），
外加 Controller 封装。**先有"缓存+磁盘"的分层共识，才有后面所有决策。**

### 0.2 为什么选"写回缓存（缓存为权威）"

`可行性分析.md` 开篇直接采用"使用写回缓存策略"，补充原因：

- **缓存与磁盘不一致时以缓存为准**：若以磁盘为准，每次操作都要等磁盘、产生大量磁盘 IO 浪费性能；
  缓存为主时数据操作全在内存，快；
- **代价可接受**：宕机会丢未刷盘数据，但磁盘上已有此前持久化的副本，重启后相当于**回溯**
  （并发注意事项 §9 也把"丢数据窗口"列为设计内接受的已知代价）。

由此派生出一串设计：脏标记 `isDirty`、批量后台刷盘（persisData/flushDisk）、"先清脏后写盘、
失败置回"的时序（见 3.5），以及删除=空洞（见 3.2）。

## 1. 核心线程模型：读并发 + 写串行 + 磁盘单线程

> 用户点名的例子："为什么选读并发而不和 Redis 一样选单线程？"

### 1.1 决策树的根：Redis 是单线程，为什么我们不能照抄

并发注意事项 §1 把最终模型定为 **读并发 + 写串行 + 磁盘单线程**。对"全串行（Redis 单线程模型）"
的否决理由记录在案：

> 全串行把**读读也串行化**，丢弃多核读并行。**读多写少**场景下，读并发有实际吞吐收益；
> 写串行已满足结构安全，没有必要让读也付出串行代价。（`并发注意事项.md` §二）

本项目要做的正是"Redis 单线程读串行"之外的那个方向——
**读要能并行**。所以模型不是 Redis 式的单线程事件循环，而是：
读任务丢给读线程池（多核并行、读读共享锁并发）、写任务单线程串行、磁盘 IO 单线程串行。

### 1.2 其它备选模型与否决理由（全部有记录）

| 备选 | 否决理由（出处：并发注意事项 §二） |
|---|---|
| 缓存任务**多线程并发写** | 写必须串行：`unordered_map` 结构竞争 + rehash 迭代器失效。多线程写要锁互斥，效果 ≈ 单线程串行，还多锁竞争与上下文切换 |
| **Redis 单线程全串行** | 这会放弃**多核**下读并行；读多写少场景读并发有真实收益 |
| **无锁设计**（时间戳比较/布尔状态） | 比较与写入不原子，检查-写入两步仍是竞态；读者需要"正在读的数量"，计数+原子即读写锁底层；无锁只是换实现自担风险，对微秒级内存操作零收益 |
| **读优先读写锁** | ①读者多时会读到旧值，时效性问题无法用上限兜底；②写者饥饿（脏数据刷不下去）只能靠上限缓解。反选**写者优先** |
| **磁盘多线程 + 文件锁** | 磁盘 IO 低频，单线程天然串行，省掉文件写锁与 inDisk 的全部锁；多线程写要处理偏移竞争、fsync 并发，收益为零 |
| **锁内做磁盘 IO** | 毫秒级 IO 持锁会阻塞一切读写；正确做法=锁内拷贝快照→解锁→写盘 |

### 1.3 为什么"写串行 + 磁盘单线程"反而正确且省事

- 写串行保护了 `cache_db`（结构竞争/迭代器失效是硬约束，见并发注意事项 §3），只需和读互斥就行；
- 磁盘单线程 = **inDisk/文件句柄/空洞索引全部只被一个线程访问 = 天然无锁区**，
  删除、覆盖、压缩、空洞登记之间的顺序是程序顺序而非锁序——正确性推理成本极低；
- 已知代价：miss 磁盘读被串行（成为后期第一瓶颈，见第 6 章），但"先求正确、再按证据放宽"是主线。

### 1.4 写者优先会饿死读者怎么办 → 差距记账 + 批放行

写者优先（有写者排队新读者不插队）保证读到的数据新，但可能让读饥饿。
方案（`设计优化.md` §缓存2、并发注意事项 §5）：用 `readSubWrite`（读任务 − 写任务）记账，
**写太多（≤ 下界 minDisEdge）就放行一批 `batchSize` 个读插队名额；读太多（≥ 上界且无写者等）清账重来**。
双向防饿只靠两个阈值 + 一个批名额，没有重量级公平队列（详见 5.1）。

## 2. 异步形态：future + 续延链（"只投递不等待"）

### 2.1 接口为什么用 future 而不是引用传返回值

`设计优化.md` §缓存1 记录：引用传值只能在同步场景——调用方线程继续执行后引用对象可能已析构，
接口再向悬垂引用写数据就崩溃；**future 适合异步**：提交即返回，需要时 `get()` 阻塞取。
本层所有后台任务在专属线程执行，天然异步，故统一 `std::future<int>/future<SelResult>`。

### 2.2 为什么服务线程"只投递不等待"（慢 IO 隔离）

并发注意事项 §7 的三条原则：
- 磁盘写（持久化/刷盘/重写）：提交任务立即返回，调用者不等；
- 磁盘读（未命中）：返回 future，**只有发起该次读的上层线程 get() 阻塞**，其它读任务不受影响；
- 磁盘线程访问 cache_db 只做微秒级拷贝/回填，真正的毫秒级文件 IO 全程锁外。

效果：慢磁盘 IO 被隔离，不占死写线程/读池——否则写线程同步等一条毫秒级 IO，
它队列里成百上千个微秒级写请求全部排队（吞吐崩塌、尾部暴涨）。

### 2.3 续延链（AsyncResult）：一段请求拆多段，跨线程投递

addData 被拆成：写线程查缓存 → 磁盘线程查磁盘索引 → 写线程插入，段与段在两条队列间交替。
设计点与理由（cache.h 注释）：

- **promise 桶 shared_ptr 跨段共享**：各段闭包值捕获同一桶；
- **段体异常统一 `set_exception`**：线程池 work() 会吞异常，漏记会让调用方 `get()` 永久等待；
- **线程停止兜底 `fallback()`**：后续段被拒收（线程池已停止）时兑现兜底错误码。
  这两条把"谁都能吞异常/线程会停"的异步常态风险堵死。

为什么不让写线程在段2 同步 `get()` 等磁盘线程？——就是 2.2 的慢传导问题：
等一次 = 写线程被那条磁盘任务占住，阻塞其后全部写（cache.h 有完整注释论证）。

## 3. 磁盘文件：格式、空洞、压缩的演进

### 3.1 记录格式：单文件自描述记录（不用独立索引文件）

演进证据（磁盘模块分析/设计优化）：

- **为什么单文件、数据与索引合并**："为什么不分索引文件和实体文件：减少磁盘 IO 次数"——
  `inDisk` 已把"名字→偏移"放内存，文件内无需再维护索引区；
- 记录 = 定长头 + 实体：`校验码(1) + 实体大小(4) + 时间(17=更新8+过期8+永久1) + 类型名(32) + 变量名(32) + 实体`，
  头 **86B 定型**（变量名变长必须有上限，写不满补 `\0`，超长返回失败码）；
- 为什么**不要独立删除码集合 delDisk**："允许崩溃回溯，并减少项目复杂度"——删除状态直接写在文件头，
  用 `CHECK_*` 三态表达：`CHECK_VALID(0x5A)` 活 / `CHECK_DELETED(0xFF)` 已删(洞) / `CHECK_BROKEN(0x00)` 残尾；
- **两段式写**：先整条写 BROKEN，写毕回写 VALID——写一半崩溃的记录在重建时被当残尾截断，
  不产生坏数据；重建/跳读规则只有一种：`下一条 = 当前 + 86 + dataSize`。

> 如果写失败，那么说明未写完，会出现无效校验码，那么dataSize是不是错的？这会导致顺序偏移错乱？

### 3.2 空洞策略的三步演进（项目里最典型的"想明白了再做"）

**Step 1（设计期）为什么不做"空洞链表"**——可行性分析/并发注意事项都记录了三段否决理由：
1. 空洞链表要持久化（文件头或索引区），崩溃恢复复杂；
2. 每次写都要读洞头确认大小找合适的洞，洞比数据大时分裂出更小的洞（碎片化）；
3. 唯一收益是降重写频率，但每次增删改都要动态维护，反而增加磁盘 IO。

于是初期结论：**空洞不管理，留给整文件重写回收**（设计优化 §3"覆盖会产生碎片，留空洞等重写回收"）。

**Step 2（初期实现）**：追加式日志 + 容量到上限才全量重写。跑起来后发现：
观测数据（空洞删除段设计 §1）：30s 内自动压缩 **38~41 次、总耗时 4.4~7.7s（磁盘线程 15%~25% duty）**，
每次都是"顶到上限(~500MB)才整文件重写"，热更新/淘汰的整版本追加把文件喂到 cap。

**Step 3（二轮优化）空洞/删除段设计 A+**：推翻"空洞不管理"，但**不是回到空洞链表**，
而是新的形态——**空洞是文件里显式自描述的对象**：
- 删除/覆盖旧版本 = 记录头 1 字节改 `CHECK_DELETED`（dataSize 保留），整段成洞、可跳读可复用；
- 内存只维护一份**可由文件重建的空闲索引** `holes`（`multiset<(容量,偏移)>`），运行期磁盘单线程同步维护；
- 崩溃后 loader 顺序扫文件即可重建（规则后置定义，见 3.6）。

这里的决策要点（空洞删除段设计 §4.2）：
| 备选 | 否决理由 |
|---|---|
| 空洞**链表/内存顺序表** | 见 Step1 三条；且运行期索引改成有序表只是"分配选择器"，不参与文件正确性 |
| **max-heap（大洞优先）** | 大洞被反复切成中/小洞，很快没有能容纳 1M~10M 大记录的洞 → 碎片加剧 |
| **first-fit（按偏移找第一个）** | 需沿偏移扫描、小洞堵在前部，碎片与复杂度都差 |
| **best-fit（lower_bound 最小够用洞）** | **选中**：记录大小严重不均时保留大洞给大记录，碎片最少 |

配套规则（空洞删除段设计 §3.2/§4.1/§10）：
- **切洞阈值 ≥86**：覆盖缩小或复用后，剩余 ≥86 才写洞头登记（洞段最小合法长度 86）；
  剩余 `0<R<86` 无法表达成任何自描述段 → **回退追加**，否则顺序扫描错位（链断）；
- 洞头实际只写 code+dataSize 共 5B（跳读只依赖这两字段）；
- 旧版本被取代时**一律显式标洞**（顺带修复"旧 VALID 残留会被 loader 复活"的隐患）；
- 写洞失败恢复：该段恢复 DELETED 并放回索引、回退追加。

效果（空洞删除段设计 §10，场景2）：QPS 83k→124k；追加字节 −61%（15.3GB→6.0GB）；
自动压缩 41 次/4.0s→16 次/1.5s（~5% duty）；P999 13.9ms→7.1ms。

### 3.3 压缩（reWrite）的两步演进：新文件 → 原地两阶段

**Step 1 设计稿**：写新文件 + 删旧文件（磁盘模块分析）。代价：磁盘利用率砍半；
崩溃全损属极端情况，交给运维（事先备份文件，可行性分析/设计优化都这样记录）。

**Step 2 实现**（优化1 §7）：**不用 tmp 文件**（磁盘利用率优先）改成**原地两阶段**：

- 阶段A 搬"缓存没有/干净"的记录（读旧写新、长度不变 → 写游标永远 ≤ 读游标）；
- 阶段B 缓存脏 key 最后写（旧区已无可读记录，变大也安全）；
- 阶段C 全新数据追加；末尾 `resize_file` 截断；成功清空 holes。

为什么必须两阶段——**证据**：自动压缩曾几乎全失败（fail 6348/6351），
失败现场集中在"小 offset + 文件顶到上限"：原地从 0 紧凑重写时，中途写入"变大的缓存记录"
会让写游标越过还没读的旧记录（写覆盖读）→ 读到半覆盖区 → 压缩中断、索引陈旧、之后在同一点反复失败。
两阶段 = "长度不变的先搬、可变的后写"，是让原地重写安全的最小充分条件。
（另：为什么不做局部压缩：会制造难以利用的细碎洞、空间利用率下降、压缩更频繁——"贵但少"。）

### 3.4 偏移 64 位化的由来（一个典型的数据驱动修复）

`int` 偏移在文件超 ~2GiB 后溢出为负，磁盘读全失败（file-ok 掉到 9%~18%）。
现场打印 `[SEL-FAIL] offset=-2139695632 fileLen>2GiB` 一眼定位（优化1 §5）→ 全链路 `long long`。
这同时暴露了更深的问题：`maxSize` 从未生效、文件无界增长——于是有了容量执行
（追加超限先自动压缩，仍超返回 MEMO_OUT；见 3.7）。

### 3.5 脏数据落盘时序：为什么"先清脏、后写盘、失败置回"

代码实现部分细节分析：写盘前先把 `isDirty` 置 false，写盘失败再改回 true。
若写文件之后再清脏：磁盘线程等锁期间缓存可能已并发改出**新脏数据**，写完后磁盘线程又把
新脏数据误清成"干净"——丢更新。先清再写 + 失败恢复，杜绝这个窗口。

### 3.6 崩溃一致性与 loader（后置但规则先定）

- 两段式校验码 + 批 flush（删除标记/洞头/记录随所在写任务批 flush，不逐条）——单线程内读写有序，
  可见性由此保证；
- loader（冷启动重建）：顺序扫描一次重建 inDisk + 空洞索引、CHECK_BROKEN 截断残尾
  （空洞删除段设计 §7）。**为什么本阶段未实现**：测试全部全新建库，不需要重启重建；生产必须补，
  归管理层阶段。这是明确的后置决策，不是遗漏。

### 3.7 容量执行（maxSize/MEMO_OUT）

优化1 §6：maxSize 只在构造时保存、从未被检查（无界增长的根因）。修复：写路径统一执行
"追加将超限 → 先 flushSync 提交缓冲 → 自动 reWrite 回收 → 仍放不下返回 MEMO_OUT(300)"；
批量写遇 MEMO_OUT 立即中断。MEMO_OUT 变成双语义：内存满/磁盘满。

## 4. 缓存淘汰：从标准 LRU 一路改到"全局采样 + 分档评分"

这是最长的一条决策链（LRU淘汰算法优化 + LRU实现细节处理 + 设计优化 §6）。

### 4.1 起点：为什么标准 LRU 不够

需求里缓存要按字节容量管（`curSize vs memoSize`），且要存大小差异极大的自定义类型。
标准 LRU（力扣语义）的局限（LRU淘汰算法优化 §局限性，两个例子）：
1. 大对象只要不是最久没用就永不淘汰 → 缓存被大数据占满、条目数少、淘汰频繁、命中率低；
2. 单次访问一个大数据会挤掉大量热门小对象 → 缓存污染 + 后续大量磁盘 IO。

因此维度不能只有时间，要加**数据大小**。又发现"使用频率"不适用：
热点有**时效性**（秒杀数据一小时 100 万次、之后一周不访问，频率很高却应清掉）→
改用**最近访问间隔**（interval），它已隐含频率信息且无污染问题。

### 4.2 评分公式的演化（每步都在解决上一步的问题）

```
标准 LRU(单维时间)
  → 双维 ln(interval) + ln(dataSize)        // 压缩量纲
  → 发现问题：log 把量纲压太狠，一天 vs 一小时差距太小
     （1MB 只新 20 分钟就因大 10 倍反超热门 100KB×3 小时，先被淘汰）
  → 给 ln(interval) 乘系数 3：仍不行——静态系数无法适配所有业务；
     动态系数则每个分数依据不同函数算出，淘汰没有统一标准，无意义
  → 定型：时间【分档】而非连续量：score = 时间档位 × 档距(30) + ln(dataSize)
```

为什么分档+档距是对的设计：
- 档距`(比如30)` > ln(memoSize) 上限（10GB ≈ 23）→ **跨档绝对无法靠大小翻盘**：冷数据永远先于热数据；
- 同档内比 `ln(dataSize)`：优先删大对象（腾空间最快）；
- 无参数可调：档位是自然时间锚点（1min/1h/1d/7d，测试接口换成 ms/s 级档位），极端情况重分档即可。

### 4.3 采样：Redis 采样思想 + 最终"不要链表"

参考 Redis 随机采样淘汰，但采样区最初定在"LRU 链表尾部（冷区）"，
配合优先队列避免每轮 O(n) 重采样（LRU淘汰算法优化 §优先队列优化）。
**最终实现**推翻了"哈希链表 LRU"本身（LRU实现细节处理，全文 5 行）：

> 我们不能用链表，因为这会让锁的粒度更大，锁的争抢会更严重，性能下降太多，
> 只能舍弃部分命中率来维持性能。

于是变成 **无链表的全局采样**：从 `unordered_map` 随机起点桶环形扫样本 → 大顶堆按 evictScore
→ 每轮 pop 堆顶、堆空补采；"采样(共享锁内只读) 与 淘汰(独占锁删) 之间数据可能变"用
**删前锁内重校验**解决；脏数据浅拷贝攒批落盘（cache.cpp evict）。
命中路径因此零链表维护（只刷一个 relaxed 原子时间戳）——与"临界区最小化"原则一致。

### 4.4 配套细节：为什么数据大小要用户给 theSize

LRU实现细节处理第 1 行：数据大小只能在**序列化后**精确计算，会损失很多性能 →
要求用户自定义类型提供 `theSize` 成员函数（轻量估算），序列化只发生在落盘时。

### 4.5 淘汰执行时机与目标

写线程内、插入/回填超限后触发（防刚插入就超限）；先全扫清过期，再采样淘汰到
`curSize < 90% × memoSize`（留余量防抖动）。过期=TTL 语义，不算 miss（统计口径在 cache.h）。

## 5. 锁与调度的两个"写优先 + 防饿"

### 5.1 WritePrefMutex：账本式双向防饿

设计优化 §缓存2 + writePrefMutex.cpp：
- 读者进入条件：无写者写 **且**（无写者排队 或 持批名额）；
- 记账在 unlock 内封装：读者离开 `readSubWrite+1`，到上界且无写者排队→清账关批；
  写者离开 `readSubWrite-1`，到下界且批未开→`batchRemain=batchSize` 放行一批读者插队。
- 为什么用"任务差账本 + 批"而不是公平队列：实现小、无锁内额外结构、
  只在临界（写多把读饿）时干预，正常读多时零开销（只两个整数加减）。

### 5.2 磁盘线程双队列差距调度（upEdge=15 / lowEdge=-5）

磁盘模块分析 + taskThreads.h：缓存任务（微秒：inDisk 查重/删索引）与磁盘任务（毫秒：文件 IO）
分开排队；`taskGap = 缓存处理数 − 磁盘处理数`：
- 常态缓存任务优先（快任务不被慢 IO 堵死）；
- `taskGap ≥ 上缘` 且有待处理磁盘任务 → 让位处理一个磁盘任务（防快任务无限积压饿死慢任务）；
- `taskGap ≤ 下缘` → 清零重计（防连做磁盘任务饿死缓存任务）。
与 WritePrefMutex 同一个思想：**用廉价差记账实现"优先 + 不饿死"**。

### 5.3 热度字段`updateTime`原子化（一个"小改大修"的正确性案例）

读命中在**共享锁**内刷新 `updateTime`，多读者并发写同一非原子 `time_point` = 数据竞争 UB，
不是性能问题。改成 `std::atomic<long long>`（µs、relaxed）：并发写安全且 relaxed 无屏障开销，
行为零漂移（优化1 §1）。
教训：共享读锁不等于"锁内随便写"。

## 6. 读路径演进与"为什么不读并行"

### 6.1 读路径的三次瘦身（证据驱动）

1. 序列化/反序列化零拷贝（`VecBuf/VecStream` 直写记录缓冲、`MemInBuf` 只读解析）——去掉
   stringstream→string→vector 的 MB 级两轮拷贝；
2. miss 读复用常驻句柄，去掉每次 open/close（优化1 §3/§8）；
3. 效果：未命中单条读 avg ≈1,480µs → ~750µs（优化1 §8 数据）。

### 6.2 为什么 miss 读至今不并行（读并行 v1 的教训）

- 现状：miss 读是 DISK_TASK，在**磁盘单线程**串行（读并行设计(废弃).md §1 数据：
  读 15.8s/30s、21k×~750µs），是当前第一瓶颈；
- **曾试过**：一版读并行实现（备份版本）**实测反而恶化，已回退**（已确认）；
- 为什么"只把 miss 读挪去线程池"不行——废弃稿总结出需要整套协议：
  ① inDisk 需要 shared/exclusive 锁且读锁要**横跨整个文件读**（否则"删除复活"）；
  ② 偏移"发布"必须后移到 flush 之后（先落盘后可见），单线程时才安全；
  ③ 压缩 reWrite 会原地改写文件，并发读者会读到半改写区 → 压缩须全程独占；
  ④ 命中读路径不能变（快读池不碰磁盘是好性质）。
- 结论：v2 要按废弃稿重新设计（新增磁盘读池、发布时序、压缩互斥），不能搬线程了事。

> 恶化也可能是其他原因，因为当时不知道还有其他瓶颈和错误，但是现在**暂时不考虑优化读并行了**
> 因为裸接口的性能目前看来暂时足够，并且这个优化比较复杂，需要进行很大的设计和改动

## 7. 一致性 / 可见性策略汇总

| 问题 | 方案 | 为什么 |
|---|---|---|
| 写一半崩溃 | 两段式校验码（BROKEN→VALID） | 重建时把 BROKEN 当残尾截断，规则唯一 |
| 物理落盘时机 | 批 flush（写任务批末/显式落盘点） | 合并物理 IO；单线程顺序保证可见性 |
| 删除 | 擦 inDisk + 1B DELETED（删除即空洞） | 删除状态可随文件重建（loader），无需独立删除表 |
| TTL | 惰性三判定点（命中时/读盘后/淘汰全扫） | 功能寄生在既有路径，不养清理线程；过期不算 miss |
| 脏数据权威 | 缓存为主、先清脏后写盘、失败置回 | 防并发误清；丢窗口设计内接受（回溯语义） |

### 7.1 写失败后的文件一致性：截断回滚（已实现）

**风险**：appendRecord 是"整条写 → seekp 回写 VALID → 才检查 `!file`"，bulk 写**半途失败**时
物理文件可能已残留半条（头为 0x00），而 `inDisk/curSize` 只在成功后才更新（仍等于写入前长度），
二者不再一致。下一次追加用 `seekp(0, end)` 会在**残渣之后**继续写——
残渣夹在两次成功记录中间时，**未来 loader 顺序扫描遇到中间 0x00 就截断，会把残渣之后的有效记录全部误丢弃。**

**处理（只改失败路径，正常路径零开销；disk.cpp appendRecord / tryOverwriteInPlace）**：

- **尾部追加失败（appendRecord）**：写入前记录 `offset`（`seekp(0,end); tellp()`）；
  失败分支 `clear()` 清 badbit → `flush()` 先把同批**此前已入 inDisk/清脏的记录**落盘 →
  flush 成功则 `resize_file(dbName, offset)` **截掉半条残渣（写失败的区块不留）**；
  flush 也失败（如盘仍满）则保留缓冲，交调用方"脏标记恢复 + 重试追加"自愈，不强截断；
- **中间覆盖失败（tryOverwriteInPlace）**：槽可能已被半写污染 → 把**旧 code + 旧 dataSize**
  写回原位置，槽恢复为"长度 = 旧槽"的自描述记录（body 混合旧/新，链不断，
  等下次成功刷盘以新版本取代/标洞）；**不能只恢复 code**——dataSize 若被新值覆盖，
  槽长改变会让顺序扫描/loader 错位；
- **复用写洞失败（tryUseHole）**：本就把该段恢复 DELETED 头 + 放回索引，无需改。

**代价**：仅失败路径多一次 flush + 截断 IO（写失败概率低，一般不会触发，可接受）；
flush 可能在用户态缓冲未满时就送入内核，极端失败场景下略微降低缓冲利用——
换来文件一致性安全（用户判断：比"整槽重写覆盖"性能稍弱，但安全性与简洁性更好）。

**边界**：进程崩溃时无代码可执行，残尾仍靠 loader 的 BROKEN 截断语义兜底——两者互补；
即 loader 上线前**无需再为"代码内可恢复写失败"额外处理**（此项已闭环）。

> 用户注：总之就是处理写失败后的顺序偏移定位问题——要么删除写失败的区块
> （记录原文件大小 A，写失败后清空 A 偏移后面的数据），要么把原 dataSize 写回原位置（覆盖场景）。
> 现状（全新建库测试）不受影响的原因不变：loader 未实现时崩溃残尾从未被扫描到。

## 8. 容量建模与测试策略的决策链（为什么 1:3:5）

### 8.1 为什么缓存:数据集:磁盘 ≈ 1:3:5

依据（优化1 §13.1 + Redis 官方 Auto Tiering/Flex 文档）：
- 适用场景："工作集 << 总数据 + 热点"（RAM 高命中率）；
- 官方容量建议：RAM 至少放全部 value 的 ~20%，闪存 ≥ 总量 + 写缓冲/**写放大**余量；
- 因此 test3 定 100MB 缓存 / ~300MB 数据集 / 500MB 磁盘；Pika 为反例（面向全量落盘，无此分层模型）。
为什么不用更小的数据集（如 1:1）做主线：1:1 时"全量读 = 全命中"，测不到缓存中间件最该被考验的
miss/回填/淘汰路径；1:3 才让"热子集命中 vs 冷数据 miss"同时存在。

### 8.2 测试方法论上的自我修正（很典型的"先失真后修正"）

- 纯读档曾把 1:3 全数据集都当读目标 → 变成磁盘冷读、QPS 失真 → 修正为**纯读档限定热子集
  ≤0.7×缓存**，语义改为"内存命中读"；冷读/命中率语义划给命中率档；
- 写请求尺寸曾含 10M 顶档 → 版本放大失真 → 削成 4K~1M 同量级（log-uniform）；
- 新增 key 曾注入洪流 → 改为缓慢增长（60 条 / 500ms ≈ 2 key/s）模拟真实数据集增长；
- `WRITE_INFLIGHT`（在途写深度）把"稳态在途写"打出来，避免退化成同步写；
- 延迟分位用蓄水池采样（每线程 20 万样本上限）——30s 高 QPS 全量样本会占数百 MB 内存。

### 8.3 探针治理

全周期用探针（阶段计时/miss 分类/失败现场/队列 busy）做归因，Release 前统一 `#if 0` 保留源码，
正式输出收敛为 QPS/P99/命中率三行——"删除测试点代码"是明确动作而非顺手删。
