# 空洞/删除段设计（A+：文件内自描述链 + 空洞复用）

**核心：对之前文档中提到的`空洞链表`进行优化并应用，减少压缩频率（重写频率）**

> 状态：设计稿（未实现）
> 目标：把"数据文件因整版本追加而膨胀 → 高频全量压缩"改成"删除即空洞、空洞可复用"，降低追加量与压缩频率；
> 压缩仍保留"整文件重写"为唯一手段（不做局部压缩）。冷启动 loader 后置（管理层阶段做），但**链与标记规则本稿先定义死**。

---

## 1. 背景与目标（数据）

压缩观测（场景2，1:3:5 编排后）：
- `disk-compact: 38~41 runs / 30s`，总 4.4~7.7s（磁盘线程 15%~25% duty），单次 avg 117~187ms；
- 压缩前文件 ≈ 上限(~500MB)，压缩后 ≈ 活跃数据(~140~250MB) → 每次顶到上限才全量重写；
- 根因：热更新/淘汰刷盘**整版本追加**，旧版本成隐式空洞，文件只增不减直到 cap → 压缩。

目标：删除/覆盖产生的空间在文件内**显式化（洞段）并可复用** → 追加量↓ → 触发压缩频率↓。

---

## 2. 核心思想：删除的数据就是空洞（洞在文件里，不在内存链表里）

- 早期文档否决的是"内存单独维护空洞链表 + 每次写去读洞头"（IO 多、复杂度高、收益低）。
- A+ 是另一个形态：**空洞段是文件里显式的自描述记录**（用 校验码 + dataSize 就能顺序跳读，包括空洞）；
- 内存只维护一份**可由文件重建的空闲段索引**用于分配选择；运行期索引与文件由磁盘单线程同步维护；
- 崩溃后重启：**顺序扫描文件一次**即可重建索引与 inDisk（算法见 §7；loader 代码后置）。

---

## 3. 文件段模型与格式

### 3.1 段类型（复用/扩展现有协议）

| 状态 | 含义 | 顺序扫描行为 |
|---|---|---|
| `CHECK_VALID`(0x5A) | 活记录 | 读入；下一条 = 偏移 + 86 + dataSize |
| `CHECK_DELETED`(0xFF) | **已删 / 空洞段**（同一语义：该段字节不可作活数据，可被复用） | 跳过；下一条 = 偏移 + 86 + dataSize |
| `CHECK_BROKEN`(0x00) | 残尾（写一半崩溃） | 截断文件到此处 |

- **不新增状态码**：删除与空洞统一用 `CHECK_DELETED`（命名上可保留"删除"或改注"删除=空洞"；语义 = 可复用段）。
- 记录头统一为现有定长头（86B：code + dataSize + 时间 + type + name），**活记录与洞段共用同一头格式**：
  - 活记录：dataSize = 实体字节数，后接实体；
  - 洞段：dataSize = 剩余容量（实体区为空/脏数据无所谓，复用时被覆盖），type/name/时间字段置零。
  - 统一头的好处：洞被复用写入活记录时不需要改跳读规则；顺序扫描逻辑只有一种。

### 3.2 两条基础链操作（写路径，磁盘单线程执行）

- **删除（delData / 过期清理）**：擦 `inDisk` 索引 + 把记录首字节改写为 `CHECK_DELETED`（旧头 dataSize 保留）→ **整段（86+旧dataSize）成为空洞，1 字节写**。段长即旧记录总长，无需重写头。
- **覆盖缩小（modData/淘汰刷盘命中已有旧记录）**：新记录总长 `V = 86+新dataSize`，旧槽总长 `T = 86+旧dataSize`：
  - `V == T`：原地覆盖，链不变，无需额外动作；
  - `T - V ≥ 86`：原地覆盖新记录，并在 `偏移+V` 处写一个 DELETED 头（dataSize = T−V−86）→ 剩余区成为显式空洞段，链完整；
  - `0 < T - V < 86`：剩余不足一个洞头 → **不做覆盖，回退追加**（否则链断，重建会错位）；
  - `V > T`：回退追加（现状，旧段留在文件由压缩回收）。

> 覆盖前需先读旧头 dataSize（磁盘线程 4B 读）。等长覆盖概率低（modData 后几乎不等长），真正收益在"缩小覆盖 + 剩余区写洞头"，所以本设计以缩小覆盖为主路径。

## 4. 空洞复用（分配）

### 4.1 何时可以放洞
某段为空洞（内存索引登记），且 `段容量 ≥ 记录总长` 时，可把记录写进洞段首（覆盖该段 DELETED 头）：
- 剩余 `R = 段容量 − 记录总长`：
  - `R ≥ 86`：记录后写 DELETED 头（dataSize=R−86）→ 剩余洞保留；
  - `R < 86`：整段利用（无剩余，浪费 <86B，不写洞头）。

### 4.2 内存索引与选择策略（关键决策）

- 结构：**按容量有序**，例如 `std::multiset<std::pair<long long,long long>>`，pair = (段容量, 偏移)；
- 选择：**best-fit** —— `lower_bound(记录总长)` 取"不小于需求的最小洞"；
- **不用最大洞优先（max-heap）**：大洞会被不断切成中/小洞，很快没有能容纳大记录（1M~10M 级）的洞 → 碎片加剧；
- **不用 first-fit**：需沿偏移扫描、且小洞堵在前部 → 碎片与复杂度都差。
- 记录大小严重不均（1K~10M）时，best-fit 保留大洞给大记录，碎片最少。

### 4.3 索引生命周期（全部在磁盘单线程上维护，天然无锁）

| 事件 | 索引操作 | 文件操作 |
|---|---|---|
| 追加到文件尾 | 无 | 写 VALID 记录（现状） |
| 覆盖缩小（有旧记录且放得下） | 若有剩余：登记剩余洞（容量= T−V−86，偏移=V'） | 覆盖 + 写洞头 |
| 删除 / 过期清理 | 登记整段洞（容量=旧记录总长） | 1 字节改 DELETED |
| 写入洞段（复用） | 移除该洞；有剩余再登记剩余洞 | 覆盖洞头为 VALID 记录(+洞头) |
| 压缩（整文件重写） | 清空（紧凑文件无洞） | 全量重写 |
| 崩溃后/冷启动 | 由文件顺序扫描重建（loader，后置） | — |

### 4.4 插入洞 vs 追加的取舍
优先复用"容量刚好的洞"；若没有可用洞 → 追加。追加仍会增长文件，但压缩触发频率已因复用大幅下降。

---

## 5. 压缩策略（保持全量重写，不做局部压缩）

- **局部压缩会制造难以利用的细碎洞 → 空间利用率下降 → 压缩更频繁**，故本设计不做；
- 整文件重写一次把所有洞收拢、利用率回 100%——"贵但少"；
- 触发：
  1. **硬上限**（现状）：`curSize + 新记录长 > maxSize` → 追加前自动压缩（现有两阶段原地压缩保持不变）；
  2. （可选）**软水位**：`空洞总量 > maxSize × 阈值` 且接近水位时提前压缩 —— 空洞总量可由内存索引实时求和（每段登记时累加），实现容易，先列为可选。
- 压缩后索引清空（新文件紧凑）。

---

## 6. 一致性 / 崩溃语义

- 沿用两段式写（先 CHECK_BROKEN 整条，写毕回写 CHECK_VALID）与批 flush 时机；
- 删除标记/洞头也遵循"随所在写任务批 flush"的可见性规则（单线程内读/写天然有序；delData 的 1 字节标记写并入所在任务 flush，具体在实现时收敛调用点）；
- **运行期**：文件与内存索引一致性由磁盘单线程保证；
- **崩溃后**：无 loader（后置）时本阶段测试全新建库不受影响；**生产前必须补 loader**（见 §7），否则删除/洞与索引不同步会丢空间信息。

---

## 7. 冷启动加载（loader，后置实现，规则先定）

顺序扫描重建算法（一次读文件）：
```
offset = 0
while offset < 文件长:
    读头 code + dataSize
    if code == CHECK_BROKEN: 截断文件到 offset; 结束        // 残尾
    if code == CHECK_DELETED: 登记空洞(offset, 86+dataSize) // 跳过
    else (VALID): 读入记录 → inDisk[name]=offset            // 活记录
    offset += 86 + dataSize
重建空洞索引 = 登记的空洞集合（best-fit 有序表）
```
- 该算法同时校验损坏、截断残尾、恢复 inDisk 与空洞索引；
- 实现时机：管理层阶段（本层完成后）。

## 8. 待决策 / 备注

1. 洞头统一用 86B 定长头（推荐）vs 最小 5B（code+dataSize）：
   - 86B 统一 → 跳读/复用规则只有一种；洞容量 = 86+dataSize，复用记录直接覆盖；
   - 5B 更省空间但复用记录时洞容量要能装 86+payload，规则分裂。**选 86B 统一**。
2. 切洞阈值：剩余 ≥ 86 才切/写洞头；剩余 < 86 时整段利用（浪费 <86B）或缩小覆盖前直接判断 `T−V≥86`，否则回退追加；
3. delData 标记写入点的 flush 收敛（多处调用点：显式删/过期清理/淘汰相关）→ 实现时统一成"随任务批 flush"；
4. 软水位压缩（空洞占比触发）为可选项，先不做，等复用上线看观测再定。

---

## 9. 实施顺序建议（每步可独立验证）

1. 协议常量与注释：`CHECK_DELETED`(0xFF) + 段语义（删除=空洞）；
2. `delData`/过期清理：擦索引 + 1 字节删除标记（不引入复用）；
3. 覆盖缩小：新记录放得下（T−V=0 或 T−V≥86）→ 覆盖(+写剩余洞头)，否则追加；
4. 空洞索引（best-fit 有序表）+ 复用分配 + 切洞登记；
5. （可选）软水位压缩触发。

验证观测（复用现有 printDiskIo）：
- `disk-write MB/30s`、`disk-compact runs/time` 应随 2→3→4 逐步下降；
- 新增观测：复用次数（写进洞的次数）、追加次数、当前空洞总量/占比。
