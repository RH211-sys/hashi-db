# 读并行设计：缓存未命中（磁盘读）并行化方案

**核心：**处理`读未命中`带来的磁盘单线程多次阻塞读文件带来的瓶颈，需要改成并发读，提高未命中的读并发，

> 状态：设计稿（未实现）
> 目标读者：自己（存储层后续实现时对照）
> 语义优先，尽量直白；先讲清"谁在什么锁下干什么"，再讲实现点。

---

## 1. 要解决的问题（数据）

当前（场景2 read70/write30，95MB 预热池，优化1 完成后）：
- 磁盘线程 30s 内 ~96% 忙碌，时间账 ≈ **读 15.8s + 写 ~4s + 压缩若干**；
- 未命中读全部在**磁盘单线程**上串行执行（21k 次 × avg ~750µs）；
- 命中读（93%+）走读池很快，但读池只"提交 miss 任务"，不碰磁盘 → 命中读本身不受磁盘影响（这是**要保留的好性质**）；
- P99/P999 尾巴主要来自：miss 读 + 压缩这些长任务在单线程上排队，把后面所有任务（含其它 miss）拖住。

**结论：miss 的文件读是磁盘线程最大的一块串行开销，值得并行化；但并行方式不能破坏"命中读不受磁盘拖累"。**

---

## 2. 设计原则（三条，后面所有机制都从这三条推导）

1. **阻塞 IO 不放进命中读池**。命中读是读池线程干的快活；谁阻塞在磁盘上，谁就必须是"专门干磁盘活"的执行者（专用读池）。
2. **读并行只并行"文件读"这一件事**。inDisk 索引的查重/删除/发布仍由磁盘单线程串行做——顺序与可见性靠它保证。
3. **先落盘、后可见**。一条记录只有写完文件（含 flush）之后，它的偏移才对读者可见；读者永远读不到"写了一半/还没落盘"的记录。

---

## 3. 线程拓扑（目标形态）

```
            上层调用（等 future.get()）
                 │
        ┌────────┴───────────────┐
        │                        │
   命中读（快读池，多线程）      miss（只投递，不等待）
        │                        │
        │                  ┌─────┴──────────────────────┐
        │                  │                            │
        │            磁盘读池（新增，多线程）         磁盘线程（单线程，保留）
        │            只管：文件读+反序列化             只管：索引查重/删除/发布、
        │            读锁 = inDisk 共享锁                文件写(落盘)、压缩 reWrite
        │                  │                            │
        └──────────────────┴────────────────────────────┘
                  回填缓存 → 写线程（原样，后台）
```

| 执行者 | 任务 | 能不能阻塞在磁盘 | 备注 |
|---|---|---|---|
| 快读池（原样） | 命中读、过期判定、miss 的"提交" | 不能 | 保留"服务线程不等 IO" |
| **磁盘读池（新增）** | miss 文件读 + 反序列化 | 可以（本职） | 线程数可配，如 2~4 |
| 磁盘线程（单线程，保留） | `containsVar`、`delData`(删索引)、过期清扫、persisData/flushDisk（文件写）、压缩 reWrite | 可以 | inDisk 唯一写者，保顺序 |
| 写线程（原样） | 缓存增删改、淘汰、回填插入 | 不能 | — |
| 调用方 | future.get() | 可以 | — |

> 为什么不把 `containsVar` 也并行读？查重必须看到"已发布"的 inDisk；发布顺序由磁盘线程 FIFO 保证
> （先排队的淘汰落盘先发布，后来的 add 查重才看不到旧版本）。它是内存微秒级操作，留在单线程零成本。

## 4. 同步协议（核心）

### 4.1 Disk 内新增一把锁（语义直观）

```
Disk::rwMutex（可复用 Cache 那套 WritePrefMutex 或直接用 std::shared_mutex）
- 读锁(shared)：读者取偏移 + 读文件全过程
- 写锁(exclusive)：inDisk 增删/发布偏移、压缩 reWrite
```

锁保护的对象：`inDisk`（偏移表）+ "文件正被原地压缩改写"的互斥。

### 4.2 读者流程（磁盘读池线程执行 miss 读）

```
lock_shared()                      ← 读锁覆盖整个读文件过程
  offset = inDisk.find(name)       ← 看不到 = 没有（含未发布）
  seek/读记录（校验码、定长头、实体）
  反序列化
unlock_shared()
→ 把读到的 Val 交回缓存（cache 层投递给写线程回填，原样）
```

- 读锁**必须覆盖到文件读结束**，不是只取偏移：否则持锁期间删除执行后，读者仍会按旧偏移把已删数据读回来（删除复活）。
- 读者拿到的偏移一定已发布 → 记录必然完整可读（发布时序见 4.4），不需要校验码重试。

### 4.3 写者流程（磁盘线程执行落盘）

```
appendRecord 写文件（两段式校验码照旧）
flush（本批写任务结束处统一 flush）   ← 先落盘
lock()                                ← 再发布
  inDisk[name] = offset
unlock()
```

- 偏移"发布"从 appendRecord 移到 flush 之后（当前实现里 appendRecord 边写边登记，单线程才安全；并行后必须后移）。
- 批量 flush 时机不变：批末 flush 后批量发布（登记动作本身在磁盘线程内、一次独占即可）。
- `delData`/过期清扫擦 inDisk = 独占锁内 erase。

### 4.4 一条记录的生命周期（直白版）

```
写：文件里先有(BROKEN→VALID)，flush 到 OS → 再登记进 inDisk
删：独占锁 erase inDisk → 文件字节留作空洞（读者此后查不到）
压缩：独占锁 + 原地重写 + 截断（见 5）
读：shared 锁内查 inDisk → 一定查得到"完整已落盘"的记录
```

### 4.5 压缩 reWrite 与读的互斥

- 压缩会**原地改写文件**，期间并发读者会读到半改写区 → 损坏。
- 处理：压缩全程持**独占锁**。后果：压缩期间 miss 读会短暂等待（等价于现在的"读排在压缩后面"），
  但**命中读不受影响**（快读池没被占用）——这已经是净改善。
- 备选：压缩写新文件 + 原子换名（读总指向完整旧文件），但在 Windows 上对"打开的句柄"换名不友好，
  且你们倾向"无 tmp、磁盘利用率高"，故主方案取原地压缩 + 独占互斥。

## 5. 实现改动点清单（对照代码）

| 位置 | 改动 |
|---|---|
| `disk.h` | 新增读写锁成员（shared_mutex 或复用 WritePrefMutex）；`selData` 读路径加 shared 锁；inDisk 增删/发布处加 exclusive 锁；`reWrite` 全程 exclusive |
| `taskThreads.h` | 新增"磁盘读池"类（可复制 ReadPool 模板：固定 N 线程，跑文件读任务）；或泛化一个线程池供快读/磁盘读复用 |
| `controller.h/.cpp` | 创建磁盘读池并注入 Cache；对外暴露线程数配置；`getQueueStat` 等观测扩展 |
| `cache.h/.cpp` | `selData` miss 段2 由 `diskThread->submit(DISK_TASK)` 改为 **磁盘读池 submit**；读回后的回填仍投递写线程（不变）；磁盘读池停止时兜底与现逻辑一致 |
| `disk.cpp` | 发布时机后移到 flush 后；`containsVar/delData` 等索引读写加锁（若仍在磁盘线程串行则只需对跨线程读者加 shared 保护——即 containsVar 仍只在磁盘线程调，就只给"读者(读池) ↔ 写者(磁盘线程)"之间加锁） |
| 观测 | 新增：磁盘读池线程数/正在读的 miss 数、busy%；沿用现有 `disk-read avg`、`disk-queue`、`worker busy` 做前后对比 |

注意点：
- miss 读从"磁盘线程执行"改为"读池线程执行"后，`Disk::selData` 的执行线程变了；它内部只读 inDisk + 文件，
  不触碰其它线程私有状态，按 4.2 加 shared 锁即可。
- 读池线程数建议先 2~4，观测 miss 平均读时长与命中读 P99 再调。

## 6. 正确性推演（重点场景逐一过）

1. **发布竞态**：读者查 inDisk 前，写者已 flush 完但还没登记 → 读者查不到 → 正常 miss（再去磁盘线程？不，直接返回没有）→
   等价于"数据还没持久化完成"，与淘汰落盘前语义一致，不产生半截记录。
2. **删除复活**：删除要独占锁；读者 shared 锁横跨整个文件读 → 二者互斥 → 读者要么在删除前读完（拿到旧值，可接受：
   删除尚未生效的时刻），要么在删除后开始（查不到）→ 不会出现"删除后仍读到值"。
3. **压缩互斥**：压缩独占锁 → 期间无并发读；读池其它线程排队（只有 miss 读，不伤命中读）。
4. **查重顺序**：containsVar 仍在磁盘线程 FIFO → add 的"磁盘查重"一定排在它之前排队的淘汰落盘/发布之后 → 语义不变。
5. **批 flush 发布**：一个批量写任务 flush 一次、发布一批 → 读者要么整批可见要么整批不可见，无中间态。

## 7. 预期收益（先算账，再验证）

- 磁盘线程 30s 账单里 ~15.8s 读开销挪给 N 个读线程 → 读墙钟 ~15.8/N（受盘带宽/锁串行度打折）；
- 磁盘线程只剩写+压缩 → busy% 大幅下降 → miss 排队与 P99/P999 尾随之下降；
- 命中读路径完全不变 → P50 不受影响。
- 风险项：读池阻塞 = miss 突发时读池占满（这是预期内，读池可调大）；磁盘带宽上限 = 读再多线程也打不过物理盘。

**验证方法**（复用现有观测）：
- 场景2 对比：`disk-read avg/次`、`disk-queue depth`、`worker busy %`、P99/P999、QPS；
- 新增：读池 busy%、并发 miss 数；纯读 hit-rate 档（miss 多）看读并行收益最大处。
