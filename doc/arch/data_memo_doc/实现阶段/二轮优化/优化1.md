# 第二轮优化记录 优化1

> 内容：在"恢复原方案（单写线程 + 全局采样淘汰）"基线上做的一轮性能与正确性优化。
> 涉及模块：Cache（读命中热度原子化）、Disk（写路径/压缩/读路径）、线程与测试观测。
> 记录方式：每项 = 动机/现象 → 改动 → 结果；末尾附证据数据与提交建议。

## 0. 总览（这轮做了什么）

| # | 主题 | 解决的问题 | 主要改动 |
|---|------|-----------|---------|
| 1 | updateTime 原子化 | 读命中在共享锁内写 `time_point`：多读者并发写同一字段（数据竞争）+ 命中路径跨核写 | `Val::updateTime` → `std::atomic<long long>`(µs, relaxed)，配套自定义拷贝/移动 |

## 1. 方案三：读命中热度字段原子化（数据竞争修复，行为零变化）

### 现象
`selData` 命中分支在 `rwMutex->lock_shared()` 内执行
`it->second.updateTime = system_clock::now()`。共享锁允许多读者并发进入，
同一热 key 被多个读线程命中时 = 多线程并发写同一非原子 `time_point`（UB/数据竞争），
且命中路径每 hit 一次就产生一次缓存行跨核写。同时代码注释与实现语义互相矛盾。

### 改动
- `data_type.h`：`Val::updateTime` 类型由 `system_clock::time_point`
  改为 `std::atomic<long long>`（µs since epoch，relaxed），初始化 `{0}`；
  原子成员不可拷贝/移动 → 补自定义拷贝/移动四件套（atomic 字段 relaxed load 携带）。
- 全部读写点机械适配：
  - 命中刷新 → `updateTime.store(µs, relaxed)`（仍在共享锁内，位置不变）；
  - `addData` 置 now、磁盘回填沿用磁盘旧时间、`modData` 回填保持默认 0（与旧行为一致）；
  - `evictScore` 取 `load(relaxed)`；落盘处直接取 µs 整数（磁盘记录字节不变）；
  - 统一了三处互相矛盾的注释。

### 结果
混合读写性能几乎不变（符合"纯正确性修复"预期）：消除了数据竞争，无回归、无语义漂移。

## 3. 磁盘写路径：常驻句柄 + 序列化直写连续缓冲

### 现象（观测后确认）
- 每次持久化 `ofstream touch` + `fstream` 开闭一次；单条写后逐个字段多次小 `write`；
- `toBytes` 走 `stringstream → string → vector` 两轮整块拷贝，全压在磁盘线程上；
- 观测：写一条 avg `build(serialize)` 只占 ~1/4，**文件写占 ~3/4**。

### 改动
- `data_type.h`：`SerializeFunc` 改为 `void(*)(const any&, std::ostream&)`，
  `toBytes<T>` 直接写调用方提供的流（配合自定义 `VecBuf/VecStream` 输出缓冲 → 零中间拷贝）；
- `disk.h/.cpp`：
  - 新增私有成员：常驻句柄 `std::fstream file`、记录缓冲 `std::vector<char> recBuf`；
  - `ensureFileOpen()`（惰性创建/异常重建）；`buildRecord()`（定长头+实体拼一条记录）；
  - `appendRecord()`（追加位整条一次 write + 校验码回写）；
  - 4 个 `persisData` 重载与 `reWrite` 统一走 helper，删除每次 open/close 与多次小 write。

### 结果
- 磁盘记录字节格式不变，可读旧文件；崩溃窗口与 flush 时机保持原样；
- per-write 序列化成本显著下降（build 56~135µs / 700KB 量级），序列化不再是单条主成本。

## 4. 阶段计时与 miss 归类探针（观测器）

### 加装观测（均为零行为影响）
- 磁盘写分相计时：`build(序列化)` / `file(文件写)` / `flush`（总耗时+次数+条数+字节）；
- 磁盘读：`readCnt/readUs`（avg/次）；
- 磁盘线程：push 时双队列深度（avg/max）、worker 执行任务数/总耗时（busy %）；
- miss 去向分类：`selCalls / inDisk-miss / file-fail(细分 check/name/eof/type/open) / file-ok`；
- 失败现场抽样打印 `[SEL-FAIL]`/`[REWRITE-FAIL]`（前 N 条，带 key/offset/codeByte/fileLen）。

### 探针结论（一步步定位）
1. **假说排除**：miss 大部分不是"已淘汰未落盘"（inDisk-miss=0）；
2. 发现 **91% 的"有 offset 的读"在文件读阶段失败**；
3. 失败现场显示 **offset 为负、fileLen>2GiB** → 定位 `int` 偏移溢出；
4. 修完溢出后出现"offset 小但 read-head 失败 + 压缩反复失败(code=400)" →
   定位原地压缩"写覆盖读"，最终改两阶段原地压缩（见 §6/§7）。

## 5. 修复 A：偏移全链路 64 位化（int存不下偏移量，diskMemo未起作用）

### 现象
```
[SEL-FAIL] kind=check key=key_267 offset=-2139695632 codeByte=0 fileLen=2155302579
```
`offset` 为负、`fileLen > 2^31-1` → `inDisk` 存的 `int` 偏移在文件超 ~2GiB 后溢出；
`seekg(负偏移)` 失败 → 读全失败、file-ok 掉到 ~9%~18%。

### 改动
- `disk.h`：`unordered_map<string, long long> inDisk`；
- `disk.cpp`：`appendRecord` 存 `long long` 偏移；`selData` 偏移变量、`reWrite` 的
  `writePos`、排序 `vector<pair<string,long long>>`、`recLen` 全部 64 位化。
  记录格式不变。

## 6. 修复 B：maxSize(diskMemo) 真正生效 + 自动压缩

### 现象
`maxSize` 只在构造时被保存，全代码从未检查；数据文件"只增不减"（追加日志 +
`delData` 只擦索引不删字节 + 无自动 reWrite）→ 文件无界增长到几十 GB，磁盘 500M
上限形同虚设（这也是 §5 溢出能触发的根因）。

### 改动（disk.cpp appendRecord 统一执行，覆盖全部写路径）
```
if (maxSize > 0 && curSize + 本条长度 > maxSize) {
    flushSync();                 // 先提交本任务此前缓冲的追加（压缩读回安全）
    压缩 = reWrite();             // 自动回收空洞/截断
    if (压缩失败) return 错误;
    重建本记录；若压缩后仍放不下 → return MEMO_OUT(300);
}
```
- 批量函数遇 `MEMO_OUT` 立即中断（避免容量满时逐条反复触发压缩）；
  `persisData(varNameSet)` 会把已清 `isDirty` 的 key 置回脏；
- `maxSize <= 0` 视为不限；`protocol.h` MEMO_OUT 注释更新为双语义（内存/磁盘容量）。

### 注意
- 淘汰刷盘为 fire-and-forget，若配置导致"活跃数据 ≥ diskMemo"，其 MEMO_OUT 目前无人接收
  → 属配置错误场景，正常部署（diskMemo >> 缓存活跃集）不触发。

## 7. reWrite 改造：两阶段原地压缩（写覆盖读的根治）

### 现象
自动压缩几乎全部失败（`disk-compact: 6351 runs / fail 6348`，code=400），
定位打印 `why=read-head` 且集中在"小 offset + fileLen 顶在上限"：
**原地压缩从 0 紧凑重写时，若中途写入"变大的缓存记录"，写游标会越过后面还没读的
旧记录 offset（写覆盖读）→ 读到半覆盖区 → 压缩中断 → 留下半新半旧文件与陈旧偏移，
后续压缩在同一点反复失败。**

### 方案（按用户意见：不用 tmp 文件，磁盘利用率高）
两阶段原地压缩，全部在常驻句柄上完成，末尾 `resize_file(dbName, writePos)` 截断：
- **阶段A**：只搬"缓存里没有 / 缓存里干净"的 key —— 整条读旧写新、**长度不变**，
  写游标 ≤ 读游标，永远不会覆盖未读记录（干净缓存 key 与磁盘一致，读旧等价；
  期间变脏则脏位仍在，后续刷盘以缓存覆盖，最终一致）；
- **阶段B**：缓存里的**脏 key** 最后写 —— 它们可能变大，但此时旧区已无任何待读记录，
  可安全覆盖/追加；安全清脏：实体指针未变才清（防并发 mod 后误清）；
- **阶段C**：缓存里 inDisk 没有的全新数据追加写入；
- 失败出口：返回错误（中断语义同旧版：交运维），失败仅可能来自真实 IO 错误。

### 结果（场景2）
```
disk-sel:  calls X | inDisk-miss 0 | file-fail 0 | file-ok X      ← 读盘 100% 成功
disk-compact: 28~43 runs / fail 0                                 ← 压缩可靠，文件被压在上限内
```

## 8. 读路径瘦身

### 现象
未命中读 avg ≈ 1,480µs（21k 次读吃掉磁盘线程 ~2/3 时间）：每次
`ifstream` open/close + 读 ~600KB 记录 + `stringstream(string(bytes))` 两轮整条拷贝反序列化。

### 改动
1. **反序列化零拷贝**（data_type.h）：`fromBytes` 改用只读内存流缓冲
   （`detail::MemInBuf : std::streambuf`）让 cereal 直接在读出的 `vector<char>` 上解析，
   去掉 stringstream + string 两轮 ~MB 级拷贝（对单条/批量读全局生效，签名不变）；
2. **miss 读复用常驻句柄**（disk.cpp 单条 selData）：去掉每次 miss 的 ifstream open/close，
   改用 `ensureFileOpen()` 后的常驻 `file`（in|out）读。

### 结果（场景2）
```
disk-read: 21052 reads / 15838 ms (avg 752 us)   ← 由 ~1,480µs 砍半
disk-sel:  file-fail 0 | file-ok 21052
```
QPS 与写吞吐同步回升（QPS ~10.4k→17.4k，写 9.5k→14.7k 条；不同轮次构建模式有差异，看相对变化）。

## 11. 遗留问题 / 后续方向（未做）

1. **读并发化**：miss 读目前仍在磁盘单线程串行执行（21k 次 × 750µs ≈ 15.8s/30s）。
   真正并行需解决：`inDisk` 并发读安全、每线程/共享句柄、压缩与并发读互斥
   （或"压缩写新文件+原子换名"，读总指向完整旧文件）——结构级改造，建议单独一轮设计；
2. **压缩尾巴**：cap 触发时整块全量压缩，单次占住磁盘线程上百 ms → P999 大尾巴。
   空闲窗口压缩在满负载下收益小（本负载无空闲）；根治仍依赖调度/并发改造；
3. **写放大**：每次淘汰的新版本整条追加、压缩全量重写——大记录高 churn 场景下
   盘写字节 ≈ 数倍于活跃数据，属追加式日志 + 全量压缩的结构成本。

## 13. 追加（后续实现，独立成节）

### 13.1 测试比例修正：缓存:数据集:磁盘 ≈ 1:3:5
- 依据 Redis Enterprise Auto Tiering（RAM 热层≥20% 总值、闪存≥总数据+写放大余量；适用"工作集<<数据+热点"）与 80/20 热集定容；Pika 为反例。
- test3 重排：缓存 100M / 数据集 300M / 磁盘 500M；命中率 2x/3x(=200/300M) 作对照；
  写请求改用同量级尺寸（4K~1M，削掉 10M 顶档的版本放大）；注入改为缓慢增长（60 key）。
- 效果：混合 QPS 由 ~17k（失衡小数据集）升到 ~83k，命中率 ~96%，贴近业界预期。

### 13.2 空洞/删除段（步骤 1~4 已实现；详见 `空洞删除段设计.md` §10）
- 协议 `CHECK_DELETED`(0xFF)：删除=空洞；
- 覆盖缩小 + 空洞 best-fit 复用 + 旧版本取代时显式变洞；
- 场景2结果（read70/write30，1:3:5，30s）：
  - QPS 83k → 124k；追加字节 ~15.3GB → ~6.0GB（−61%）；
  - compact 41 次/4.0s → **16 次/1.5s（~5% duty）**；P999 13.9ms → 7.1ms；
  - overwrite 30.6k + hole-use 26.8k；场景末 holes 快照仅 20 段/4MB。
- 遗留：冷启动 loader（管理层阶段）、（可选）软水位压缩。

### 13.3 当前瓶颈（按数据）
场景2磁盘线程 ~98% 忙碌，构成已转为：**读 ~20s/30s**（92,944 × ~215µs）为主；
写/压缩已降到零头。下一步候选：读并行 v2（每线程缓存句柄，避免 per-read open 回归）。
