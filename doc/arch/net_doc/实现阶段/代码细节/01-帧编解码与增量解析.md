# 帧编解码与增量解析

本篇记录帧解析里的几个手法：怎么保证粘包不会撑爆内存、怎么做不会溢出的长度比较、遗留接口怎么给自己设上限。

## 1. 只缓存“拼完这一帧所需要的字节”

### 要解决什么问题

TCP 是字节流，一次可读事件读到的可能是半帧、一帧、也可能是十几帧粘在一起。解析器必须把“还没拼完的那部分”存下来。

最直接的做法是把读到的整块数据都追加进内部缓冲，再从里面切帧。问题在于：如果一次读到 1MB、里面有 10 帧，那么这 1MB 全都会被复制进内部缓冲，即使其中 9 帧马上就被消费掉了。粘包越严重，这份多余拷贝越大。

### 代码

```cpp
    // Append only bytes needed to finish this frame so a large coalesced read does
    // not become an unbounded retained buffer.
    while (inputBuffer.size() < FIXED_HEADER_SIZE && offset < data.size()) {
        const std::size_t needed = FIXED_HEADER_SIZE - inputBuffer.size();
        const std::size_t available = data.size() - offset;
        const std::size_t count = std::min(needed, available);
        inputBuffer.insert(inputBuffer.end(), data.begin() + static_cast<std::ptrdiff_t>(offset),
                           data.begin() + static_cast<std::ptrdiff_t>(offset + count));
        offset += count;
    }
```

### 为什么这么写

内部缓冲**只负责拼当前这一帧**：先凑够固定头，读出内容长度，再按“还差多少”补齐这一帧。至于这次读到的数据后面还跟着多少帧，解析器不管——它通过 `offset` 参数把消费位置告诉调用方，调用方在同一块数据上继续调用即可。

这样内部缓冲的峰值大小被限制在“一帧 + 固定头”这个量级，与一次读到多少数据无关。粘包越严重，省下的拷贝越多。

### 坑点

- **两个游标含义不同**：`inputBuffer` 是解析器自己攒的半帧，`offset` 是调用方数据块里的消费进度。混用会导致重复消费或丢字节。
- **`offset` 越界要当成非法输入**：调用方传进来的位置超出数据长度，说明调用方的记账和解析器不一致，此时清空缓冲并报非法帧，而不是继续往前走。
- **换块时 `offset` 归零**：新的一块数据到来时，消费位置从 0 重新开始，但 `inputBuffer` 里攒的半帧要保留。这两个生命周期是独立的。

## 2. 长度比较：先减后比，不要先加

### 要解决什么问题

判断“这一帧是否超过上限”，直觉写法是：

```cpp
if (headerLength + bodyLength > maxFrameBytes)   // 危险
```

`headerLength` 是线上读来的 2 字节值，`bodyLength` 是 4 字节值。两者相加在 `size_t` 上不会溢出（32 位量级远小于 64 位），但在 32 位平台或字段变宽之后就可能绕回，绕回之后一个超大帧会被判成合法。

### 代码

```cpp
    if (maxFrameBytes < headerLength || bodyLength > maxFrameBytes - headerLength) {
        reset();
        return DecodeStatus::FRAME_TOO_LARGE;
    }
```

### 为什么这么写

把加法改成减法，先确认 `maxFrameBytes >= headerLength`，再用 `maxFrameBytes - headerLength` 作为 `bodyLength` 的上界。减法在“被减数不小于减数”的前提下不可能下溢，因此整个比较恒为安全。

同样的手法用在字段总长的累加上：

```cpp
        if (field.value.size() > std::numeric_limits<std::size_t>::max() - TLV_HEADER_SIZE ||
            bodySize > std::numeric_limits<std::size_t>::max() - TLV_HEADER_SIZE - field.value.size()) {
            return false;
        }
        bodySize += TLV_HEADER_SIZE + field.value.size();
```

### 坑点

- 累加型溢出检查必须在**累加之前**做，累加之后检查已经晚了。
- 两个减法的顺序不能交换：先确认 `value.size() <= max - 8`，才能安全地算 `max - 8 - value.size()`。
- 上线的是**未信任数据**。所有来自线上的长度字段都要按“可能是任意 32 位值”来对待，不能假设它合理。

## 3. 编码时自己算长度，不信调用方

编码入口在写出字节前会重新校验一遍头部和所有字段，并且**由编码器自己累加内容长度**，而不是采用结构体里填好的那个值：

```cpp
    std::size_t bodySize = 0;
    if (!validateFields(frame.fields, bodySize) || bodySize > std::numeric_limits<std::uint32_t>::max() ||
        maxFrameBytes < frame.header.headerLength || bodySize > maxFrameBytes - frame.header.headerLength) {
        return {};
    }
```

### 为什么这么写

内容长度是一个可以从字段列表推导出来的值。如果编码时直接采用调用方填的值，一旦两者不一致，就会产出一条“自称长度与实际长度不符”的帧。这种帧在接收端会被判为坏帧，而发送端却以为自己发的是对的——排查方向会被彻底带偏。

由编码器自己算，这个不一致就不可能产生。头部字段和字段内容同样会重新校验，任何一个不合法就返回空结果表示拒绝编码，绝不产出一条半合法的帧。

### 坑点

- 返回空缓冲区表示“拒绝输出”，调用方必须检查。把空结果当成“零字节的合法帧”发出去，会让对端收到一段无法解析的字节流。
- 校验时用的是**同一个上限**（单帧上限），保证编码和解码对“多大的帧算合法”理解一致。两边不一致会造成“发得出去、收不进来”。

## 4. 遗留接口的内存上限

解析器提供两个入口：一个带消费位置参数，一个不带。不带位置参数的那个是为早期调用方保留的兼容接口，它必须把“这一帧之后剩下的字节”留在内部缓冲里，供后续调用继续切帧。

```cpp
    // Legacy one-frame API buffers coalesced suffixes for later empty-feed calls.
    const std::size_t legacyLimit = maxFrameBytes <= std::numeric_limits<std::size_t>::max() / 2
        ? static_cast<std::size_t>(maxFrameBytes) * 2
        : std::numeric_limits<std::size_t>::max();
    const std::size_t suffixSize = data.size() - offset;
    if (suffixSize > legacyLimit || inputBuffer.size() > legacyLimit - suffixSize) {
        reset();
        return DecodeStatus::FRAME_TOO_LARGE;
    }
```

### 为什么这么写

这个接口会把粘包的尾部留在缓冲里，而调用方每次喂进来的数据块大小不受解析器控制。如果不设限，一个持续喂大块数据的调用方可以让内部缓冲无限增长。

上限取“单帧上限的两倍”：一帧的上限是已知的，留一帧的余量给“刚解析完一帧、后面又粘了几乎一整帧”的情况，再多就说明调用方用错了接口。

### 坑点

- **新代码应当使用带位置参数的接口**。遗留接口的额外拷贝和内存上限都是为了兼容；带位置参数的版本不需要在内部保留粘包后缀，内存表现更好。
- 上限计算里的两个判断都不能省：`suffixSize > legacyLimit` 防止本次就超，`inputBuffer.size() > legacyLimit - suffixSize` 防止本次加上已有内容后超。第二个判断用减法写成，也是为了避免溢出。
- 超限时返回“帧过大”而不是“非法帧”，因为字节流本身格式可能是对的，是使用方式超出了接口设计容量。

## 5. 整体逻辑

把上面几点串起来，一次 `feed` 的顺序是：

1. 校验消费位置是否越界；越界则清空缓冲并报非法帧；
2. 补齐固定头（只补需要的字节）；
3. 校验魔数、版本、头长度、保留位；
4. 用防溢出的比较判断帧大小是否超限；
5. 按内容长度补齐整帧；
6. 解析字段并逐个校验类型与长度；
7. 从缓冲头部移除这一帧，返回“帧完整”。

任何一步失败都会**清空内部缓冲**。原因是字节流里一旦出现无法解析的内容，解析器无法确定下一个帧头在哪里，继续保留只会让后续解析全部错位，产生一连串虚假错误。清空并报错，由上层决定关闭连接。

编码方向的顺序是：校验头部 → 校验字段 → 自己累加长度 → 检查上限 → 写字节。任何一步失败返回空结果。
