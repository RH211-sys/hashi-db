# 连接槽位的一次性释放

本篇记录客户端名额（连接槽位）的预留与释放：为什么用循环比较交换、为什么释放动作必须做成幂等、以及怎么把不可拷贝的资源塞进可拷贝的任务里。

## 1. 要解决什么问题

服务限制同时存在的客户端数量。这个限制必须**在连接建立后立刻生效**，而不是“先接受再检查”——后者在连接洪峰时会先创建一堆连接再全部拒绝，白白消耗资源。

所以流程是“先占位，成功才继续”：

1. 尝试把当前计数加一；
2. 加一之后仍然不超过上限，才算占位成功；
3. 占位失败就关掉这个连接。

## 2. 占位：为什么不能“先读后加”

直觉写法是“读当前值，判断小于上限，然后加一”。这在多线程下是错的——接入线程和事件循环线程都可能释放名额，两个线程也可能同时占位，读到的值和加一时看到的值可能不同。

```cpp
                std::size_t clients = activeClients->load(std::memory_order_relaxed);
                bool reserved = false;
                while (clients < maxClients) {
                    if (activeClients->compare_exchange_weak(clients, clients + 1,
                            std::memory_order_acq_rel, std::memory_order_relaxed)) {
                        reserved = true;
                        break;
                    }
                }
                if (!reserved) {
                    close(client);
                    continue;
                }
```

循环比较交换的要点：

- `compare_exchange_weak` 把“读、判断、写”合成一个不可分割的操作，失败时会把读到的**最新值**写回 `clients`，所以循环下一轮用的是新值，不需要手动重读；
- 用 `weak` 而非 `strong` 版本，是因为它本来就写在循环里——`weak` 允许伪失败，在循环中重试的代价远小于在非循环场景下必须用 `strong` 的约束；
- 比较失败时会重新读值，因此循环条件 `clients < maxClients` 始终基于最新状态判断，不会出现“两个线程都以为还有空位”。

## 3. 释放：为什么必须幂等

一个连接名额可能从多条路径被释放：

- 连接正常关闭；
- 协议错误导致关闭；
- 传输失败导致关闭；
- 服务停止时统一关闭；
- **接入任务因为事件循环队列满而被丢弃**——这条最容易被忽略：连接对象根本没被创建出来，但名额已经占了；
- 连接对象析构（析构里也会走一次关闭）。

如果在这些路径上各自减一，计数会被多减，最终变成负数或者提前放行超额连接。所以释放动作被包装成一个“只能成功一次”的回调：

```cpp
                const auto releaseSlot = [counter = activeClients, released]() {
                    if (!released->exchange(true, std::memory_order_acq_rel)) {
                        counter->fetch_sub(1, std::memory_order_acq_rel);
                    }
                };
```

`exchange` 返回**交换前的值**：第一次调用拿到 `false`，于是执行减一；后续调用拿到 `true`，直接跳过。无论被调用多少次，实际效果只有一次。

## 4. 释放回调被多方持有：靠析构兜底

释放回调会被两处持有：

- 接入任务（如果任务被丢弃，需要释放）；
- 连接对象（连接关闭时释放）。

只有一方会真正触发，而且我方**无法预知**是哪一方。让回调随最后一个持有者析构而触发，是一个干净的兜底：

```cpp
struct SlotRelease {
    std::atomic<bool> released{false};
    ClientSlotRelease callback;

    explicit SlotRelease(ClientSlotRelease callback) : callback(std::move(callback)) {}

    void run() {
        if (!released.exchange(true, std::memory_order_acq_rel) && callback) {
            callback();
        }
    }

    ~SlotRelease() {
        run();
    }
};
```

要点：

- 析构里调用 `run()`，因此“忘记调用”不会导致名额泄漏——对象销毁就是最后的保险；
- `run()` 本身幂等，所以“显式调用过之后又被析构”也不会重复减一；
- 这个封装自身套了一层原子标记，覆盖了“超出回调内部一次性保证”的情况（回调是外部传入的，不能假设它自己幂等）。

## 5. 坑点：不可拷贝的资源塞不进任务

任务类型是 `std::function<void()>`。标准要求 `std::function` 的目标对象**必须可拷贝构造**，因此一个“移动捕获了 `unique_ptr` 的 lambda”是放不进去的——这类 lambda 只有移动构造。

但连接接入任务确实需要带着两个不可拷贝的资源：传输对象和释放回调。解决办法是把它们**各自包一层共享指针**，lambda 捕获共享指针（可拷贝），实际资源仍在共享指针内部：

```cpp
    auto releaseHolder = std::make_shared<SlotRelease>(std::move(releaseSlot));
    auto transportHolder = std::make_shared<std::unique_ptr<Transport>>(std::move(transport));
```

好处有三点：

1. lambda 变成可拷贝，可以放进 `std::function`；
2. 任务被丢弃时，共享指针的引用计数归零，传输对象析构（关闭套接字）、释放回调析构（归还名额），两件事都自动完成；
3. 连接创建时把同一个共享指针也给连接一份，于是无论哪一方先结束，释放动作都只发生一次——由第 3 节的原子标记保证。

如果入队本身就失败了（队列满、已停止），任务从未被创建，此时在函数结尾显式触发一次释放：

```cpp
    if (!queued) {
        releaseHolder->run();
    }
```

## 6. 连接侧拿到的释放动作

连接不直接持有共享指针，而是拿到一个可调用的包装：

```cpp
        auto connection = std::make_unique<Connection>(connectionId, state->id, std::move(*transportHolder),
            maxPipelineRequests, std::move(peer), maxFrameBytes, generation,
            [releaseHolder]() { releaseHolder->run(); }, std::move(completionPoster));
```

这样连接只知道“关闭时调用这个动作”，不知道名额是怎么记账的。职责划分清楚：容量记账属于接入侧，连接只负责在关闭时通知一声。

## 7. 整体逻辑

1. 接入线程接受连接，循环比较交换预留名额；
2. 预留成功后构造释放回调，用共享指针包住传输对象和释放回调；
3. 把接入任务投给事件循环；投递失败立刻释放名额；
4. 事件循环执行任务：创建连接（连接也持有释放回调的共享指针）、注册关注事件、放入连接表；
5. 连接创建失败或注册失败：连接自身关闭并释放名额，任务结束；
6. 连接在之后的任意时刻关闭：释放名额，之后连接对象析构不会再重复释放。

第 5 步里“连接创建失败时也调用一次释放”是必要的：此时传输对象已被连接接管，任务这边的共享指针不再拥有它，如果只依赖任务析构兜底，名额会在任务结束时才释放——虽然最终也会释放，但连接构造失败本应立即回收名额。当前实现让连接在构造失败路径上主动释放，语义更直接。

## 8. 一句话总结

**名额的占位必须是一次原子判断，名额的释放必须幂等，不可拷贝的资源通过共享指针进入可拷贝的任务。** 三条合起来，才能在“任务可能被丢弃、连接可能构造失败、关闭路径有多条”的情况下保证计数不漂移。
