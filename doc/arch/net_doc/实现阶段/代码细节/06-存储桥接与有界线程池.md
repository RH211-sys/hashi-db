# 存储桥接与有界线程池

本篇记录当前挂在网络层下面的执行实现：为什么必须用独立线程池、回调为什么要共享持有、队列满时为什么立即返回。

先明确定位：**存储桥接是阶段测试适配器**，它的注释里写了“不代表最终的存储对接方式”。本篇记录的是它作为一个“需要等待异步结果的执行方”的通用做法，这部分做法在正式执行层里同样适用。

## 1. 要解决什么问题

执行方拿到的请求可能是存储操作，而存储接口返回的是 future——要拿到结果必须等待。等待是阻塞的。

如果这个等待发生在事件循环线程上，就会出现：一条连接的存储操作要 20 毫秒，这 20 毫秒里同一条事件循环上的**所有其他连接**都无法处理任何事件。连接数越多，问题越严重。

所以要解决的是：**把阻塞的等待挪到不承担 I/O 职责的线程上。**

## 2. 线程池的所有权

线程池是执行器对象的成员，由执行器独占持有：

```cpp
class StorageControllerExecutor::WorkerPool {
    // ...
    std::mutex mutex;
    std::condition_variable condition;
    std::deque<std::function<void()>> tasks;
    std::vector<std::thread> workers;
    bool stopping = false;
};
```

```cpp
StorageControllerExecutor::StorageControllerExecutor(::Controller& storageController)
    : storageController(storageController), workerPool(std::make_unique<WorkerPool>()) {}
```

关键点是**不能写成函数内的静态局部对象**。静态局部对象的问题：

- **生命周期不受控**：第一次调用时构造、进程退出时析构，与“服务已经停止、存储引用已经失效”这件事完全脱钩。服务重启后，线程池里可能还留着上一次的线程。
- **跨实例共享**：多个执行器实例会共用同一个线程池，任何一个实例销毁都不会让线程池停止。
- **析构时机不可预测**：静态对象在进程退出阶段析构，此时其他静态对象可能已经被销毁，线程池里的任务访问这些对象就是访问已释放内存。

作为成员持有之后，执行器销毁 → 线程池销毁 → 线程停止，顺序是确定的。

## 3. 线程池的结束行为

线程池析构时先标记停止、唤醒所有线程，再逐个等待：

```cpp
    ~WorkerPool() {
        {
            std::lock_guard<std::mutex> lock(mutex);
            stopping = true;
        }
        condition.notify_all();
        for (auto& worker : workers) {
            worker.join();
        }
    }
```

配合工作线程的循环条件，实际效果是“**先把队列里已有的任务做完，再退出**”：工作线程只有在队列为空**且**已标记停止时才返回。所以析构是一个可能耗时的操作——它会等到所有已提交的存储任务完成。

需要注意的推论：**不要在事件循环线程上销毁执行器**。否则析构会阻塞事件循环线程，直到所有存储任务完成，正好违反了本篇要解决的问题。当前实现里执行器由服务控制器持有，销毁发生在服务停止之后（此时事件循环线程已经退出），所以不会命中这个陷阱。这是依赖调用顺序成立的性质，不是代码强制的，改动装配顺序时要注意。

## 4. 队列满时立即返回

```cpp
    bool submit(std::function<void()> task) {
        {
            std::lock_guard<std::mutex> lock(mutex);
            if (stopping || tasks.size() >= MAX_PENDING_TASKS) {
                return false;
            }
            tasks.push_back(std::move(task));
        }
        condition.notify_one();
        return true;
    }
```

队列上限是固定的。达到上限时返回失败，**不等待、不阻塞**。

为什么不能改成“等待队列有空位再提交”：等待发生在调用方线程上，而调用方是事件循环线程。一旦在这里等待，事件循环线程依然被阻塞——只是从“等存储结果”变成了“等队列空位”，问题一点没解决，还额外增加了锁竞争。

返回失败让调用方立刻回一条“忙”给客户端，客户端可以重试。这是**快速失败**：明确告诉对方现在处理不了，比让它挂在那里等更诚实。

## 5. 坑点：回调必须两边都能拿到

完成回调既要在任务真正执行时调用，也要在提交失败时立刻调用。如果按直觉写成“把回调移动进任务”，提交失败的那条路径就再也拿不到回调了——它已经被移走了。

解决办法是让两边共享同一个回调：

```cpp
    auto completionHolder = std::make_shared<CommandCompletion>(std::move(completion));
    const bool accepted = workerPool->submit([this, request = std::move(request), key = std::move(key),
                                              completionHolder]() mutable {
        // ... 执行完成
        (*completionHolder)(std::move(response));
    });

    if (!accepted) {
        (*completionHolder)(statusResponse(pendingRequest, ErrorCode::BUSY, "storage executor queue is full"));
    }
```

这样“恰好调用一次”是由结构保证的，而不是靠一个额外的标志位去防重：

- 提交成功 → 任务被排队，最终一定被执行一次，回调在里面调用一次；
- 提交失败 → 任务从未入队，外层立刻调用一次。

两条路径互斥，所以不需要额外的“是否已回调”判断。

另一个细节：提交失败时要回一条“忙”，需要用到请求里的连接标识和请求标识来构造响应。但请求已经被移动进任务了，所以在外层留了一份副本用于构造这条失败响应。

## 6. 坑点：在队列上等待 future 时不要持锁

工作线程从队列取出任务后**先释放锁再执行**：

```cpp
                    {
                        std::unique_lock<std::mutex> lock(mutex);
                        condition.wait(lock, [this] { return stopping || !tasks.empty(); });
                        // ... 取出任务
                    }
                    try {
                        task();
                    } catch (...) {
                    }
```

任务内部会阻塞等待 future（可能几十毫秒），如果持锁执行，整个队列的进出都会被卡住——包括其他工作线程取任务和调用方提交任务。取出任务再释放锁，锁的持有时长就只覆盖“从队列拿一个元素”这个极短的操作。

任务外层的异常捕获也是必要的：任务抛出的异常会让工作线程直接结束。工作线程数量固定，少一个就永久少一份处理能力，而进程不会有任何提示。捕获之后线程继续取下一个任务，执行器的其他部分不受影响。

（这里的捕获只保证“工作线程不死”。真正的错误处理发生在外层：执行器在任务里对存储操作做了异常捕获并转成错误响应。两层捕获的分工不同。）

## 7. 错误码映射

存储层的返回码不直接暴露给客户端，而是映射成网络层自己的错误码：

```cpp
ErrorCode mapStorageCode(int code) {
    if (code == SUCCESS) {
        return ErrorCode::OK;
    }
    if (code == FIND_FAILED || code == EXPIRED) {
        return ErrorCode::STORAGE_UNAVAILABLE;
    }
    if (code == TYPE_VALID) {
        return ErrorCode::TYPE_NOT_REGISTERED;
    }
    return ErrorCode::INTERNAL;
}
```

理由：存储错误码属于内部实现。一旦它出现在协议里，就成了对外契约，将来调整存储层错误码就会破坏客户端兼容性。网络层维护一套自己的稳定错误码，两边各自独立演进，中间由这个映射函数承担翻译。

“找不到”和“已过期”合并成同一个对外结果，也是同样的考虑：客户端对这两种情况的处理是一样的（都是没拿到数据），没有必要在协议里区分。

## 8. 哪些命令不经过线程池

有三类命令**不走**线程池，在事件循环线程上就地完成：

- **探活**：不需要任何后端，直接回成功；
- **退出**：直接回成功，并标记“写完就关连接”；
- **查询、新增、修改**：还没有确定的线上数据编码，直接回“类型未注册”。

这三类都不涉及等待，所以就地处理没有任何问题。反过来说，**任何需要等待外部结果的命令都必须走线程池**，这条边界要一直守住。

## 9. 整体逻辑

一次需要存储的命令的完整路径：

1. 事件循环线程调用执行器；
2. 执行器就地判断命令类型：不需要后端的就地回结果；需要后端的构造任务并提交；
3. 提交成功 → 工作线程取出任务，调用存储接口并等待结果；提交失败 → 立刻回“忙”；
4. 工作线程把存储返回码映射成网络层错误码，组装响应；
5. 通过完成回调把响应交回——回调最终会把它投回连接所属的事件循环。

第 5 步之后的事情见 [02-跨线程完成回投与代际校验](./02-跨线程完成回投与代际校验.md)。整条链路上，事件循环线程从未等待过任何存储操作。
