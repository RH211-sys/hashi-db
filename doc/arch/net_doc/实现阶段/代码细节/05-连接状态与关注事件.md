# 连接状态与关注事件

本篇记录“这条连接当前该关心哪些 I/O 事件”这个问题是怎么算出来的，以及为什么可以安全地返回“什么都不关心”。

## 1. 要解决什么问题

事件通知机制支持为每条连接注册一组关注事件。注册多了会收到无意义的通知（浪费一轮处理），注册少了会漏掉该处理的事情（数据积压在缓冲里没人读）。

而且连接的关注需求是**动态**的：刚建立时要读；待执行队列满了要停读；有响应要发时要关注可写；进入关闭流程后又只剩“等对端断开”。

## 2. 计算规则

```cpp
    std::uint32_t events = 0;
    if (!readPaused && !draining && !peerClosed && state != ConnectionState::CLOSING &&
        pipeline.size() + (activeRequest ? 1U : 0U) < maxPipelineRequests) {
        events |= POLL_READ;
    }
    if (!outputQueue.empty() || (transport->events() & WANT_WRITE) != 0) {
        events |= POLL_WRITE;
    }
    return events;
```

关注可读需要同时满足四个条件：

| 条件 | 排除的情况 |
|---|---|
| 未暂停读取 | 输入缓冲已达上限，或待执行队列已满 |
| 未进入排空 | 停止服务时只把已有请求做完，不再读新请求 |
| 对端未关闭 | 对端已经发了结束，读到的是结束标记而不是数据 |
| 不处于关闭中 | 已经决定关闭，再读也没有意义 |

关注可写只需一个条件：有积压的输出，或者传输层自身要求可写（加密握手类传输在握手阶段需要）。

**每次事件处理结束后都会重新计算并提交**，而不是把关注集合当成一份需要手工维护的状态。这样就不会出现“某个分支忘了关掉可读/打开可写”的遗漏——只要连接内部状态是对的，关注集合就一定是对的。

## 3. 返回“什么都不关心”是合法的

当上面两个条件都不满足时（典型场景：待执行队列已满，正在等在途请求的结果），函数返回 0，也就是不关注任何读写事件。

这看起来像是“放弃了这条连接”——不再收数据、也不发数据，如果对端此时断开，谁来发现？

答案是底层轮询器**始终额外订阅对端关闭通知**：

```cpp
    event.events = toNativeEvents(events) | EPOLLRDHUP;
```

即使上层要求的事件集合是空的，这一位仍然会加上。所以连接在“什么都不关心”的状态下依然能感知对端断开，不会变成一条永远不被回收的僵尸连接。

## 4. 坑点：不要用“兜底关注可读”来掩盖空集合

一个看起来合理的做法是：当算出的事件集合为空时，强行加上“关注可读”，理由是“反正可读事件无害，多收一次而已”。

这个做法的害处是会**掩盖真实状态**：

- 连接明明处于“队列满、等结果”的状态，却仍然会对每次可读事件做出反应；
- 可读事件到来后连接会尝试读取，而读取路径第一件事就是检查“是否应该读”，发现不该读就立刻返回——白跑一轮；
- 更糟的是，这个兜底会让“关注集合为空”这个有诊断价值的状态消失，排查“连接卡住不动”时看不到任何线索。

正确做法是让空集合如实表达“当前不需要读写”，而由底层补上必要的兜底通知（对端关闭）。**兜底应该发生在最靠近系统调用的那一层，而不是在上层伪造状态。**

## 5. 坑点：读预算与事件触发模式必须匹配

读取有预算（一次事件最多读 64KB），不会一直读到无数据可读。这种做法只在**水平触发**模式下安全：

- 水平触发：只要还有数据没读完，下一次等待会再次报告可读，所以没读完的部分不会丢；
- 边沿触发：只在状态变化时报告一次，没读完的部分必须自己读到无数据可读为止，否则永远收不到通知。

当前实现选择水平触发，正是为了让“按预算读”这种写法成立——否则一次事件必须读干净才能正确，而“读干净”在恶意客户端持续发送的情况下会演变成一轮事件处理不设上限。

这个匹配关系是隐含的约束：**如果将来改成边沿触发，读取逻辑必须同步改成“读到无数据可读”，否则会丢数据。**

## 6. 坑点：写入进度必须记录

发送可能只发出去一部分。已发送的位置必须记录下来，下一次从断点继续：

- 输出缓冲里存的是完整帧，逐帧记录“已经发出多少字节”；
- 发送前按剩余字节构造待发片段，发送后累加已发字节；
- 一帧发完就从队列里移除，并丢弃对应的进度记录；
- 积压字节数同步扣减。

不记录进度而是“发失败就整帧重发”，会让对端收到重复字节，破坏协议——帧头会被解析成错误的内容，对端只能判定为坏帧并断开。

另一个细节：发出去多少就扣多少积压字节，而不是“整帧发完才扣”。输出积压的上限是按字节算的，如果只在整帧完成时扣减，一条大响应的积压量会被重复计算。

## 7. 整体逻辑

一次可读事件的完整处理顺序：

1. **先解析已有缓冲**：即使这次没读到新字节，之前留下的半帧也可能已经能拼完；
2. 检查是否应停止：连接正在关闭、输入达上限、队列已满、已排空、对端已关闭——任一命中就返回；
3. 按预算循环读取：读到的字节立刻交给解析，边读边解析；
4. 每次读完后再次检查停止条件（可能因为解析出请求而队列变满）；
5. 遇到对端结束：标记对端关闭、停止读取、进入“写完剩余响应再关闭”的状态；
6. 遇到传输失败：直接关闭。

一次可写事件的顺序：按预算发送 → 发送完检查是否需要“写完就关” → 如果不需要关且不在排空，恢复解析并继续调度队列里的请求。

两者共同的一点是：**处理结束后统一重算关注事件**，而不是在各个分支里分头调整。

## 8. 一句话总结

关注集合是连接内部状态的**纯函数**，每次重新算、绝不手工维护；空集合是合法且有意义的表达，兜底通知交给最底层；读取用预算的前提是水平触发，这两者必须成对出现。
