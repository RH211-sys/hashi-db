# 跨线程完成回投与代际校验

本篇记录业务结果如何安全地回到连接：为什么用弱引用、为什么只看连接标识不够、以及执行任务时为什么必须先解锁。

## 1. 要解决什么问题

业务执行在别的工作线程上完成，它手上的结果必须回到连接所属的事件循环才能写入连接。但它不能直接调用连接——连接的所有状态由事件循环线程独占，跨线程访问就是数据竞争。

所以只能“投递任务”：把“处理这个结果”包装成一个任务，放进该事件循环的任务队列，由事件循环线程取出来执行。

## 2. 代码

投递器在连接接入时创建，随连接一起存活：

```cpp
        ConnectionCompletionPoster completionPoster =
            [weakState = std::weak_ptr<Impl>(state), connectionId, generation](CommandResponse response) {
                const auto owner = weakState.lock();
                if (!owner) {
                    return;
                }
                owner->enqueue([weakState, connectionId, generation, response = std::move(response)]() mutable {
                    const auto reactor = weakState.lock();
                    if (!reactor) {
                        return;
                    }
                    const auto found = reactor->connections.find(connectionId);
                    if (found == reactor->connections.end() || found->second->generation != generation) {
                        // 连接已关闭或标识已被复用：丢弃过期完成结果。
                        return;
                    }
                    found->second->complete(std::move(response));
                    reactor->refreshInterest(connectionId);
                }, InboxKind::COMPLETION, connectionId);
            };
```

## 3. 为什么用弱引用而不是共享引用

事件循环对象由它的所有者（事件循环组）持有。如果完成结果里存的是**共享引用**，那么只要还有一条结果在路上，事件循环对象就无法销毁：

- 服务停止时，事件循环线程结束后对象本该析构；
- 但只要工作线程里还攥着一个共享引用，对象就活着，它包含的队列、套接字集合、互斥量全都不能释放；
- 表现是“线程退了但内存不回收”，在反复启停的场景里会持续累积。

用**弱引用**则相反：取不到就说明事件循环已经结束，直接放弃这条结果。这里放弃是安全的——事件循环已经不存在，连接自然也已经被关闭，这条结果本来也没有意义了。

## 4. 为什么只看连接标识不够

连接标识是进程内递增分配的，看起来唯一。但结果投回是**异步**的：从提交请求到结果回来之间，连接可能已经关闭，而关闭之后：

- 这个标识不会再被使用（当前实现里标识单调递增，不复用）；
- 但**将来若引入标识复用**（比如为了压缩编号空间），就会出现“结果属于旧连接，却匹配到了新连接”的情况；
- 届时结果会被写进一条完全无关的连接，客户端收到不属于自己的响应。

代际编号解决这个问题：每接入一条新连接就分配一个递增的代际，和连接标识一起记录。判断时必须**两个都对上**：

```cpp
                    if (found == reactor->connections.end() || found->second->generation != generation) {
```

代价很小（一个递增计数器），但把“结果串到别的连接上”这类最难排查的错误从根上排除了。

## 5. 坑点一：执行任务时必须先解锁

这是本篇最需要注意的一点。

任务队列受一把互斥量保护。如果**持锁执行任务**，就会出现下面这条死锁链：

1. 事件循环取出一个“接入新连接”的任务并持锁执行；
2. 该任务里创建连接、注册关注事件；
3. 如果这个过程中触发了任何一次入队（例如连接构造失败需要投递关闭任务），入队会再次尝试获取同一把锁；
4. 这把锁不是递归锁，于是死锁。

更常见的触发路径是完成结果：执行一个完成任务时，如果连接立刻被判定需要关闭并投递关闭任务，同样会二次加锁。

所以取任务和执行任务必须分成两段：

```cpp
    void drainInbox() {
        std::deque<ReactorTask> tasks;
        {
            std::lock_guard<std::mutex> lock(inboxMutex);
            tasks.swap(controlInbox);
            // ... 把其余队列里的任务也搬进 tasks
        }
        for (auto& task : tasks) {
            try {
                task();
            } catch (...) {
                // 单个任务失败不得中断事件循环。
            }
        }
    }
```

先用锁把当前所有待执行任务**搬到一个局部容器**，释放锁，再执行。这样任务内部无论怎么入队都不会死锁。

同一条规则适用于所有内部方法：任何内部方法只要会入队，就绝不能在持有这把锁的状态下被调用。

## 6. 坑点二：完成结果队列满时不能只是丢弃

完成结果队列有上限。队列满时如果仅仅“丢弃这条结果”，会留下一个半死状态：

- 连接把某条请求标记为在途，然后等待结果；
- 结果被丢了，永远不会回来；
- 连接既不会继续处理队列里的下一条，也不会自己关闭；
- 它一直占着客户端名额，直到服务停止。

所以队列满时的正确处理是**放弃这条响应并关闭对应连接**：

```cpp
                if (completionInbox.size() < MAX_COMPLETION_TASKS) {
                    completionInbox.push_back(std::move(task));
                    accepted = true;
                    needWakeup = true;
                } else if (connectionId != 0) {
                    overflowConnections.insert(connectionId);
                    needWakeup = true;
                }
```

被标记的连接由事件循环在下一轮开头统一关闭。这里记录标识而不是“记录一个指向连接的指针”，同样是因为入队可能发生在工作线程上，不能碰连接对象。

用一次明确的断连换掉一个不会推进的半死状态，是这里唯一自洽的选择。

## 7. 坑点三：任务可能是在“已停止”之后被投递的

停止过程中还会有结果回来，所以判断入队是否允许时，条件要看两件事：

```cpp
            if (kind == InboxKind::COMPLETION) {
                if (stoppingNow && !drain.load(std::memory_order_acquire)) {
                    return false;
                }
```

- **立即停止**：停止之后一律不再接受完成结果；此时连接马上就要被强制关闭，接受结果没有意义。
- **优雅排空**：停止之后**仍然接受**完成结果。那些请求是在停止之前提交出去的，排空的目的就是等它们回来；此时拒绝会导致排空永远等不到结束。

“停止”停止的是新请求，不是已有请求的结果。这条区分必须在入队判断里体现出来，否则排空要么永远不结束，要么提前丢弃本应发回的响应。

## 8. 整体逻辑

一次完成的完整路径：

1. 工作线程拿到结果，调用投递器；
2. 投递器尝试锁定事件循环的弱引用；取不到说明循环已结束，直接放弃；
3. 打包一个任务并**带连接标识和代际**入队；
4. 入队成功则唤醒事件循环；队列满则记录待关闭连接并唤醒；
5. 事件循环在循环开头取出任务（已释放锁）并执行；
6. 执行时再次确认连接存在且代际一致；不一致就丢弃；
7. 一致则把结果交给连接处理，随后刷新该连接的关注事件；
8. 刷新时若发现连接已关闭或刷新失败，关闭并回收这条连接。

第 6 步的二次校验不是多余的：第 2 步到第 6 步之间，连接完全可能已经被关闭。
