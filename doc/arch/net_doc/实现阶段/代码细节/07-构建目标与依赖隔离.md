# 构建目标与依赖隔离

本篇记录网络层的构建目标怎么划分，以及为什么必须这么分。

## 1. 问题是怎么暴露的

网络层曾经只有一个构建目标。首次在 Linux 上编译协议测试时出现了这样的失败：

```text
In file included from project/net_level/command/../../data_memo_level/controller/controller.h:5,
                 from project/net_level/command/command_executor.cpp:10:
    data_memo_level/data_type.h:5:10: fatal error: cereal/archives/binary.hpp: No such file or directory
```

原因是存储桥接文件被放进了这个目标。它包含存储层的头文件，而存储层头文件又包含第三方序列化库的头文件。这个目标没有第三方库的搜索路径，于是编译在包含阶段就失败了。

问题不在于“缺一个搜索路径”——补上路径也能编过。真正的问题是**依赖污染**：一个本该与存储无关的网络目标，被迫依赖存储层的头文件、进而依赖一个序列化库。

## 2. 解决方式：按依赖切分目标

```cmake
# 平台无关的协议与连接核心
add_library(mydb_net_core STATIC EXCLUDE_FROM_ALL
    protocol/frame_codec.cpp
    command/command_parser.cpp
    server/session.cpp
    server/connection.cpp
    reactor/reactor.cpp
)

# Linux 网络服务端装配，不含存储依赖
add_library(mydb_net_linux STATIC EXCLUDE_FROM_ALL
    transport/tcp_transport.cpp
    reactor/epoll_poller.cpp
    reactor/reactor_group.cpp
    server/acceptor.cpp
    server/network_server.cpp
)

# 阶段测试用存储桥接：这里才允许出现存储与第三方依赖
add_library(mydb_net_storage_bridge STATIC EXCLUDE_FROM_ALL
    command/command_executor.cpp
    controller/controller.cpp
)

target_include_directories(mydb_net_storage_bridge PRIVATE
    "${CMAKE_CURRENT_SOURCE_DIR}/../third_party_lib/cereal_lib/include"
)

# 聚合接口目标，供需要完整服务端的测试使用
add_library(mydb_net INTERFACE)
target_link_libraries(mydb_net INTERFACE mydb_net_linux mydb_net_storage_bridge)
```

划分依据只有一条：**按“依赖了什么”分，而不是按“代码放在哪个目录”分。** 桥接的代码确实在网络的目录下，但它依赖存储层，所以它必须和目标主体分开。

## 3. 坑点：包含路径要用 PRIVATE

```cmake
target_include_directories(mydb_net_storage_bridge PRIVATE
    "${CMAKE_CURRENT_SOURCE_DIR}/../third_party_lib/cereal_lib/include"
)
```

如果用 `PUBLIC`，这个路径会**传递给所有链接该目标的消费方**。结果是：引用网络层的测试虽然没有直接用序列化库，编译命令行里却会多出一条第三方库路径。

后果不只是“多一个参数”：

- 消费方被迫依赖一个它根本不需要的目录存在；
- 三方库升级或换位置时，改动的影响面扩大到所有下游；
- 依赖关系从此无法从编译命令行里看出来——分不清“我依赖它”和“别人依赖它，顺便传给了我”。

规则很简单：**只在编译本目标自身源文件时需要的东西，一律 PRIVATE。** 只有出现在自己对外头文件里的依赖，才有资格 PUBLIC。

## 4. 坑点：静态库按需取用这个性质决定了测试能不能链上

协议测试只用到帧编解码和命令解析两个模块，但链接的是聚合目标（包含 Linux 服务端和存储桥接）。链接阶段却不会报“存储层符号未定义”，原因是**静态库只把“被引用到的目标文件”取进最终可执行文件**：

- 测试引用了帧编解码和命令解析的符号 → 这两个目标文件被取进来；
- 桥接的目标文件里的符号没有任何人引用 → 不取进来；
- 因此桥接引用的存储层符号也不需要解析，链接成功。

这个性质不能反过来依赖：**只要有一个测试引用了服务端装配或对外控制器，桥接的目标文件就会被拉进来，届时存储层的编译产物必须在链接列表里**，否则会出现一堆未定义符号。这一点已经写进网络层 README 的限制条目里。

## 5. 为什么所有目标都标记为“不参与默认构建”

每个目标都带 `EXCLUDE_FROM_ALL`，网络测试目录也以同样方式加入。原因是根构建当前以存储测试为主，默认构建必须继续只产出存储测试。如果网络目标参与默认构建：

- 每次构建存储测试都要捎带编译整个网络层，编译时间无谓增加；
- 网络层一旦编译失败，存储测试也构建不出来，破坏“两边互不影响”的现状。

标记之后，网络目标只在被显式指定时构建，符合“独立网络测试”的定位。

## 6. 线程库的链接

事件循环、接入器、工作线程池都用到了标准线程库。在类 Unix 平台上 `std::thread` 需要显式链接线程库，所以三个静态目标都补上了：

```cmake
if(UNIX AND NOT APPLE)
    find_package(Threads REQUIRED)
    target_link_libraries(mydb_net_core PUBLIC Threads::Threads)
    target_link_libraries(mydb_net_linux PUBLIC Threads::Threads)
    target_link_libraries(mydb_net_storage_bridge PUBLIC Threads::Threads)
endif()
```

这里用 `PUBLIC` 是正确的：符号级依赖会传递到最终可执行文件，消费方在链接时也需要这个库。用 `PRIVATE` 会出现在“库编过了、可执行文件链不上”的奇怪失败。

## 7. 平台边界

`mydb_net_core` 与平台无关，`mydb_net_linux` 只在 Linux 上有实际实现：

- 平台专属的系统调用（事件通知、唤醒句柄）全部集中在少数几个文件里，并且用条件编译包住；
- 非目标平台上这些文件仍然可以编译通过，但所有操作返回失败；
- 目标是让“换平台”只影响 `mydb_net_linux` 这一层，协议、连接调度和上层装配不需要改动。

判断平台用的条件同时检查“是 Linux”和“不是 Windows”，而不是只检查其中一个。原因是：既不匹配 Linux 宏也不匹配 Windows 宏的环境（例如某些交叉编译配置）下，只检查一边可能让平台专属代码被错误编译进去。

## 8. 整体逻辑

依赖方向是单向的：

```text
mydb_net_core（协议、连接、事件循环核心，无外部依赖）
      ↑
mydb_net_linux（Linux 传输、接入、服务装配，只用系统库）
      ↑
mydb_net_storage_bridge（存储桥接，依赖存储层与第三方序列化库）
      ↑
mydb_net（聚合接口目标）
      ↑
网络测试
```

箭头方向表示“被依赖”。任何一层都不能反向依赖上层：桥接可以依赖网络核心，网络核心绝不能依赖桥接。这条规则保证纯协议测试可以完全脱离存储层构建和运行——这既是构建效率问题，也是模块边界的可验证性：如果哪天核心层不小心引用了桥接，依赖方向会立刻在构建上暴露出来。
