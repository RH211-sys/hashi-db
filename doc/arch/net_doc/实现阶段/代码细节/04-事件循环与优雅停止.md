# 事件循环与优雅停止

本篇记录事件循环主循环的结构，以及停止流程里几个必须处理的问题。

## 1. 主循环的形状

```cpp
    void run() {
        std::array<PollEventItem, POLL_EVENT_BATCH> events{};
        while (true) {
            drainInbox();
            applyPendingClosures();

            if (stopping.load(std::memory_order_acquire)) {
                if (!drain.load(std::memory_order_acquire)) {
                    break;
                }
                startDrain();
                if (connections.empty()) {
                    break;
                }
                if (std::chrono::steady_clock::now() >= drainDeadline) {
                    closeAllConnections();
                    break;
                }
            }

            const int count = poller->wait(events.data(), static_cast<int>(events.size()), POLL_WAIT_MS);
            if (count <= 0) {
                continue;
            }
            handleEvents(events.data(), count);
        }

        closeAllConnections();
        discardQueuedTasks();
        running.store(false, std::memory_order_release);
    }
```

每轮的固定顺序是：**先清任务、再判停止、最后等事件**。三个步骤的顺序都有原因，见下。

## 2. 为什么先清任务再判停止

停止标志可能是在“任务队列里已经躺着东西”的时候被设置的。如果一看到停止标志就跳出，队列里那些任务会被永远放弃，其中就包括连接接入任务——它们持有已经预留的客户端名额。

当前实现的选择是：把清理放在判断之前，让已经入队的任务先执行完，然后才决定是否退出。真正需要丢弃的（停止之后才排队进来的）由退出前的清理统一处理，而那条路径会正确归还名额。

## 3. 为什么等待必须有超时

事件循环在没有事件时会阻塞在等待上（当前是 100 毫秒超时）。理论上停止方会主动唤醒它，但超时仍然不能省：

- 唤醒信号可能因为各种原因没有被观察到（例如唤醒发生在“检查停止标志之后、进入等待之前”的窗口里）；
- 如果没有超时，这个窗口一旦命中，事件循环就会永久阻塞，停止调用方永远等不到线程退出，服务无法停止。

用 100 毫秒的超时，最坏情况下的停止延迟是 100 毫秒，这个代价换来了“停止一定会生效”的保证。

## 4. 等待之后不能假设“没有事件”

唤醒事件用的是保留的连接标识 0，它不对应任何真实连接。处理事件时遇到标识 0 直接跳过：

```cpp
            if (item.connectionId == 0) {
                // 唤醒事件：仅用于打断 poller 等待，入队任务已在本轮开始处理。
                continue;
            }
```

这里不需要在唤醒时“处理任务”——任务在本轮循环开头已经取走并执行了。唤醒的唯一作用是把阻塞的等待打断，让循环回到开头。

另一点：等待返回的数量可能是 0（超时）也可能是负数（被信号打断等情况）。两种情况都直接进入下一轮，不做错误处理。负数不当作致命错误，是为了避免一次可恢复的失败把整条事件循环打死。

## 5. 排空：进入一次，检查每轮

排空的三个判断按固定顺序：

```cpp
                startDrain();                                    // 第一次进入时初始化
                if (connections.empty()) {
                    break;                                       // 全部收工，正常退出
                }
                if (std::chrono::steady_clock::now() >= drainDeadline) {
                    closeAllConnections();                       // 超时，强制收尾
                    break;
                }
```

要点：

- **初始化只做一次**。`startDrain()` 自己用 `drainStarted` 标记保证幂等，因为它每轮都会被调用。它负责：停止接收入队、记录截止时间、给所有连接发排空通知。如果每轮都重新设置截止时间，截止时间会被无限推迟，排空永远不会超时。
- **先查空、再查超时**。所有连接都已经关闭时应当正常退出，而不是走“超时强制关闭”的分支。顺序颠倒在结果上差别不大，但会让日志和状态停在错误的分支上。
- **截止时间是硬性上限**。排空不是无限等待；超时后强制关闭剩余连接并退出，保证停止一定能在可预期的时间内完成。

## 6. 退出前必须做的清理

```cpp
        closeAllConnections();
        discardQueuedTasks();
        running.store(false, std::memory_order_release);
```

三步各自解决一个问题：

1. **关闭所有连接**：释放套接字和客户端名额，避免把资源留给下一个使用者。
2. **丢弃所有未执行任务**：这一步是必须的，因为控制任务里包着客户端名额。任务对象销毁时，捕获的槽位释放封装才析构，名额才归还。少了这一步，每次停止都会泄漏一批名额。
3. **标记循环已停止**：让之后所有入队请求立刻失败，而不是进入一个再也不会被处理的队列。

第 3 步在最后，是因为前两步可能间接触发入队（例如连接关闭路径上的刷新），此时还应当允许它们完成。

## 7. 停止方：不能等自己

停止时如果当前线程就是事件循环线程自己，等待自己会造成死锁：

```cpp
    if (state->worker.get_id() == std::this_thread::get_id()) {
        // 在事件线程内请求停止时不能自等待，交由线程自行结束。
        state->worker.detach();
        return;
    }
    state->worker.join();
```

这里选择分离而不是报错，是因为“在事件循环内部触发停止”是一个合理场景（例如某个投递进来的任务检测到致命错误，要求整个服务停下）。分离之后线程自己跑完循环、自己结束，对象由共享指针维持存活，不会悬空。

## 8. 坑点：重启前必须先接管旧线程

事件循环允许停止后再次启动。启动时会创建一个新的线程对象赋给同一个成员，如果旧线程对象**仍然处于可等待状态**，给一个可等待的线程对象赋值会直接终止进程（标准规定）。所以启动时先判断并接管：

```cpp
    if (state->worker.joinable()) {
        // 上一次线程已退出但尚未回收，先接管线程对象再创建新线程。
        state->worker.join();
    }
```

正常路径下停止方已经等待过，这里不会真的执行；但上一次停止是“从循环内部触发”时，线程被分离、没有等待，成员就还是可等待状态。少了这个判断，那种场景下重启会直接把进程干掉。

## 9. 坑点：排空期间不能停止接收入队之外的判断

排空期间的处理是“停止接收入队，但继续处理事件和完成结果”。实现上体现为两个不同的判断：

- 数据类任务（通用、控制）：`!acceptingPosts || stoppingNow` → 一律拒绝；
- 完成结果：只有“立即停止”才拒绝，排空时继续接受。

如果偷懒把两者合成一个判断（比如都用 `stoppingNow`），排空期间就会拒收完成结果，连接永远等不到结果，排空只能靠 30 秒超时收场——功能上“没坏”，但优雅排空完全失效，退化成“等 30 秒再强杀”。

## 10. 整体逻辑

停止的完整时序：

1. 停止方在锁内设置停止标志（以及是否排空），释放锁；
2. 停止方唤醒事件循环；
3. 事件循环回到循环开头，执行完已排队任务；
4. 看到停止标志：
   - 立即停止 → 跳出循环；
   - 排空 → 第一次进入时初始化截止时间并通知所有连接，之后每轮检查“是否全部关闭”和“是否超时”；
5. 跳出后依次关闭连接、丢弃未执行任务、标记停止；
6. 停止方等待线程退出（如果停止方不是该线程自己）。

第 1 步“在锁内设置、在锁外唤醒”也是刻意的：唤醒操作会让事件循环立刻去读停止标志，如果标志还没写进去就唤醒，事件循环会白跑一轮；反过来，如果持锁唤醒，而唤醒实现可能触发回调路径，就有二次加锁的风险。当前写法让“标志可见”发生在“唤醒发出”之前，两者都不出问题。
