# 服务生命周期

本篇说明服务从配置到停止的完整过程，以及每一步的约束。

## 1. 对外只有一个入口

使用方只需要接触一个控制器对象：给它一份配置，叫它启动；停止时叫它停止。监听器、接入线程、事件循环、连接管理这些概念都藏在内部，使用方不需要知道，也不能绕过它直接操作连接。

控制器还提供一个“绑定存储控制器”的入口，用于把当前阶段测试用的存储桥接挂上去。这个入口在设计上就是临时的，注释里也写明了它不代表最终的对接方式。

## 2. 启动前的配置校验

启动时会先做一轮校验，任何一项不满足就直接拒绝启动，不做部分启动。校验项：

| 校验项 | 要求 |
|---|---|
| 当前状态 | 必须处于“已创建” |
| 命令执行器 | 必须已提供 |
| 监听地址 | 只接受数字形式的回环地址 |
| 加密要求 | 若要求加密，则必须拒绝启动（TLS 未实现） |
| 明文许可 | 必须显式打开 |
| 非回环监听 | 在明文许可之外，还需要单独打开“允许远程明文” |
| 连接数上限 | 不能为 0 |
| 流水线深度 | 不能为 0 |
| 帧上限 | 不能小于固定头长度，且不能超过实现能安全处理的值 |

这里值得说明两条：

**回环地址只认数字字面量。** 不解析主机名，因为主机名需要解析，解析结果可能指向非回环地址，等于绕过限制。只接受 `127.0.0.1`、`::1` 及其 IPv4 映射形式。

**默认配置会拒绝启动。** 默认要求加密传输，而加密传输尚未实现，所以“默认安全”的表现就是起不来。要用明文开发，必须同时显式声明两件事：这次允许明文、这次是开发用途。非回环再额外加一层。这样做是为了让“不小心把明文服务暴露到网络上”这件事变得不可能——必须有人明确地、逐条地把三道许可都打开。

## 3. 事件循环数量的决定

配置里的事件循环数量为 0 时按机器推导：取逻辑核数的一半，向下不低于 1、不超过 16。

取一半是因为存储层自身也有线程池，I/O 线程和业务线程争抢同一个物理核只会互相拖慢；上限 16 是为了避免连接数很少时创建大量空转线程。

## 4. 监听与接入

监听套接字创建时设置三个属性：

- **地址可重用**：便于服务重启后立刻重新绑定，不用等内核回收。
- **非阻塞**：接入循环不能被单个连接卡住。
- **关闭时自动释放**：进程派生子进程时不会把监听句柄泄漏出去。

接入线程的循环逻辑：

1. 等待监听套接字可读，最长等 100 毫秒（同样是为了给停止留响应期限）；
2. 循环接受连接，直到没有更多待接受的连接；
3. 对每个新连接：设为非阻塞、关闭时自动释放、开启小包即时发送和连接保活；
4. 记录对端地址和端口（只取数字形式，不做反向解析）；
5. 预留一个客户端名额；
6. 把连接交给事件循环组。

第 3 步的两个套接字选项各有用途：小包即时发送避免小响应因等待合并而引入延迟；连接保活让死连接最终能被内核检测出来并回收，这是当前缺少应用层超时的一种兜底。

## 5. 容量控制

客户端数量上限通过**先占位、后使用**的方式控制：

1. 读取当前计数；
2. 如果小于上限，尝试把计数加一；
3. 加一成功才算占到名额，失败就重试；
4. 占不到名额就拒绝这个连接（直接关闭）；
5. 连接关闭时把名额还回去。

关键在于“名额只能还一次”。连接的关闭路径不止一条：正常关闭、协议错误、传输失败、服务停止、任务被丢弃。如果在多条路径上都还名额，计数会被多减，最终变成负数或提前放行超额连接。所以名额释放被包装成一个**只能成功执行一次**的动作，无论被调用多少次，实际效果只有第一次生效。

名额的另一个作用是它同时承担了“连接释放”的语义：无论是连接对象析构，还是接入任务因为队列满被丢弃，最终都会触发这同一个动作。

## 6. 分派

新连接交给事件循环组后，按轮询方式选定一个事件循环，由那个循环接管后续全部操作。

如果事件循环组尚未启动或已经停止，分派会被拒绝，名额立即释放，连接关闭。这一步保证了停止过程中不会再接入新连接。

## 7. 停止顺序

停止按固定顺序进行，顺序不能颠倒：

1. 先停接入器：它可能仍在接受新连接，必须先让这条路径停下来；
2. 再停事件循环组：按排空或立即方式停止所有循环，等待线程退出；
3. 释放组件，服务状态置为已停止。

先停接入器的原因很直接：反过来的话，接入线程可能在事件循环组已经停止之后又递交一个新连接，而这个连接将永远不会被处理，名额也不会释放。

状态流转：

```text
已创建 → 运行中 → 排空中 → 已停止
             ↘ 已停止（立即停止）
```

处于已停止时再次调用停止是无操作；处于已创建时调用停止只做状态转换。

## 8. 等待线程退出

设计文档里保留了一个“等待服务线程退出”的入口，当前实现里它是空操作——因为停止过程本身就是同步的：停止调用会一路等到接入线程和所有事件循环线程都结束才返回。调用方不需要额外等待。

这意味着**停止是一个可能耗时的同步调用**：优雅停止最多会等待 30 秒的排空期限。如果需要非阻塞停止，应当由调用方自行放到别的线程上执行。

## 9. 启动失败的处理

任何一步失败都不会留下半启动状态：

- 事件循环组启动失败：释放事件循环组，直接返回失败；
- 监听器启动失败：先停止并释放事件循环组，再返回失败；
- 事件循环组内部某个循环启动失败：把已启动的循环回滚停止，返回失败。

这条要求是为了避免“服务报告启动失败，但某些线程还在跑”的情况——那种状态下重新启动会叠加线程，问题极难定位。
