# 连接与调度

本篇说明单条连接内部的行为：怎么读、怎么排队、怎么保证顺序、什么时候被关闭。

## 1. 请求为什么必须串行

同一条连接上，业务请求**按接收顺序执行，响应也按相同顺序返回**。同一时刻只有一个请求在执行，后面的请求先排队。

这不是为了省资源，而是业务语义的要求：

- 客户端可能先发“新增”、再发“查询同一个键”，这两条之间有先后依赖；
- 如果并发执行，查询有可能先于新增完成，返回“键不存在”，而客户端无法预期这种结果；
- 即使允许并发执行、只保证响应顺序，也只是把不确定性藏起来，没有消除。

跨连接之间是完全并发的，所以这个约束不会让服务整体串行化。

## 2. 连接的四个缓冲区

每条连接维护四类状态，各有上限：

| 名称 | 含义 | 上限 |
|---|---|---|
| 未解析输入 | 已收到但还不足以拼成完整帧的字节 | 单帧上限 + 64KB |
| 待执行队列 | 已拼成完整帧、已通过校验、等待执行的请求 | 待执行加在途总数不超过配置的流水线深度 |
| 在途请求 | 已交给执行层、还没拿到结果的那一条 | 固定 1 |
| 输出积压 | 已编码、还没发完的响应 | 固定 16MB |

“未解析输入”的上限比单帧上限多留 64KB，是为了容纳“一帧刚好拼完、后面还粘着下一帧开头”的情况，同时避免为粘包预留过多内存。

## 3. 读与解析的流程

一次可读事件的处理顺序：

1. **先解析已有的缓冲**。即使这次没有读到新字节，之前留下的半帧也可能因为后续数据已经到达而拼完整。
2. **检查是否需要继续读**。以下几种情况直接停止，不再读新数据：连接正在关闭、输入缓冲已达上限、在途请求已占满流水线、连接进入排空、对端已经关闭。
3. **按预算读取**：一次事件最多读取 64KB。读进来的字节立刻尝试解析，边读边解析，而不是读满再解析。
4. **解析结果分支处理**：
   - 数据不足：保留半帧，等待下一次事件。
   - 帧完整：交给命令校验；通过则入队，未通过则按协议错误收尾。
   - 帧非法或过大：无法在字节流中重新定位，直接关闭连接。

第 3 步的“边读边解析”是必要的：如果先读完 64KB 再解析，一个恶意客户端可以用大量垃圾数据让输入缓冲在两次解析之间涨到上限。

## 4. 调度与顺序保证

请求入队后，调度遵循一个简单规则：**如果当前没有在途请求，就取队首提交，并把它标记为在途**。提交时会记录这条请求的标识和命令码。

结果回来时按以下规则处理：

- 结果的连接标识和请求标识必须与当前在途请求完全一致，否则说明调度状态与执行结果对不上，按内部错误收尾并关闭连接。这是为了防止“结果贴错请求”这种最难排查的错误被静默吞掉。
- 结果正常时，先更新会话状态（协商或认证成功时推进阶段），再编码响应，最后清空在途标记。
- 在途清空后，如果队列里还有请求就继续提交下一条；如果没有，连接回到可读状态。

响应必须原样带回请求标识，这是客户端把响应和请求对上号的唯一依据。执行层如果没填，网络层会用请求里的值补上。

## 5. 写与输出缓冲

- 结果编码成响应帧后追加到输出缓冲，同时累加积压字节数。
- 可写事件触发时按预算发送，一次事件最多 256KB。
- 一帧没发完时记录已发送位置，下一次从断点继续，不重复发送。
- 输出缓冲空且没有在途请求、且连接处于“写完即关”状态时，执行最终关闭。

输出积压超过 16MB 时不排队等待，直接认为连接不可恢复并关闭。理由是：积压到这个量级通常意味着对端不读数据（客户端卡死或恶意），继续缓冲只会耗尽服务端内存；而丢弃响应又会让客户端收到不完整的结果，破坏协议。两者相权，关闭连接是唯一能让客户端明确感知到失败的做法。

## 6. 背压与丢弃规则

限额到达时的行为是明确规定的，不是“尽力而为”：

| 触发条件 | 行为 |
|---|---|
| 待执行队列已满 | 停止读取（不再关注可读事件），已读入缓冲中的完整帧继续保留；**超出的请求在解析阶段就被丢弃** |
| 未解析输入达上限 | 暂停读取，等在途请求完成后继续 |
| 输出积压达上限 | 关闭连接 |
| 事件循环的任务队列满 | 丢弃该任务并告知提交失败 |
| 完成结果队列满 | 放弃该响应，并关闭对应连接 |

最后一条需要说明：完成结果无法投递时，连接会一直停在“等待结果”的状态，既不会继续处理队列，也不会自己关闭。所以此时唯一正确的做法是关闭这条连接——用一次明确的断连，换掉一个永远不会推进的半死状态。

## 7. 关闭的几条路径

连接可能因为下面任意一种原因关闭，行为略有差别：

| 触发原因 | 处理方式 |
|---|---|
| 协议错误（帧非法、字段不合法、请求顺序违规） | 写出一条错误响应，然后关闭。不再接受新请求 |
| 对端正常关闭 | 停止接收新请求；已产生的响应尽量写完再关闭 |
| 对端异常断开 | 直接关闭，丢弃缓冲 |
| 主动优雅关闭（服务排空或管理踢出） | 停止读取，把已接收的请求依次执行完并写完响应，然后关闭 |
| 主动立即关闭（服务立即停止） | 直接关闭，丢弃未执行请求和输出 |
| 输出积压超限 | 直接关闭 |
| 结果与在途请求无法对应 | 按协议错误处理并关闭 |
| 完成结果队列满 | 直接关闭 |

关键区别在于“是否先写完已有响应”。协议错误和对端关闭都会尽量把话说清楚再断开，让客户端知道发生了什么；而资源超限和立即关闭不做这个努力——此时继续写只会加重问题。

## 8. 关注事件的动态调整

连接在任一时刻只关注自己真正需要的事件：

- 需要读数据（未达上限、非排空、非关闭中）：关注可读。
- 有数据要发（输出缓冲非空或传输层要求可写）：关注可写。
- 两者都不需要时：不关注任何读写事件，只保留对端关闭通知。

最后一种情况是刻意保留的。它通常出现在“待执行队列已满、等在途请求完成”的时刻——此时既不读也不写，但仍然需要知道对端是否已经断开，否则连接会一直占着名额等到服务停止。

关注集合每次事件处理后都会重新计算并提交，保证它始终反映连接当前的真实需要。
