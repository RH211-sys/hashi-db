# 命令执行与错误语义

本篇说明命令交给谁执行、结果怎么回来、出错时用什么方式表达。

## 1. 执行接口的约束

网络层只通过一个统一接口把命令交出去。这个接口的约定有四条：

1. **只接收结构化命令**：连接标识、请求标识、来源、对端地址、主体名称、命令码、字段列表。执行方不需要、也拿不到连接对象。
2. **异步返回**：调用时同时传入一个完成回调，结果通过回调交回，同步返回不代表执行完毕。
3. **回调必须恰好被调用一次**：无论成功、失败还是被拒绝，都要给一个结果，不能既不回也不报错。否则网络层会一直等在途状态上。
4. **不得触碰连接对象**：执行方在别的线程上运行，直接操作连接会造成数据竞争。它只能把结果交回，由连接所属的事件循环去更新连接。

第 4 条是这一层最重要的边界。执行方的线程和连接的线程不是同一个，跨越这条边界的任何直接访问都是错误的。

## 2. 当前挂上去的实现

当前挂的是**存储桥接**，它的定位是阶段测试适配器，注释里明确写了“不代表最终的存储对接方式”。它的行为按命令分三类：

| 命令 | 行为 | 结果 |
|---|---|---|
| 探活 | 就地响应，不经过任何后端 | 成功 |
| 退出 | 就地响应，并标记“写完就关连接” | 成功 |
| 查询、新增、修改 | 就地拒绝 | 类型未注册 |
| 删除、持久化、刷盘、重写 | 交给工作线程调用存储接口并等待结果 | 成功或存储不可用 |
| 其余全部（协商、认证、统计、连接列表、连接踢出） | 交给工作线程后落到未实现分支 | 不支持 |

“查询、新增、修改”三类直接被拒，是因为还没有确定可上线的数据编码约定。当前的选择是明确拒绝，而不是把存储层内部的序列化格式直接暴露到协议上——后者一旦上线就再也改不动了。

“协商、认证”落到未实现分支这一点，造成的影响见 [03-会话与认证](./03-会话与认证.md) 第 6 节：会话无法推进，业务命令全部被拦。这是当前最需要处理的功能缺口。

## 3. 工作线程池

需要访问存储的命令走一个独立的工作线程池：

- 线程数量固定 4 个；
- 待处理任务队列上限 1024；
- 队列满时**立即返回“忙”**，不排队等待；
- 线程池由桥接对象自己拥有，随对象销毁而结束。

为什么必须用独立线程池：存储接口返回的是 future，取结果会阻塞。如果直接在事件循环线程上取结果，一个慢请求会卡住那条循环上的所有连接，正是“第三条不变式”明令禁止的。

为什么队列满时立刻返回“忙”而不是等待：等待会让事件循环线程被间接拖住——它在提交时被阻塞，同样影响其他连接。返回“忙”让客户端明确知道这次请求没被接受，可以重试。

线程池的析构会先标记停止、唤醒所有线程、等待它们结束，保证不会有任务在对象销毁后还在访问已释放的存储引用。

## 4. 错误码

网络层对外使用自己的一套错误码，不与存储层内部错误码共用。这样存储层的错误码调整不会直接改变协议行为。

| 数值 | 名称 | 含义 | 典型场景 |
|---|---|---|---|
| 0 | 成功 | 请求已正常处理 | — |
| 100 | 坏帧 | 帧头、长度或字段格式非法 | 长度对不上、字段重复、缺必填字段 |
| 101 | 不支持 | 版本、特性或字段当前不支持 | 保留标志位、未知字段编号 |
| 102 | 未认证 | 会话尚未通过认证 | 未认证时发业务命令 |
| 300 | 忙 | 服务容量或在途请求达上限 | 执行队列满 |
| 301 | 过大 | 帧、字段或输出超过限制 | 键超过 32 字节 |
| 400 | 未知命令 | 命令码不在定义范围内 | 客户端写错命令码 |
| 401 | 无权限 | 会话不允许执行该命令 | 预留，当前无 ACL |
| 402 | 类型未注册 | 数据没有可用的线上编码 | 查询、新增、修改 |
| 500 | 内部错误 | 未分类的服务端错误 | 结果与在途请求对不上 |
| 501 | 存储不可用 | 执行层无法接受或完成请求 | 存储操作失败 |
| 502 | 加密传输失败 | 握手或加密传输出错 | 预留，TLS 未实现 |

分组来看：100 段是协议问题，300 段是容量问题，400 段是命令与权限问题，500 段是服务端问题。客户端可以按段位决定是重试、改请求，还是报告服务异常。

## 5. 存储错误码如何映射

桥接把存储层的返回码映射成上面的错误码：

| 存储层结果 | 映射为 | 理由 |
|---|---|---|
| 成功 | 成功 | — |
| 找不到、已过期 | 存储不可用 | 对客户端而言都是“这次没拿到数据” |
| 类型未注册 | 类型未注册 | 语义一致，直接对应 |
| 其他 | 内部错误 | 未分类，不在协议里暴露细节 |

映射时**不把存储层的原始错误码写进响应**。原因是存储错误码属于内部实现，一旦暴露就成了对外契约的一部分，将来改动会破坏兼容性。客户端只需要知道“这类失败该怎么处理”，不需要知道内部具体是哪个环节出的问题。

## 6. 响应的构成

一条响应由三部分组成：

1. **状态码**：由网络层统一写入，取值来自上面的错误码表。
2. **信息文本**：可选的、给人看的说明；有错误时一般会带上。
3. **业务字段**：执行方返回的结果字段，随命令而定。

两条硬性约束：

**状态码和信息字段是网络层保留的。** 执行方返回的业务字段里如果包含这两个编号，整条响应按内部错误处理并关闭连接。这样做是为了防止业务的返回值覆盖网络层写入的状态码——否则客户端可能收到一个“成功”标记横在错误响应上。

**信息文本有长度上限，且必须保持合法文本编码。** 超出上限时截断；如果截断位置落在多字节字符中间，会继续往前退到完整的字符边界。不做这一步的话，一条中文错误信息被截断后会产生非法编码，接收方按协议校验会直接判为坏帧，反而掩盖了真正的错误。

信息文本还应当只写“发生了什么”，不写“内部怎么实现的”。当前实现里返回的都是固定短语，不含内部路径、键值或凭据。

## 7. 执行层抛异常时怎么办

如果执行接口抛出异常，网络层会把它转成一条“内部错误”响应，写明执行方拒绝了这条请求，然后按正常流程把响应发回去。

这样做而不是直接把连接关掉，是因为异常通常只影响这一条请求；把错误变成一条明确响应，客户端能继续使用这条连接。真正不可恢复的情况（比如结果和请求对不上）才会关闭连接。

## 8. 还没有的部分

- **没有权限模型**：无权限错误码已定义，但没有产生它的逻辑。
- **没有统计命令实现**：命令和字段都已定义，执行侧为空。
- **没有连接管理实现**：连接列表和踢出命令只有协议定义；连接注册表目前只是一个接口声明，既没有实现，也没有装配到服务里。
- **没有业务数据编码**：查询、新增、修改三类命令的返回值格式尚未确定，当前一律返回类型未注册。

在这些补齐之前，把这一层接上真实客户端只能验证到协议与探活层面，无法验证完整的数据读写闭环。
