# 整体逻辑

本篇回答三个问题：这一层为什么存在、请求在它内部经过谁、哪些性质必须始终成立。后面各篇展开具体模块。

## 1. 这一层的定位

网络层是数据库对外的唯一入口。它把网络上来的字节流变成一条条结构化命令，交给业务执行层处理，再把处理结果变回字节流发回去。

它负责的事情：

- 维护客户端连接，包括建立、读写、关闭和容量控制。
- 按自定义协议把字节流拆成完整的帧，并校验帧是否合法。
- 把合法的请求帧翻译成结构化命令，校验每条命令携带的参数是否符合约定。
- 维护每条连接的会话阶段（是否已协商、是否已认证），并按阶段决定命令能否执行。
- 在连接内保证请求按接收顺序执行、响应按相同顺序返回。
- 限制每条连接和每个事件循环占用的资源，超限时按既定规则丢弃或关闭。

它明确不负责的事情：

- 不直接读写缓存和磁盘。业务数据怎么存、怎么取，属于存储层。
- 不做业务数据的编解码。网络层只认识协议规定的字段和类型，具体某种数据怎么序列化由执行层决定。
- 不在 I/O 线程上等待慢操作。任何可能阻塞的等待都放到独立的工作线程上。

这三条“不负责”是这一层的边界。越界的后果很直接：一旦在网络层引入存储细节，协议就被序列化格式绑死；一旦在 I/O 线程上等待，单个慢请求就会卡住整条事件循环上的所有连接。

## 2. 端到端链路

一个请求从建立连接到拿到响应，依次经过下面这些环节：

```text
客户端 TCP 连接
   ↓
接入环节：接受连接、预留客户端容量、分配连接标识、选定一个事件循环
   ↓
事件循环：可读事件触发读取，把字节交给帧解析
   ↓
帧解析：缓冲区里的字节拼成完整帧（处理拆包与粘包），校验帧头与字段格式
   ↓
命令解析：按命令码校验字段集合与取值，还原成结构化命令
   ↓
会话检查：当前阶段是否允许执行这条命令
   ↓
排队：进入该连接的待执行队列；若已有请求在途则等待
   ↓
调度：取出队首交给命令执行层（此时只有一个请求在途）
   ↓
执行：在工作线程上调用业务接口并等待结果（I/O 线程不参与等待）
   ↓
回投：结果带着连接标识与代际，投回该连接所属的事件循环
   ↓
编码：把结果编成响应帧，放进该连接的输出缓冲
   ↓
写出：可写事件触发按预算发送，发完继续处理队列里的下一条
```

反向也有一条独立路径：**对端关闭或出错**时，连接不再接收新请求，先把已产生的响应尽量写完，再释放资源。

## 3. 四条不变式

这四条在任何实现改动中都不能破坏。破坏其中任何一条，都会产生难以复现的问题。

**第一条：一条连接在生命期内只属于一个事件循环。**
连接的所有状态、缓冲区和对 socket 的操作，都只由那个事件循环的线程执行。这样连接内部不需要加锁，也不存在两个线程同时读写同一条连接的可能。

**第二条：同一条连接上，同一时刻只有一个业务请求在执行。**
已解析但还没提交的请求排队等待。这样做不是为了省资源，而是为了保证同一条连接上的操作顺序——上一条是写入、下一条是读取时，顺序错了结果就错了。

**第三条：I/O 线程绝不等待业务结果。**
业务执行可能是毫秒级也可能是十几毫秒级，I/O 线程只负责把请求交出去，然后回去处理其他连接的事件；结果完成后再投回来。等待只发生在专门的工作线程上。

**第四条：所有队列都有上限。**
连接数、未解析输入、待执行队列、输出积压、跨线程任务队列都有硬上限。到达上限时的处理规则是预先定好的，不是“等一等就好了”。

## 4. 线程模型

系统里有四类线程，各自的职责边界很清楚：

| 角色 | 数量 | 做什么 | 不做什么 |
|---|---|---|---|
| 接入线程 | 1 | 接受新连接、预留容量、把连接交给某个事件循环 | 不解析协议、不处理已建立的连接 |
| 事件循环线程 | 可配置，按机器核数推导 | 驱动自己名下所有连接的读写、解析、调度和关闭 | 不等待业务结果 |
| 业务工作线程 | 固定若干 | 调用业务接口并等待结果 | 不触碰连接对象，不直接写 socket |
| 存储内部线程 | 由存储层决定 | 实际的缓存与磁盘操作 | 与本层无直接接触 |

跨线程传递只有两个方向：接入线程把新连接交给事件循环；工作线程把执行结果投回事件循环。两个方向都是“投递任务”，不是直接调用对方的数据结构。

## 5. 一次请求的完整旅程

以一次“探活”请求为例，走一遍上面链路：

1. 客户端连上来，接入环节预留一个客户端名额，分配连接标识，选定事件循环。
2. 事件循环注册可读关注，客户端发来的字节被读入该连接的输入缓冲。
3. 帧解析在缓冲中切出一个完整帧，校验帧头（版本、头长度、长度关系）和每个字段（类型、长度、编码）。
4. 命令解析按命令码校验字段集合：该命令允许哪些字段、哪些必填、长度是否超限、有没有重复。
5. 会话检查确认当前阶段允许这条命令。
6. 请求进入待执行队列，被取出后交给命令执行层。
7. 执行层就地给出结果（探活不需要访问存储），结果被投回该连接所属事件循环。
8. 事件循环把结果编成响应帧，放进输出缓冲，注册可写关注。
9. 可写事件触发后按预算发送，发完后清空在途标记，继续处理队列里的下一条。
10. 客户端发出退出命令时，响应写完后连接关闭，客户端名额被释放。

需要访问存储的命令，第 7 步换成“工作线程调用存储接口并等待结果”，其余不变。

## 6. 限额总表

当前实现里的全部限额。括号里是默认值，可在服务配置里调整带“可配”标记的项。

| 层级 | 限制对象 | 上限 | 到达上限时的行为 |
|---|---|---|---|
| 接入 | 同时存在的客户端连接数 | 可配（默认 10000） | 拒绝新连接，直接关闭 |
| 接入 | 监听等待队列 | 固定 1024 | 由内核行为决定，超出部分客户端侧失败 |
| 连接 | 未解析输入缓冲 | 单帧上限 + 64KB | 暂停读取，等在途请求完成后再继续 |
| 连接 | 待执行请求队列 | 可配（默认 64，含在途） | 超出的请求直接丢弃，只暂停读取 |
| 连接 | 输出积压 | 固定 16MB | 视为不可恢复，关闭连接 |
| 事件循环 | 通用任务队列 | 固定 4096 | 丢弃后续任务，提交方收到失败 |
| 事件循环 | 控制任务队列 | 固定 256 | 丢弃后续任务，同时释放连接名额 |
| 事件循环 | 完成结果队列 | 固定 4096 | 放弃该响应并关闭对应连接 |
| 执行 | 工作线程待处理任务 | 固定 1024 | 立即返回“忙”，不排队等待 |
| 协议 | 单个帧 | 可配（默认 16MB） | 拒绝该帧并按协议错误处理连接 |

“待执行请求队列”一项需要特别注意：它算的是**待执行加在途**的总数，所以达到上限时连接会停止读取，而不是无限接收后排长队。

## 7. 关闭与排空的总原则

关闭分两种，行为差别很大：

- **立即停止**：不再接受任何入队，丢弃未执行的任务，直接关闭所有连接并释放资源。用于进程退出或异常场景。
- **优雅停止**：停止接收新连接和新请求，但**已经提交出去的请求要继续等结果回来**，把响应尽量写完再关闭。等待有时间上限，超时后强制关闭剩余连接。

排空期间有一个容易混淆的点：此时**仍然接受完成结果的回投**。因为那些请求是在停止之前就提交出去的，如果此刻拒绝它们的完成结果，连接会一直停在“等待一个永远不会到的结果”的状态上。停止的是“新请求”，不是“已有请求的结果”。

## 8. 模块划分

各模块的职责边界：

| 模块 | 一句话职责 |
|---|---|
| 公共类型 | 连接标识、端点、缓冲区、状态与错误码等共享定义 |
| 协议编解码 | 帧与字节流之间的双向转换，含拆包、粘包和格式校验 |
| 命令解析 | 按命令码校验字段并还原成结构化请求 |
| 会话 | 记录协商与认证状态，决定命令能否执行 |
| 连接 | 单条连接的状态、缓冲、排队与读写 |
| 事件循环 | 驱动一批连接的 I/O，接收并执行跨线程投递的任务 |
| 事件循环组 | 创建多个事件循环，把新连接均衡地分派下去 |
| 接入器 | 监听端口、接受连接、控制客户端容量 |
| 服务端 | 组装上述组件，管理启动、运行、排空和停止 |
| 对外控制器 | 对使用方暴露的唯一入口，隐藏内部分层 |
| 命令执行 | 业务执行接口，以及当前用于阶段测试的存储桥接实现 |

各模块的详细业务规则见后续各篇。
