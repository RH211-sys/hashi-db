# 代码编写（非常重要）

1. **明确三类代码**

   每个函数中的代码先区分：

   - **核心流程**：完成当前功能的正常步骤。
   - **边界处理**：检查客户端输入、系统调用结果、队列容量和资源状态等防御边界。
   - **状态收尾**：关闭连接、释放资源、恢复状态或生成错误结果。

   **核心流程不应反复穿插大量边界判断。边界处理完成后，核心流程只使用已经满足契约的数据。**

2. **每个模块只检查自己的条件**

   比如沿着网络层的调用流程（参考，可能仓库更新后，原有的意义已经修改）：

   - `Transport` 检查 socket、TLS 和非阻塞 I/O 的结果。
   - `FrameCodec` 检查字节流能否组成合法帧。
   - `CommandParser` 检查帧字段是否符合具体命令规则。
   - `Connection` 检查会话阶段、请求顺序和在途状态。
   - `Reactor` 检查任务队列、线程归属和连接生命周期。
   - 执行器处理业务命令和存储结果。

   例如，`FrameCodec::feed` 返回 `FRAME_READY` 后，`Connection` 不再重新检查帧头和 TLV 的字节结构，只处理连接级规则。

3. **公共入口检查，内部函数依赖契约**

   模块对外公开的函数必须检查调用前提。模块内部的私有函数可以依赖调用者已经建立的条件。

   例如：

   ```
   DecodeStatus FrameCodec::feed(...) {
       // 检查输入偏移和帧边界。
       ...
       return DecodeStatus::FRAME_READY;
   }
   
   bool Connection::handleFrame(Frame frame, ...) {
       // 这里直接处理完整 Frame，不重复检查底层字节边界。
       ...
   }
   ```

   如果一个私有函数需要反复检查同一个条件，说明调用契约或状态设计不清楚，应优先修改接口和调用关系。

4.  **把边界处理拆成独立步骤**

   一个函数尽量按照下面顺序组织：

   ```
   检查输入 ( /* ============ 检查输入 ============ */)
   → 转换数据 ( /* ============ 转换数据 ============ */)
   → 执行核心流程 ( /* ============ 核心流程 ============ */)
   → 提交状态 ( /* ============ 提交状态 ============ */)
   → 返回结果 ( /* ============ 返回结果 ============ */)
   ```

   不要写成：

   ```
   执行一步核心流程
   → 检查一个错误
   → 再执行一步核心流程
   → 再检查一个错误
   → 重复清理状态
   ```

   > 防御代码，核心执行，结果返回等逻辑在整个函数中杂糅在一起，这是不可取的

   **复杂的检查应提取为有明确名称的函数**，例如：

   - `validateFrame`
   - `parseFields`
   - `checkSessionPermission`
   - `handleTransportResult`
   - `closeConnection`

   **提取函数后，调用处应该能直接看出主流程，而不是隐藏真正的业务动作。**

5. **统一错误表示**

   **每个模块只负责把错误转换成自己的结果类型：**

   - Transport 返回 `OK`、`WOULD_BLOCK`、`PEER_CLOSED`、`FAILED`。
   - FrameCodec 返回 `NEED_MORE`、`FRAME_READY`、`INVALID_FRAME`、`FRAME_TOO_LARGE`。
   - CommandParser 通过 `bool` 加错误码和说明返回解析结果。
   - Connection 把连接级错误转成协议响应或关闭动作。
   - Reactor 处理任务入队失败和过期完成结果。

   上层不要重新解释底层错误的细节。例如 `Connection` 不应直接读取 `errno`，而应根据 `TransportResult` 决定继续、等待、关闭或处理对端关闭。

6. **正常流程使用单一主路径**

   核心函数应尽量只有一条清晰的成功路径。失败分支在入口集中返回，或者交给专门的错误处理函数。

   例如请求派发应接近：

   ```
   取出队首请求
   → 检查会话阶段
   → 保存 HELLO/AUTH 的暂存状态
   → 标记当前请求在途
   → 提交执行器
   ```

   不要在这条流程中重复处理帧格式、socket 错误、输出缓冲和 Reactor 队列错误。

7. **正常流程使用单一主路径**

   核心函数应尽量只有一条清晰的成功路径。失败分支在入口集中返回，或者交给专门的错误处理函数。

   例如请求派发应接近：

   ```
   取出队首请求
   → 检查会话阶段
   → 保存 HELLO/AUTH 的暂存状态
   → 标记当前请求在途
   → 提交执行器
   ```

   不要在这条流程中重复处理帧格式、socket 错误、输出缓冲和 Reactor 队列错误。

8. **用对象结构减少运行时防御**

   优先通过类型和生命周期保证条件：

   - 使用 `std::unique_ptr` 表示唯一资源所有权。
   - 使用 `std::shared_ptr` 表示跨线程共享生命周期。
   - 使用枚举表示连接和请求状态。
   - 使用 RAII 自动释放 socket、锁和线程资源。
   - 使用不可复制类型防止错误复制连接或传输对象。
   - 使用独立的结果类型表达“成功、等待、关闭、失败”。

   这样可以删除一部分“理论上不应该发生”的重复空指针和状态检查。

9. **防御代码必须有处理策略**

   每个检查都必须回答两个问题：

   1. 检查失败说明什么？
   2. 失败后应该返回、重试、排队、生成错误响应，还是关闭连接？

   禁止添加没有明确处理意义的代码，例如：

   ```
   if (object == nullptr) {
       return false;
   }
   ```

   如果对象在接口契约中绝不可能为空，就应通过构造流程保证它非空，而不是在每个调用处重复检查。

10. **执行代码部分的注释说明目的，不复述语句**

    注释应该解释（参考）：

    - 为什么要限制读取预算；
    - 为什么完成结果必须回到原 Reactor；
    - 为什么协议错误要延迟到前序请求完成；
    - 为什么某个失败会关闭连接。

    不要写只重复代码表面含义的注释，例如：

    ```
    value += 1; // 给 value 加一
    ```

    对于 `if`，只有当分支改变状态、请求顺序、线程归属或资源生命周期时才需要说明原因。普通条件不应靠大量注释弥补命名和结构问题。

11. **网络层的推荐结构**

    对于当前项目，可以采用下面的固定职责链：

    ```
    Acceptor
    → 接收连接并创建 Transport
    
    ReactorGroup
    → 选择连接所属 Reactor
    
    Reactor
    → 等待事件并保证线程归属
    
    Connection
    → 管理连接状态、请求顺序和响应顺序
    
    Transport
    → 执行非阻塞 TCP/TLS I/O
    
    FrameCodec
    → 字节流与 Frame 转换
    
    CommandParser
    → Frame 与 CommandRequest 转换
    
    ICommandExecutor
    → CommandRequest 与 CommandResponse 转换
    
    Connection
    → 响应编码、发送和关闭
    ```

    每个箭头只传递已经符合前一个模块契约的数据。后一个模块只补充自己的检查，不重复前一个模块已经完成的检查。

12. **提交前检查标准**

    重构或新增代码时，逐个函数检查：

    - 能否一眼看出正常执行路径？
    - 当前检查属于哪个模块？
    - 是否重复检查了前一个模块已经保证的条件？
    - 每个失败分支是否有明确处理结果？
    - 一个请求是否只提交一次、完成一次？
    - 状态修改是否集中在状态拥有者中？
    - 资源释放是否由唯一负责人执行？
    - 跨线程代码是否只传递任务和结果，不直接修改连接？
    - 注释是否解释原因，而不是翻译代码？

这套规范的核心可以压缩成一句话：

> **每个模块只检查自己负责的条件；检查通过后，把结果交给下一个模块；下一个模块不重复前一个模块的检查，只处理自己的功能和状态。**
