## 

### 1 协议常量没有集中管理

当前存在：

```
protocol.h 中的 BASE_HEADER_LENGTH = 24
frame_codec.cpp 中的 FIXED_HEADER_SIZE = 24
frame_codec.cpp 中的 TLV_HEADER_SIZE = 8
command_parser.cpp 中的 8U
test 中的 8U
```

这会造成修改协议时漏改。

> 解决方案建议：聚合到protocol目录下

### 2 `FrameHeader` 的注释和实际含义不完全一致

`FrameHeader` 当前字段实际只有：

```
version  1
flags    1
opcode   2
length   2
body     4
request  8
```

合计 18 字节。

但线上固定头是 24 字节，因为还包括：

```
magic     4 字节
reserved  2 字节
```

而这两个字段不在 `FrameHeader` 结构体里，是编码器额外写入的。

所以当前注释：

```
表示 24 字节基础帧头在主机内存中的结构化形式
```

容易让人误以为它对应完整的线上头部。更准确的说法应该是：

```
表示固定帧头中由业务对象持有的可变字段；
Magic 和 Reserved 由编解码器统一处理。
```

### 3 `PROTOCOL_VERSION` 类型不一致

当前：

```
PROTOCOL_VERSION 是 uint16_t
FrameHeader::version 是 uint8_t
线上 version 是 1 byte
```

协议版本明显是一个字节，因此类型应该统一，否则会产生不必要的转换。

### 4 `bodyLength` 存在两个来源

当前：

- `FrameHeader::bodyLength` 保存一个值；
- `FrameCodec::encode` 不使用它，而是重新根据 `fields` 计算；
- `CommandParser` 又要求 `frame.header.bodyLength` 必须等于字段实际编码长度。

这表示当前存在两个潜在来源：

```
FrameHeader.bodyLength
字段列表计算结果
```

后续需要明确一个原则：

- 要么 `bodyLength` 完全由字段列表计算，禁止外部设置；
- 要么编码前验证 `bodyLength` 与字段列表一致；
- 不应该一处忽略，一处强制校验。

> 解决方案：使用FrameHeader::bodyLength，不要重新计算

### 5 `headerLength` 的扩展语义和实现不一致

`FrameHeader` 的注释说：

```
基础头和扩展头总长度
```

但：

```
validateHeaderValues(...)
```

要求：

```
headerLength == BASE_HEADER_LENGTH
```

也就是说当前并没有真正支持扩展头。

需要在设计上二选一：

- 当前版本明确只支持固定 24 字节，并修改注释；
- 或者实现跳过和解析扩展头的逻辑。

> 解决方案：当前版本明确只支持固定 24 字节，并修改注释

### 6 两个 `feed` 接口语义差异较大

如前面所说，两个接口不仅参数不同，连粘包数据的管理方式都不同，属于接口设计复杂度问题。

> 建议解决方案：使用不同命名

### 7 顶层 TLV 解析和嵌套 TLV 校验存在重复逻辑

当前：

- `validateTlvSequence` 解析一次 TLV 头；
- `parseBody` 又解析一次 TLV 头。

这不是当前功能错误，但会带来维护风险：

```
一个地方修改了 TLV 规则，另一个地方可能忘记同步。
```

> 解决方案建议：可以考虑统一成一个底层 TLV 解析逻辑，再分别执行：
>
> - 结构验证；
> - 字段对象构造；
> - 业务字段校验。

### 8 底层指针和偏移没有被足够抽象

当前代码的底层写法本身有合理性，但协议字段偏移没有命名，会让维护人员必须手工计算：

```
6 是 opcode
8 是 headerLength
10 是 bodyLength
14 是 requestId
22 是 reserved
```

这是可读性和维护性问题。

> 解决方案建议：在protocol.h中存放每个字段的大小，不要直接用字面量（这是对该问题的解决方案，实际上，它应该被放在一个protocol目录下的某个文件中）

### 9 `FrameFlag` 与其他枚举风格不统一

当前：

```
Opcode    enum class
FieldType enum class
FrameFlag enum
```

需要明确是否要统一为强类型枚举，并提供位运算辅助函数。

> 解决方案建议：统一为强类型枚举

### 10 `protocol.h` 的职责略多

当前 `protocol.h` 同时包含：

- wire 协议枚举；
- FrameHeader；
- TlvField；
- Frame；
- CommandRequest；
- CommandResponse。

这不是立即错误，但它混合了：

```
线上协议对象
网络层内部对象
执行层交互对象
```

后续执行层继续开发时，可能需要考虑是否拆成：

```
wire_protocol.h
command_types.h
```

当前可以先不拆，但 review 时要明确边界。

> 解决方案：新增一个protocol目录，里面分类存放协议/字段 常量

### 13. 防御性编程问题，防御性代码过多

当前实现把几类代码混在了同一个执行路径中：

- 正常功能逻辑；
- 外部输入校验；
- 系统调用错误处理；
- 资源容量控制；
- 生命周期竞态处理；
- 内部状态一致性检查；
- 异常兜底和重复状态判断。

因此阅读时经常会变成：

```
执行一步核心逻辑 → 检查多个异常 → 再执行一步核心逻辑 → 再检查多个异常
```

并不是所有防御代码都应该删除。

应该保留的主要有：

- 来自客户端的帧长度、字段长度、编码类型和协议版本检查；
- socket 的 `EINTR`、`EAGAIN`、对端关闭和不可恢复错误处理；
- 非阻塞 I/O 的 `WOULD_BLOCK` 处理；
- 连接数、输入缓冲、输出缓冲和流水线容量限制；
- Reactor 跨线程任务的生命周期检查；
- 连接关闭后迟到完成结果的处理；
- 连接代际校验，避免旧连接结果写入新连接。

比较值得删减或重构的是：

- 对同一内部不变量的多处重复检查；
- 在已经由上层保证的情况下，底层再次重复检查相同条件；
- 对内部对象频繁检查空指针，但对象创建契约已经保证其非空；
- 对已经由状态机排除的状态再次逐层判断；
- 只为了“任何异常都不崩溃”而添加的大范围 `catch (...)`；
- 任务队列、连接关闭和回调路径中重复表达相同清理语义的代码；
- 一些失败路径本身无法恢复，却分别写了多套近似相同的关闭逻辑。

尤其需要重新审查 `catch (...)`。它目前不仅隐藏了真实错误，还可能让同一个完成回调被调用两次。防御代码如果掩盖状态错误，反而会降低正确性。

- 当前明显的问题是可读性、重复代码和状态逻辑复杂。
- 真正可能影响性能的是重复分配、缓冲区复制、无意义的异常捕获、过度的字符串构造，以及不合理的队列处理。
- 不能只按“删掉判断数量”优化，而应该按调用边界分类。

**建议把防御代码分为四层：**

1. **协议边界层**：处理不可信客户端数据，必须严格检查。
2. **系统 I/O 层**：处理系统调用返回值和非阻塞状态，必须保留。
3. **资源控制层**：处理容量、背压和队列上限，必须保留。
4. **内部实现层**：只验证模块自身应该保证的不变量，能通过结构设计保证的就删除重复检查。

这部分总结一下：

- 核心逻辑和异常路径没有充分分层。
- 部分检查重复，增加了代码噪声。
- 一些内部不变量依靠运行时判断，而不是依靠对象生命周期和接口契约保证。
- 部分 `catch (...)` 过于宽泛，可能隐藏逻辑错误。
- 错误处理路径存在重复清理和状态重置。
- 注释数量很多，但没有始终帮助读者区分“正常流程”和“失败流程”。
- 设计文档强调了 Reactor 使用 epoll，但没有明确写出 Acceptor 可以独立使用 poll，容易造成当前疑问。
