术语说明：`ICommandExecutor` 是网络层向执行层提交结构化命令的接口；`CommandRequest` 是解析、基础校验后的请求对象；`CommandResponse` 是执行层交还给网络连接的结果对象；TLV 是由字段编号、类型和字节值组成的协议字段格式。

## 1. 文档范围

本文件说明网络层与执行层之间当前已经落地的请求、响应和异步完成契约，并列出临时存储桥接的实际能力。它不是未来执行层的内部设计，也不代表当前已经完成完整 CRUD（增删改查）映射。

网络层负责接收传输字节、解析帧、校验命令字段和连接会话阶段；执行层负责命令语义、身份凭据验证、授权策略以及与存储层接口的映射。执行层接收结构化字段，不接收 socket、TLS 对象或 Connection 指针。

## 2. 服务装配入口

正式执行层应实现 `ICommandExecutor`，并在创建 `NetworkServer` 时作为共享依赖注入。`NetworkServer` 是服务端内部装配入口，负责启动监听器和 Reactor，并把解析后的命令交给该执行器。相关声明见 [`network_server.h`](../../../../../project/net_level/server/network_server.h) 和 [`command_executor.h`](../../../../../project/net_level/command/command_executor.h)。

网络层的 `Controller` 是面向上层的服务控制门面，但当前只提供绑定现有存储 `Controller` 的阶段性入口，没有通用的执行器绑定方法。因此，新的执行层要么通过 `NetworkServer` 接口装配，要么在后续工作中为网络 `Controller` 增加正式的执行器注入入口；不能把当前存储桥接当作最终接口。网络 `Controller` 的声明见 [`controller.h`](../../../../../project/net_level/controller/controller.h)。

服务启动还受 `ServerConfig` 安全配置约束：默认要求 TLS，并要求提供有效证书链和私钥；开发明文需要显式许可，非回环地址还需要额外的远程明文许可。执行层注入成功不代表网络服务必然启动成功。

## 3. 请求数据契约

命令执行入口接收 `CommandRequest`。该对象只包含当前请求的结构化数据，不暴露连接对象或传输资源。

| 字段 | 含义与约定 |
| --- | --- |
| `connectionId` | 进程内连接标识，用于关联所属连接；不是客户端 IP，也不应由执行层重新路由。 |
| `requestId` | 客户端请求标识；响应必须携带相同标识。 |
| `source` | 请求来源；网络连接请求为 `REMOTE`，进程内管理入口可使用 `LOCAL_ADMIN`。 |
| `principal` | 当前会话主体。HELLO/AUTH 尚未成功时可能为空；认证成功后的后续请求携带已确认主体。 |
| `peer` | 远程对端地址与端口；本地管理请求不一定有远程端点。 |
| `opcode` | 命令编号，定义见 [`protocol.h`](../../../../../project/net_level/protocol/protocol.h)。 |
| `fields` | 经解析和基础校验的字段列表；每项包含字段编号、字段类型和原始字节值。字段编号见 [`protocol_fields.h`](../../../../../project/net_level/command/protocol_fields.h)。 |

网络解析器在构造请求前已检查帧版本、字段类型、命令允许字段、必需字段、重复字段及已定义的长度限制。执行层仍需按字段语义解释字节值，并负责业务级约束；不得把字段值直接视为已完成业务验证的数据。

## 4. 响应数据契约

执行层通过本次请求随附的完成回调提交一个 `CommandResponse`。响应至少应包含与请求一致的 `connectionId` 和 `requestId`，并填写网络层稳定错误分类 `ErrorCode`。

| 字段 | 含义与约定 |
| --- | --- |
| `connectionId`、`requestId` | 必须与原请求关联；不匹配会被网络层视为无法关联的内部错误。 |
| `status` | 执行结果。成功使用 `OK`；失败选择合适的 `ErrorCode`，不要直接透传存储层私有错误码。 |
| `message` | 可选的 UTF-8 辅助说明；内容会被限制长度，避免暴露敏感凭据或内部细节。 |
| `fields` | 命令的结果字段。不要在此字段列表中自行加入保留的 `STATUS_CODE` 或 `MESSAGE`，网络层会统一生成它们。 |
| `closeAfterWrite` | 设为 true 时，网络层在当前响应写出后关闭连接；适用于 QUIT 等终止连接的结果。 |

网络层根据当前在途请求生成响应 opcode 和响应标志，并把 `status` 写入 `STATUS_CODE` 字段；`message` 非空时写入 `MESSAGE` 字段。执行层只提供结构化结果，不自行编码协议帧。

执行层常用状态包括 `OK`、`NOAUTH`、`FORBIDDEN`、`UNSUPPORTED`、`TYPE_NOT_REGISTERED`、`BUSY`、`INTERNAL` 和 `STORAGE_UNAVAILABLE`。完整稳定错误分类见 [`net_types.h`](../../../../../project/net_level/common/net_types.h)。

## 5. 命令字段约束

以下为当前解析器接受的请求字段。字段编号和类型属于网络接口契约；修改前需同步协议设计及对应测试。

| 命令 | 字段及约束 |
| --- | --- |
| `HELLO` | 必需：`PROTOCOL_VERSION`（`BYTES`，恰好 2 字节，当前值为版本 1）；可选：`FEATURE_BITS`（`U64`，8 字节）、`CLIENT_NAME`（`UTF8`）。 |
| `AUTH` | 必需：`USERNAME`（`UTF8`）、`PASSWORD`（`BYTES`）。 |
| `PING` | 可选：`PAYLOAD`（`BYTES`）。 |
| `QUIT` | 不接收命令字段。 |
| `GET` | 必需：`KEY`（`BYTES`，最多 32 字节）。 |
| `ADD` | 必需：`KEY`（`BYTES`，最多 32 字节）、`TYPE_NAME`（`UTF8`，最多 32 字节）、`VALUE`（`BYTES`）；可选：`TTL`（`U64`，8 字节）。 |
| `UPDATE` | 必需：`KEY`（`BYTES`，最多 32 字节）、`TYPE_NAME`（`UTF8`，最多 32 字节）、`VALUE`（`BYTES`）。 |
| `DELETE_DATA` | 必需：`KEY`（`BYTES`，最多 32 字节）。 |
| `PERSIST` | 可选：`KEY`（`BYTES`，最多 32 字节）；缺省表示作用于全部数据。 |
| `FLUSH`、`REWRITE`、`CLIENT_LIST` | 不接收命令字段。 |
| `STATS` | 可选：`SCOPE`（`UTF8`）。 |
| `CLIENT_KILL` | 必需：`CONNECTION_ID`（`U64`，8 字节）。 |

当前命令规则不接受重复字段和嵌套字段。字段值最大还受服务端单帧上限约束。请求规则的实现入口是 [`command_parser.cpp`](../../../../../project/net_level/command/command_parser.cpp)。

## 6. 会话与授权职责

网络层按连接顺序派发请求，并在派发前检查协议阶段。HELLO 和 AUTH 都经过执行器契约，但两者的职责不同：HELLO 的协议版本和特性协商由网络层在成功结果到达后提交；AUTH 的凭据验证由执行层负责。

- HELLO：执行器返回 `OK` 后，网络层根据请求中的协议版本和特性位完成协商并更新连接会话；执行器不得把不支持的协商结果报告为成功。
- AUTH：执行层必须完成凭据验证后才能返回 `OK`；成功后网络层把请求中的用户名记为当前主体。仅通过字段格式校验不代表认证成功。
- 后续业务请求会携带当前 `principal`。网络层当前只提供基本会话阶段限制，没有接入真实 ACL 策略；细粒度授权由执行层或后续授权模块负责。
- 同一连接最多有一个业务请求在途。前序 HELLO/AUTH 完成前到达的后续请求会等待，派发时再依据已经提交的会话状态检查。

会话状态的类型和规则见 [`session.h`](../../../../../project/net_level/server/session.h)；连接按序派发和成功响应后的会话提交由 Connection 完成。

## 7. 线程、回调与生命周期

网络层在所属 Reactor 线程调用执行器入口。执行器必须快速返回，不得在 Reactor 线程等待磁盘、存储 future 或其他慢操作；需要阻塞等待时，应在执行层自己的有界工作队列中完成。

执行器正常接收请求后必须调用完成回调且仅调用一次，可以同步调用，也可以在工作线程中异步调用。若入口同步抛出异常，网络层会生成 `INTERNAL` 响应；执行器不得在抛出后再调用该请求的回调。

完成回调只提交结果，不直接修改 Connection 或 socket。网络层会把结果投递到该连接所属 Reactor 的有界完成队列，由 Reactor 校验连接标识和代际后处理。连接已断开或服务已停止时，迟到结果可能被丢弃；因此执行层不能把回调执行等同于客户端一定收到响应。

执行器及其引用的存储 Controller 必须至少存活到相关在途任务结束。执行器自身应明确其工作队列容量、满队列行为、停机策略和异常到响应状态的映射。

## 8. 当前执行器能力与缺口

当前 `StorageControllerExecutor` 是阶段性适配器，不是正式执行层：

| 命令 | 当前适配器行为 |
| --- | --- |
| `PING` | 返回成功。 |
| `QUIT` | 返回成功并要求写完响应后关闭连接。 |
| `GET`、`ADD`、`UPDATE` | 返回 `TYPE_NOT_REGISTERED`；网络值类型 codec 尚未注册。 |
| `DELETE_DATA`、`PERSIST`、`FLUSH`、`REWRITE` | 在独立有界工作池中调用现有存储 Controller 接口并映射结果。 |
| `HELLO`、`AUTH`、`STATS`、`CLIENT_LIST`、`CLIENT_KILL` 及其他未列命令 | 当前适配器返回 `UNSUPPORTED`，需要正式执行层实现。 |

该适配器的工作池为 4 个线程，最多排队 1024 个任务；队列满时返回 `BUSY`。它直接等待存储 future 的做法仅存在于独立工作线程，不能迁移到 Reactor 线程。后续执行层应以本文件所列的请求、响应和回调契约为边界，再分别实现认证、CRUD、管理命令及存储错误映射。
