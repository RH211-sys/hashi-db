## 1. 实现范围与提交组成

二轮开发不能只按最后一个连接状态提交理解。本轮实际由以下两个提交共同构成：

- `f73b5a1b`：完成 OpenSSL TLS 传输、Linux 服务端装配、Reactor 生命周期和任务队列治理、传输接口低复制调整，以及网络正确性和压力测试目标。
- `5fd881a`：增加 `ConnectionActivityState` 三态请求处理状态，延后会话阶段检查，保存延迟协议错误，并补充 HELLO/AUTH/后续请求的顺序回归验证。

因此，本文件同时记录传输层、服务生命周期、Reactor、Connection、解析器、执行器和测试模块，而不是只记录最后一轮的连接队列修复。

## 2. 构建目标与传输接口

`project/net_level/CMakeLists.txt` 将网络构建拆为四个层次：

- `mydb_net_core`：协议、帧编解码、命令解析、会话和连接核心；
- `mydb_net_linux`：TCP、TLS、epoll、Reactor、接入器和服务端装配；
- `mydb_net_storage_bridge`：阶段性存储 Controller 桥接；
- `mydb_net`：完整网络服务的聚合接口。

这些目标继续使用 `EXCLUDE_FROM_ALL`，不改变根目录默认测试工程的构建边界。Linux 网络目标新增 `find_package(OpenSSL 1.1.1 REQUIRED)`，并链接 `OpenSSL::SSL` 和 `OpenSSL::Crypto`。

`project/net_level/transport/transport.h` 的写入接口改为 `std::span<const std::uint8_t>`，TCP 和 TLS 两种传输共同使用只读字节视图。Connection 仍只依赖 Transport 抽象，不感知具体的 OpenSSL 类型。

## 3. OpenSSL TLS 实现

### 3.1 共享上下文

`project/net_level/transport/tls_transport.h` 和 `tls_transport.cpp` 提供两个实现类型：

- `TlsServerContext`：使用 `TLS_server_method()` 创建服务端上下文，最低协议版本设置为 TLS 1.2，加载证书链和 PEM 私钥，并检查私钥与证书是否匹配；
- `TlsTransport`：接管已接受的底层 Transport，创建独立 SSL 会话并把底层 socket 绑定到该会话。

OpenSSL 类型隐藏在 PImpl 中，网络其他模块只看到 Transport 的统一操作。上下文由 NetworkServer 共享，单个连接只持有自己的 SSL 会话。

### 3.2 非阻塞握手和读写

`TlsTransport::handshake()` 通过 `SSL_accept()` 推进服务端握手。`read()` 使用 `SSL_read_ex()` 解密到明文输入缓冲，`write()` 使用 `SSL_write_ex()` 加密输出。

OpenSSL 的 `SSL_ERROR_WANT_READ` 和 `SSL_ERROR_WANT_WRITE` 被转换为 Transport 的等待方向。`events()` 返回当前期望的 Poller 事件，使一次非阻塞操作需要交叉等待时，Reactor 能在下一次合适事件到达后重试。

TLS 读取有独立的 `readRetryBuffer`、`readRetryBytes` 和 `readPending` 状态。重试期间缓冲地址和本次读取长度保持不变，避免第一次调用已经消耗部分底层状态后，第二次调用使用失效的临时缓冲。

### 3.3 关闭和资源所有权

`TlsTransport::close()` 释放 SSL 会话、清理读取重试状态，并关闭被接管的底层 socket。TLS 上下文由共享指针管理，保证活动连接结束前服务端上下文仍然有效。

## 4. 服务启动与立即停止

`ServerConfig` 新增 TLS 证书路径和私钥路径；`tlsRequired` 默认开启，`allowPlaintextForDevelopment` 和 `allowInsecureRemote` 默认关闭。

`NetworkServer::start()` 的检查顺序为：

1. 检查服务当前状态、执行器、连接上限、流水线上限和帧上限；
2. TLS 开启时检查证书路径和私钥路径，并创建 `TlsServerContext`；
3. TLS 关闭时检查是否显式允许明文，以及非回环监听是否显式允许远程明文；
4. 创建并启动 `ReactorGroup`；
5. 创建 Acceptor，接受连接后按配置包装为 `TlsTransport`，再交给 ReactorGroup；
6. 监听器启动成功后才把服务状态改为 `RUNNING`。

当 `reactorCount` 为零时，服务根据逻辑处理器数量自动选择 Reactor 数量，并限制在 16 个以内；显式配置时仍使用调用方提供的数量。

失败路径会按已创建资源的反向顺序停止服务，不把配置失败降级成明文运行。

`NetworkServer::stop()`、Controller 停止入口、`ReactorGroup::stop()` 和 `ConnectionRegistry::kill()` 统一为无参数立即停止或立即关闭。`ServerState::DRAINING`、排空标记和排空超时被移除；Reactor 停止时停止接收入队任务、唤醒事件线程、关闭全部连接、丢弃剩余任务并等待线程退出。

## 5. Reactor 队列与事件循环

### 5.1 有界任务队列

`project/net_level/reactor/reactor.cpp` 在 `Reactor::Impl` 中维护三类队列：

| 队列 | 用途 | 容量 |
| --- | --- | ---: |
| `inbox` | 通用跨线程任务 | 4096 |
| `controlInbox` | 接入、关闭和连接控制任务 | 256 |
| `completionInbox` | 业务完成结果回投 | 4096 |

`InboxKind` 区分三类入队动作。所有入队都在 `inboxMutex` 下完成，入队后调用 Poller 唤醒；事件线程取出任务后释放锁，再依次执行任务，避免任务执行期间持有队列锁。

完成队列满时，`connectionId` 被放入 `overflowConnections`，随后由事件线程调用关闭路径。这样不会让 Connection 永远停留在有在途请求但永远收不到结果的状态。停止过程中不再接受完成回投，剩余队列在事件线程退出前统一释放。

### 5.2 连接槽位和代际

`SlotRelease` 使用原子标记保证客户端槽位释放回调最多执行一次。接入任务因队列满而被丢弃、Connection 构造失败、正常关闭或 Reactor 关闭连接时，都可以安全触发同一个释放对象。

Reactor 为连接维护单调递增的 generation。完成回投同时携带连接标识和代际，连接被关闭或标识复用后，旧结果不能误投给新连接。

### 5.3 Poller 注册和事件刷新

Connection 增加 `pollerRegistered`，`refreshInterest()` 按当前 `interestEvents()` 结果执行添加、修改或移除：

- 事件集合为空时移除已注册连接；
- 未注册但重新需要事件时执行添加；
- 已注册连接只修改关注事件；
- Poller 操作失败时进入连接关闭路径。

TLS 握手单独处理读写事件；普通连接则根据读、写、挂断和待重试传输操作推进 Connection。`PendingTransportOperation` 和 `pendingTransportBytes` 使 OpenSSL 引起的交叉 I/O 等待能够在下一次合适事件中继续。

## 6. Connection 的请求流水线

### 6.1 三态和队列门控

`project/net_level/common/net_types.h` 新增 `ConnectionActivityState`，`connection.h` 增加 `activityState` 和 `PendingProtocolError`。

`activeRequestId` 只负责异步完成结果关联；`activityState` 负责派发门控：

- `IDLE` 时允许出队；
- 进入 `PROCESSING` 后只保留后续请求；
- `DISCONNECTED` 后禁止派发并允许清理消息。

`processInput()` 计算流水线深度时，把 `PROCESSING` 状态视为一个在途请求，再加上 `pipeline` 中的等待数量。达到 `maxPipelineRequests` 或存在待处理协议错误时暂停读取。

### 6.2 阶段检查和异步完成

`handleFrame()` 只负责把完整帧解析为请求、附加对端信息并入队；HELLO 已完成、AUTH 需要 HELLO 等会话阶段检查移到 `dispatchNext()`。

出队时重新取得 `session.getPrincipal()`，然后检查 HELLO 重复提交和 `session.canExecute()`。允许执行的请求再保存 HELLO 能力位或 AUTH 主体，设置在途字段并提交给 `ICommandExecutor`。

`complete()` 校验连接标识和请求标识，先推进 HELLO/AUTH 成功后的会话阶段，再构造响应并加入 `outputQueue`。普通响应完成后恢复 `IDLE` 并继续处理输入；终止类响应、协议错误和不可恢复编码错误进入 `DISCONNECTED`。

### 6.3 延迟协议错误

解析失败时，`handleFrame()` 只保存 `PendingProtocolError` 并暂停继续接收。`dispatchNext()` 只有在 `pipeline` 为空且没有在途请求时才取出该错误，调用 `queueProtocolError()`。

错误响应入队后才清理等待队列、未解析输入并设置关闭标记。该清理与前序请求处理期间的普通等待路径分开，保证后续坏帧不会清除 HELLO 的完成结果。

### 6.4 半关闭

`onPeerHalfClose()` 设置 `peerClosed`、暂停新的读取并进入关闭中的传输生命周期，但不清空 `pipeline`。若仍存在已解析请求，Connection 会继续排空；只有队列、在途请求和延迟协议错误都处理完后，才转为 `DISCONNECTED` 并最终关闭。

`onWritable()` 和 TLS 重试读路径只在请求处理状态已经断开时清理剩余输入，避免半关闭排空时误删已接收数据。

## 7. 解析和执行层的低复制调整

`CommandParser::parse()` 改为接收 `Frame&&`，校验通过后把 `frame.fields` 移动到 `CommandRequest`，减少完整帧到结构化请求之间的字段复制。

`StorageControllerExecutor::execute()` 在把请求移动给 WorkerPool 前先保存 `connectionId` 和 `requestId`。WorkerPool 满时，执行器仍可构造带有正确关联标识的 `BUSY` 响应；不会因为请求已经移动而丢失响应关联信息。

## 8. 测试模块与覆盖范围

### 8.1 测试构建

`test/memo_test/net_test/CMakeLists.txt` 新增或装配三个网络测试目标：

- `net_test`：既有基础网络测试目标；
- `net_correctness_test`：协议、Connection 和 Linux 服务集成正确性测试；
- `net_stress_test`：连续请求流水线压力测试。

`net_test_support.h` 提供 `MemoryTransport`、`RecordingExecutor`、帧构造、编码和断言辅助，使 Connection 测试不必依赖真实 socket。

### 8.2 正确性测试

`net_correctness_test.cpp` 的最终覆盖包括：

- FrameCodec 的逐字节分片、粘包帧和二进制字段；
- CommandParser 的字段类型、缺失字段、重复字段、未知字段和边界校验；
- Session 的协商、认证和权限判断；
- 同连接请求顺序及最多一个在途请求；
- HELLO 失败后排队 AUTH/业务请求的顺序拒绝；
- 在途请求之后出现坏帧时的延迟协议错误；
- 对端半关闭后的请求和响应排空；
- 非法帧错误响应；
- Linux epoll 唤醒和回环服务收发；
- 默认 TLS 配置、缺失证书、未授权明文和远程明文策略。

其中，`5fd881a` 在 `f73b5a1b` 已有的基础测试上补充了排队协商、延迟错误和半关闭场景，使本轮用户报告的正确性结果覆盖最终连接状态实现。

### 8.3 压力测试

`net_stress_test.cpp` 使用 `MemoryTransport` 连续注入 100000 个 PING 请求，执行器只保留一个待完成请求；每次完成后推进 Connection 和有限写预算。测试检查所有请求都到达执行器、没有残留完成回调、输出响应数量一致、请求标识和响应顺序一致。

本轮不修改网络层与存储层之间的 CRUD 映射。当前 `StorageControllerExecutor` 中，`DELETE_DATA` 仍调用存储 Controller 的删除接口；GET、ADD、UPDATE 的网络值类型编解码和完整存储映射仍不属于本轮交付。

本轮也没有完成 TLS 客户端证书认证、真实认证提供者、ACL、Windows 网络服务端或正式网络指标聚合。OpenSSL TLS 服务端传输、Linux Reactor 和测试目标已经纳入网络层实现，但生产证书材料和运行环境仍由部署配置提供。
