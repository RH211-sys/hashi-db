术语说明：

- TLS 是传输层安全协议，用于加密连接数据并验证服务端身份；OpenSSL 是本轮使用的 TLS 实现库。
- Transport 是 Connection 使用的统一非阻塞传输接口，用于屏蔽普通 TCP 与 TLS 的差异。
- Acceptor 负责监听端点并接收新连接；ReactorGroup 管理多个 Reactor，并为每个新连接确定固定归属。
- Reactor 是独占处理一组连接事件的单线程事件循环；Poller 是向 Reactor 报告 socket 就绪事件的轮询器。
- Connection 是单个客户端连接的状态持有者；执行器是网络请求与业务处理之间的异步边界。
- 完成回投是业务处理结束后，将结果交回连接所属 Reactor 的过程；eventfd 是 Linux 上用于唤醒等待中事件循环的计数器文件描述符。
- HELLO 用于协议版本与特性协商；AUTH 用于身份认证。

## 1. 本轮范围

本轮二次开发由两个连续提交共同组成：`f73b5a1b` 完成网络服务端的 TLS、Reactor、连接传输和测试基础设施；`5fd881a` 在此基础上增加连接请求处理的中间状态，修复 HELLO（协议协商命令）未完成时后续请求被提前拒绝以及前序响应被后续错误清除的问题。

本轮不是单一的连接队列修复，也不是单独的测试补丁，而是一次从传输层到连接调度、从服务生命周期到验收目标的网络层二次实现。核心目标有三类：

1. 让生产连接具备非阻塞 TLS 能力，并保证 TLS 的配置失败不会静默降级为明文。
2. 让 Reactor 能够安全地承载跨线程任务、完成回投和连接关闭。
3. 让同一连接在协商、认证、业务请求连续到达时保持严格顺序和可恢复的错误语义。

## 2. 加密传输与安全边界

网络服务默认使用 TLS。证书链和私钥在服务启动阶段统一加载并校验，只有上下文创建成功后服务才允许进入运行状态；证书缺失、私钥不可用或密钥不匹配都会使启动失败。

TLS 连接建立在已有非阻塞 socket 传输之上。握手、读取和写入都被视为可以暂时等待的传输动作：当 OpenSSL 要求等待读或等待写时，传输层把等待方向交给 Poller，而不是阻塞 Reactor 线程。这样，TLS 的加密细节被隐藏在 Transport 抽象之后，Connection 只处理统一的握手、读取、写入和关闭结果。

明文不是默认后备路径。只有显式开启开发明文许可时才能关闭 TLS；监听回环地址以外的明文还需要额外的远程不安全许可。该边界避免证书配置错误时服务悄然以明文启动。

## 3. 服务生命周期与停服语义

本轮将服务停止统一为立即停止：停止监听、停止接收新的 Reactor 任务、关闭已有连接、清理事件循环中的剩余任务，然后退出服务线程。服务状态不再包含“排空中”这一中间阶段，也不再等待一个停服排空期限。

立即停服与客户端半关闭是两个不同语义：服务主动停止时优先保证进程级资源快速回收；客户端半关闭时，连接仍可以对已经接收的请求进行有序收尾。两者不能混用，否则服务停止会被慢业务或慢客户端拖住。

服务启动则遵循由外向内的校验顺序：先检查配置边界和安全策略，再创建共享 TLS 上下文，之后启动 Reactor 组和监听器，最后才进入运行状态。任一阶段失败都回收已经创建的前置资源，并保持服务没有半启动状态。

## 4. Reactor 任务与事件模型

每个 Reactor 只在线程内部访问自己的连接集合和 Poller；其他线程不直接操作连接，而是通过任务队列投递工作。任务按用途分为三类：通用任务、控制任务和业务完成回投。三类队列分别设置容量上限，避免某一种任务挤占所有事件循环资源。

任务入队后通过 Poller 的唤醒能力打断等待，使 Reactor 及时处理跨线程任务。事件循环每轮先处理已入队任务，再处理因完成回投溢出而需要关闭的连接，最后进入 socket 事件等待。

### 连接并发与请求接收

并发分配的单位是连接，而不是单个请求。新连接接入后，ReactorGroup 选择一个 Reactor 并将该连接固定交由它管理；该 Reactor 创建并持有对应的 Connection。客户端之后发送的请求都沿着这条连接进入同一个 Reactor，不会在请求之间重新选择 Reactor，也不需要按客户端 IP 查找归属。

一个 Reactor 可以通过 Poller 同时等待许多连接的 I/O 就绪事件，但由自己的事件循环线程逐个处理事件和连接状态。多个 Reactor 的事件循环可以并行运行；同一个 Reactor 内的连接状态修改仍然串行。连接收到数据后，由对应 Connection 解析完整请求并按接收顺序放入该连接的等待队列；只有当前没有在途请求时，队首请求才会被交给执行器。这样不同连接可以并行推进业务，同一连接则保持请求和响应顺序。

### 业务执行与完成回投

Connection 派发请求时，会把请求和本次请求的完成回调交给业务执行器。执行器决定立即完成，还是将工作交给工作线程。连接在确定归属 Reactor 时已经关联了专属的完成回投路径；它只指向该连接所属的 Reactor，并携带定位原连接所需的信息，不是保存所有 Reactor 的全局中转站。请求完成回调复用这条路径，因此业务线程无须访问 ReactorGroup，也无须自行查找目标 Reactor。

业务完成后，完成回调将结果放进目标 Reactor 的完成队列，并唤醒该 Reactor。完成队列是每个 Reactor 共享的：同一 Reactor 管理的多个连接可以由不同工作线程并发完成，入队由队列同步机制保护；唤醒信号只负责提醒事件循环，真正的结果保存在队列中。目标 Reactor 取出结果后，按连接标识在自己的连接集合中定位 Connection，并检查连接仍有效且代际匹配，再由该连接关联请求、更新状态并准备响应发送。已经关闭的连接收到迟到结果时，结果会被丢弃。

回投路径不经过 ReactorGroup。ReactorGroup 只在新连接接入时分配归属并管理各 Reactor 的生命周期；正常业务完成直接返回原 Reactor。不同连接的完成结果可以并发产生，但只由各自所属 Reactor 的事件循环串行消费；同一连接最多只有一个业务请求在途，因此其响应仍按请求接收顺序返回。队列容量耗尽时按完成队列的失败语义关闭对应连接，避免连接无限期等待结果。

完成回投具有更严格的失败语义：完成队列满时不能让连接继续停留在“等待业务结果”的状态，因此对应连接会被标记并在 Reactor 线程中关闭。通用任务和控制任务超过容量时则按队列类型拒绝后续任务。连接槽位的释放使用一次性语义，避免接入任务被丢弃、连接构造失败和连接正常关闭之间发生重复释放。

连接的事件关注集合随当前传输状态变化。普通读写、TLS 握手以及 TLS 读写产生的交叉等待都由同一套事件刷新机制处理；连接不再需要事件时从 Poller 移除，重新需要事件时再注册，避免重复注册或保留无效事件。

## 5. 单连接有序处理

连接接收模块先把完整帧转换为结构化请求，再放入该连接的等待队列。只要当前请求仍在处理，后续请求就保持接收顺序等待，不能直接进入执行器。

本轮新增独立的请求处理三态：

- **空闲**：没有业务请求在执行，可以取出队首请求；
- **正在处理**：已经派发一个请求，后续请求只进入等待队列；
- **断开**：连接不再接受或执行新请求，允许清理消息和资源。

该三态与连接的协议阶段、TLS 阶段和关闭阶段分离。协议阶段决定请求能否执行；请求处理状态决定何时有资格检查该请求。这样，连接可以同时处于“等待 HELLO 结果”和“正在处理当前请求”的组合状态，而不必用一个状态值承担两个维度。

空闲时每次只取队首请求，完成后恢复空闲并继续下一项。由此保证接收顺序、派发顺序和响应顺序一致，同时保证同一连接最多只有一个业务请求进入执行层。

## 6. 协商、认证与协议错误

HELLO 完成前收到的 AUTH（身份认证命令）和后续请求不会被接收模块直接判定为非法，而是先进入等待队列。会话阶段检查被推迟到请求真正出队时：

1. HELLO 成功后，队首 AUTH 依据新的协商状态重新检查并可以派发；
2. AUTH 成功后，后续数据请求依据新的认证主体继续检查；
3. HELLO 失败后，队首 AUTH 和后续业务请求按原顺序得到协议层拒绝，不会提交给业务执行器。

排队请求的主体信息也在派发时取得，避免认证完成前保存的旧主体污染后续请求。

协议解析错误不立即抢占更早请求。错误先被保存，并暂停新的输入；只要仍有在途请求或等待请求，就先完成这些请求。队列排空后才生成错误响应并进入断开状态。这样，后续坏帧不会抹掉更早的 HELLO 响应，也不会改变已经接收请求的响应顺序。

## 7. 半关闭、断开与资源回收

对端半关闭只表示服务端不能继续等待新的输入，不表示已经接收的请求无效。连接会停止新的读取，但保留已经解析的请求和响应，继续排空流水线。只有请求处理回到空闲、等待队列排空且没有延迟协议错误时，连接才进入断开并完成关闭。

真正的断开包括传输失败、不可恢复协议错误、终止类响应、服务主动关闭和资源回收。进入断开状态后，才清理等待队列、未解析输入、输出缓冲和在途关联信息。迟到的业务完成结果在连接已断开后不再改变连接状态。

## 8. 容量、复制与并发边界

网络层对连接数、单连接流水线、单帧大小、输入缓冲、输出缓冲和 Reactor 各类任务队列分别设置上限。达到上限时通过暂停读取、拒绝任务或关闭无法继续关联结果的连接来保护事件循环。

帧解析阶段将完整帧的字段所有权直接转移给结构化请求，传输写入使用只读字节视图，减少不必要的数据复制。存储执行器在把请求转移给工作队列前保存连接标识和请求标识，以便队列满时仍能生成可关联的忙响应。

同一连接的状态和缓冲只由所属 Reactor 线程访问；业务执行可以在执行器的工作线程中进行，但完成结果必须回投原 Reactor。跨线程边界只传递任务和结果，不让业务线程直接触碰连接对象。

## 10. 并发连接到完成回投的完整流程

先区分两种“并发”：

- **不同连接之间**：可以并发处理。多个 Reactor 各自运行事件循环；业务执行器也可以把不同连接的请求交给多个工作线程。
- **同一连接之内**：客户端可以连续发送多个请求，服务端会接收并排队；但同一时刻只派发一个请求，保证按请求顺序处理和响应。比如 HELLO 还没完成时，AUTH 和 GET 可以先到达、排队，但不会越过 HELLO 执行。

**完整流程**

1. **连接分配**：新连接接入后，ReactorGroup 选择一个 Reactor 管理它，并创建对应的 Connection。Connection 对应一条连接，不是每个请求创建一个。
2. **等待和接收**：Poller 监听连接的读写就绪事件；Reactor 的事件循环被唤醒后，由对应 Connection 读取数据、解析完整请求，并按接收顺序放进该连接的等待队列。
3. **按序派发**：连接处于空闲状态时，取队首请求，检查当前协议和会话阶段，再把请求及本次请求的完成回调交给业务执行器。连接转为“正在处理”后，后续请求继续排队。
4. **业务执行**：执行器可以立即完成请求，也可以交由工作线程处理。不同连接的业务可以并行执行；同一连接的后续请求仍等待前一个请求完成。
5. **完成回投**：业务完成后，完成回调沿着连接预先关联的路径，把结果放进**原 Reactor 的完成队列**，并唤醒它。队列由同一 Reactor 管理的多个连接共享，能够接收多个工作线程并发提交的完成结果。`eventfd` 在这里相当于唤醒事件循环的门铃；结果本身保存在队列里。
6. **关联连接**：Reactor 取出完成结果后，在自己的连接集合中按连接标识找到 Connection，并检查连接仍有效、代际仍匹配。连接若已关闭，迟到的结果就会被丢弃。
7. **发送并继续**：Connection 处理完成结果、准备响应并恢复空闲，然后按序派发下一条等待请求。Poller 通知 Reactor 连接可写后，Reactor 继续发送响应。这样同一连接上的响应顺序与请求顺序一致。

关键点是：**ReactorGroup 只负责新连接的分配和 Reactor 生命周期管理；普通业务完成不回到 ReactorGroup，也不搜索所有 Reactor，而是直接回到连接原先所属的 Reactor。**
