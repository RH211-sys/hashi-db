## 1. 本地访问与客户端访问

原始想法：由于访问有两种方式——服务端本地处理和客户端处理——可以分两个网络任务队列，
本地任务队列优先级最高，不考虑饥饿。

评审结论：本地管理不属于网络 I/O，不经过 socket/网络队列；它直接调用同一 `IRequestHandler`，
使用 `source=LOCAL_ADMIN`。执行层为控制请求保留少量 admission 配额；如果需要优先级，采用带权轮转，
不做永久优先级，避免外部请求饿死。详见《架构设计》“本地管理与远程请求”。

## 2. 开源思路的本土化

- Redis：采用长度前缀、流水线、连接/输出限额和 fd 校准；不宣称 RESP 兼容。
- muduo：采用 Acceptor + Reactor、连接线程亲和和跨线程投递；不直接复制库的所有抽象。
- Dragonfly：采用连接终身绑定线程的思想；不采用 shard-per-core，因为当前存储层仍是共享缓存表、
  写线程和磁盘线程模型。

## 3. 当前保留的方向

1. 单机优先，分布式只在协议版本、特性位、request ID 和 handler 边界留扩展点；
2. 先确保拆包/粘包、过载、断连、关闭和错误语义，再追求 ET、io_uring 或更激进的分片；
3. 观测先行：记录 loop lag、队列深度、缓冲字节和 P99/P999，不能只报 QPS；
4. 网络层只连接命令/执行层，不直接摸存储私有结构。

## 4. 明确不采用的直觉方案

- 每个连接一个线程：线程资源和调度成本随连接数线性爆炸；
- Reactor 里同步 `future.get()`：慢磁盘会占住 I/O 线程；
- 无界本地/外部队列：短期吞吐看似增加，最终会以 RSS 爆炸和长尾偿还；
- 直接把 cereal 二进制当 wire：内部持久化格式不等于可演进网络协议；
- 为了“百万连接”一开始引入 Dragonfly 式分片：会推翻存储层已验证的并发模型。

## 5. 待评审问题

1. 是否接受首版 Linux 服务端、Windows 只做 core/协议测试；
2. `WireTypeRegistry` 首批稳定类型是仅 bytes/string/int64，还是包含 double/bool；
3. TLS 是默认强制，还是仅非回环监听强制；
4. `max_frame_bytes`、连接数和 pipeline 默认值的第一轮压测参数；
5. 管理层/执行层的认证、ACL、统计和踢出接口名称。

这些问题不影响先完成文档评审，但会影响阶段 0 的接口签名。
