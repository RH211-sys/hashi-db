# 总结

网络层的核心任务，是把客户端发来的网络字节，安全、有序地转成系统能处理的命令，再把结果送回客户端。它负责连接和通信，不负责缓存数据本身。

整体可以理解为：

```
客户端
  ↓
网络 Controller（对外服务入口）
  ↓
服务端接收连接并分配到 Reactor
  ↓
连接处理：协议帧 → 命令解析 → 会话与权限检查
  ↓
命令执行接口
  ↓
业务执行层 / 存储层
  ↓
结果返回原连接
```

核心设计思路有几条：

1. **网络接入和业务执行分开**
   网络层负责连接、协议、请求解析和响应发送；业务层负责命令语义以及如何调用存储。网络层会有自己的命令解析模块，不会把原始网络数据直接交给存储层。
2. **对外有统一入口，内部按职责分层**
   外部通过网络层的 Controller 管理服务的启动、停止和配置。Controller 负责组织内部模块，连接接收、事件循环、连接状态和协议处理各自有清楚边界。它与现有的存储层 Controller 是两个不同职责的入口。
3. **连接归属固定，避免多线程争抢**
   每个连接由一个事件循环负责。其他线程需要返回结果或关闭连接时，把任务交回连接所属的事件循环处理。这样连接状态和读写顺序更容易保持一致，也能减少并发问题。
4. **网络等待不阻塞业务执行**
   网络层提交请求后继续处理其他连接，不等待存储结果。业务完成后再把结果交回对应连接。一个连接内的命令和响应按接收顺序处理，不同连接之间则可以并发。
5. **协议与存储格式解耦**
   客户端使用明确、可版本演进的网络协议；网络数据类型由网络类型编解码规则管理。存储层的内部序列化格式只服务于持久化，不直接作为网络协议暴露。
6. **过载时有边界，不靠无限排队**
   连接数、单帧大小、每连接等待请求数、响应缓冲和全局在途请求都需要限制。达到容量时暂停读取或拒绝请求，避免慢客户端或突发流量把服务内存拖垮。
7. **安全和平台能力放在边界层处理**
   服务默认要求 TLS，连接在进入业务命令阶段前经过协议协商和认证状态检查。首发服务端面向 Linux；协议和核心逻辑尽量不依赖具体平台，给以后支持其他平台留下空间。

目前设计中的 `StorageControllerExecutor` 是一个**阶段测试用的临时桥接**：它让网络请求暂时能连接现有存储 Controller，方便验证端到端流程。后续正式命令执行层完成后，这个桥接会被替换；网络协议解析和业务执行仍保持分离。
