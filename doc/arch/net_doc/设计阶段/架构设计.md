# 网络层架构设计

## 1. 总体结构

```text
                         管理层
                  启停 / 配置 / 认证 / ACL
                            │
                    ┌───────▼────────┐
TCP/TLS ──► Acceptor│  NetworkServer │◄── 本地管理入口（不走 socket）
                    └───────┬────────┘
                            │ round-robin / least-connections
          ┌─────────────────┼─────────────────┐
          ▼                 ▼                 ▼
      Reactor 0         Reactor 1         Reactor N-1
      epoll/eventfd     epoll/eventfd     epoll/eventfd
      Connections       Connections       Connections
          │                 │                 │
          └─────────────────┼─────────────────┘
                            │ IRequestHandler::handle(req, completion)
                     命令解析层 / 执行层
                            │ callback async API
                         Controller
                 读池 / 写线程 / 磁盘线程
```

核心不变量：

1. `Connection` 创建后固定归属一个 Reactor；
2. 只有 owner Reactor 能读写 socket、修改 epoll interest、改变连接状态和输出队列；
3. 其它线程只能向 owner Reactor 的有界 inbox 投递消息并写 `eventfd` 唤醒；
4. I/O 线程不等待业务完成，业务线程不直接触碰 Connection；
5. fd 不是连接身份，异步完成用单调递增的 `ConnectionId` + `weak_ptr`/代际校验。

## 2. 组件职责

| 组件 | 职责 |
|---|---|
| `NetworkServer` | 生命周期、配置校验、ReactorGroup、停止编排 |
| `Acceptor` | `accept4` 到 `EAGAIN`、限流、socket 选项、连接分派 |
| `Reactor` | `epoll_wait`、任务 inbox、timer tick、连接事件分发 |
| `Poller` | 对 epoll 的薄封装；为测试 fake poller/未来 IOCP 留接口 |
| `Connection` | 状态机、Transport、Buffer、FrameCodec、流水线、背压 |
| `Transport` | plain TCP 或 TLS 的非阻塞 read/write/handshake |
| `FrameCodec` | 增量解析固定头与 body；只理解帧，不执行命令 |
| `Session` | 协议版本、认证主体、权限、client name、最后活动时间 |
| `ConnectionRegistry` | 跨 Reactor 的只读快照和按 ID 关闭 |
| `IRequestHandler` | 网络层到命令/执行层的唯一接口 |
| `NetMetrics` | 线程内计数，定期聚合，避免热路径全局锁 |

建议目录（编码阶段创建）：

```text
project/net_level/
  common/          # Endpoint、错误、ConnectionId、字节序
  protocol/        # Frame、FrameCodec、Encoder、协议常量
  reactor/         # Poller、EpollPoller、Reactor、ReactorGroup、TimerWheel
  transport/       # TcpTransport、TlsTransport
  server/          # Acceptor、Connection、NetworkServer、Registry
  include/         # IRequestHandler 等稳定边界（也可并入 common）
```

## 3. 线程与分派模型

### 3.1 Acceptor

首版使用一个监听 socket 和一个 Acceptor（可由 Reactor 0 承担）：

1. `accept4(SOCK_NONBLOCK | SOCK_CLOEXEC)` 循环到 `EAGAIN`；
2. 检查 `max_clients` 和全局连接内存预算；
3. 设置 `TCP_NODELAY`、`SO_KEEPALIVE`，按需设置 keepalive 参数；
4. 选择连接数较少的 Reactor，向其 inbox 投递 `AddConnection`；
5. 超限时尽量返回短错误帧并关闭，不能创建完整 Connection 后才检查。

只有压测证明 accept 成为瓶颈后，才增加 `SO_REUSEPORT` 多监听者模式。

### 3.2 Reactor

每个 Reactor 一个线程、一个 epoll fd、一个 eventfd 和一个粗粒度时间轮。一次循环：

```text
drain inbox（有条数预算）
  -> epoll_wait
  -> 处理 I/O 事件（每连接有读/写预算）
  -> timer tick（过期 bucket 有条数预算）
  -> 发布线程本地指标
```

初始公平预算建议：单连接单轮最多读 64 KiB/解析 32 帧，最多写 256 KiB；
预算耗尽但仍可能可读/可写时，把连接排入 Reactor 本地 ready queue，避免等下一次边沿通知。
数值由压测调优，但“有预算”是架构约束。

### 3.3 业务完成回投

`IRequestHandler` 的 completion 可在任意存储线程调用。completion 只捕获：

- `ConnectionId`；
- `request_id`；
- owner Reactor 索引；
- 已编码或可移动的响应对象；
- 连接弱引用/代际。

它把 `CompleteRequest` 投到 owner inbox 并唤醒 eventfd。Reactor 收到后再次校验连接仍存在且请求仍匹配，
才入输出队列、推进下一条请求。客户端已断开时直接丢弃网络响应，不撤销已提交的存储操作。

## 4. Connection 状态机

```text
ACCEPTED
   ├─ TLS required ─► TLS_HANDSHAKE ─┐
   └─ plain (explicit dev/test only) ─┤
                                     ▼
                         WAIT_HELLO
                               ▼
                          WAIT_AUTH
                         ┌─────┴─────┐
                         ▼           ▼
                       READY       CLOSING
                         │           │
                  read/dispatch/write│
                         └─────► CLOSED
```

- 默认策略要求 TLS。明文 transport 只有在显式开发/测试配置下创建；非回环明文还需要单独的 insecure 许可，不能由缺少证书自动触发降级；
- `WAIT_HELLO`：只接受 HELLO/PING/QUIT；协商版本和特性；
- `WAIT_AUTH`：只接受 AUTH/PING/QUIT；超时或失败过多关闭；
- `READY`：按 ACL 接受业务命令；同连接仅一个业务请求在执行；
- `CLOSING`：停止读取；若是优雅错误关闭，先尝试写完小型错误/QUIT 响应；硬错误立即释放；
- 对端 FIN：停止接收新请求，可写完已完成响应后关闭；协议残帧视为截断错误。

TLS transport 把 `SSL_ERROR_WANT_READ/WANT_WRITE` 映射为 interest 变化，不能在握手或读写中阻塞。

## 5. 请求生命周期

```text
EPOLLIN
  -> read 到输入 Buffer
  -> FrameCodec 增量解析（0..N 个完整帧）
  -> 帧级校验、会话/ACL 校验
  -> 放入每连接 pipeline（有界）
  -> 若无 active request，dispatch 首项
  -> handler 异步调用 Controller
  -> 存储线程 completion
  -> owner Reactor inbox/eventfd
  -> 编码响应并加入输出 Buffer
  -> EPOLLOUT 写到 EAGAIN/预算
  -> active 清空，dispatch 下一项
```

严格串行的是“单连接的业务 dispatch”，不是整个服务。这样既保留流水线减少 RTT，又保证同连接读写依赖顺序。

## 6. 跨层接口

网络层不包含 `controller.h`。目标接口示意：

```cpp
struct RequestContext {
    std::uint64_t connectionId;
    std::uint64_t requestId;
    Principal principal;
    Endpoint peer;
};

using Completion = std::function<void(CommandResponse)>;

class IRequestHandler {
public:
    virtual ~IRequestHandler() = default;
    virtual void handle(RequestContext context,
                        CommandRequest request,
                        Completion completion) = 0;
};
```

执行层负责 opcode/body 到 Controller 的映射及错误码翻译。网络层只处理通用的协议、认证状态和传输错误。

### 6.1 Controller 前置适配

C++20 `std::future` 没有标准 `then`。以下做法都禁止：

- Reactor 中 `future.get()`；
- Reactor 定时轮询 `wait_for(0)`；
- 每个请求创建一个等待线程；
- 把 future 放进无界“等待池”。

目标是 Controller/Cache 先提供 callback 异步 API，现有 future API 用 promise 包装 callback，以保持测试兼容：

```cpp
void asyncSelData(std::string key, SelCallback done);
std::future<SelResult> selData(const std::string& key); // 兼容包装
```

还需将 `SelResult` 扩展为至少包含 `typeName`；动态 ADD/UPDATE 接口接收运行时 `typeName + any + dataSize`。

### 6.2 类型编解码边界

磁盘 cereal 格式是内部持久化格式，不应默认为跨语言 wire format。增加 `WireTypeRegistry`。它是网络 wire 类型注册表：把协议中的稳定 `type_name` 映射到经过显式注册的编解码器，负责运行时类型安全和版本演进，**不是** `std::any` 的反射器，也不直接复用 cereal 磁盘格式：

```text
typeName -> decode(wireVersion, bytes) -> any
         -> encode(wireVersion, any)   -> bytes
         -> estimateSize(any)          -> size
```

每个注册项至少包含：规范化类型名、wire 版本、编码/解码函数、最大编码长度和可选的类型校验函数。注册表在服务启动时冻结，避免请求热路径修改全局类型状态。首批注册 `bytes/string/int64` 等稳定类型；业务自定义类型必须显式注册 wire codec。请求携带未注册类型时返回 `TYPE_NOT_REGISTERED`，网络层不写 `if (type == ...)` 分支。

## 7. 背压与过载

| 层级 | 触发 | 动作 |
|---|---|---|
| 连接数 | 达 `max_clients` | 拒绝新连接 |
| 单帧 | 声明长度超 `max_frame_bytes` | 返回错误并关闭 |
| 输入缓冲 | 未完成帧持续增长/超时 | 关闭慢速或畸形连接 |
| pipeline | 达请求数/字节上限 | 暂停 `EPOLLIN`，不继续解析 |
| 全局在途 | 达 `max_inflight_requests` | 已解析请求返回 BUSY；新读暂停 |
| 输出高水位 | `>= high` | 关闭该连接 `EPOLLIN` |
| 输出低水位 | `<= low` | 恢复 `EPOLLIN` |
| 输出硬上限 | `>= hard` | 记录 slow-consumer 并关闭 |
| Reactor inbox | 达硬上限 | 业务响应可丢弃并关闭对应连接；控制消息预留容量 |

控制消息（stop/close/add-connection）使用预留槽或独立小队列，不能被普通 completion 填满。
高/低水位采用滞回，避免频繁开关读事件。

## 8. 本地管理与远程请求

原始设想中的“本地任务队列优先于外部网络队列”不放在网络层实现：

1. 本地管理本来就没有 socket I/O，不应绕一圈进入 Reactor；
2. 无条件最高优先级会在本地任务持续到来时饿死外部请求；
3. 真正需要保护的是执行层容量，而不是网络读写顺序。

本地 CLI/管理器直接调用同一 `IRequestHandler`，携带 `source=LOCAL_ADMIN` 和已认证管理员身份。
执行层为控制请求预留少量 admission 配额；如需优先级，使用带权轮转而不是永久抢占。

## 9. 超时与定时器

每个 Reactor 使用秒级分桶时间轮，Connection 只保存 deadline/所在 bucket，不为每连接创建系统定时器。

- TLS 握手、HELLO、AUTH、请求组装使用明确 deadline；
- idle timeout 是近似值，可晚一个 tick；
- 收到有效帧或成功写出数据更新最后活动时间；
- timer tick 每轮有扫描预算，避免大量同时过期形成延迟尖峰。

## 10. 关闭顺序

1. 管理层将服务置为 `DRAINING`；
2. 关闭 listener，不再接收连接；
3. Reactor 停止读取新业务请求，允许已提交请求完成；
4. 在宽限期内发送已有响应；
5. 超时后关闭剩余连接，使迟到 completion 因代际校验被丢弃；
6. 停止 Reactor 并 join；
7. 最后关闭 Controller/存储线程和日志线程。

析构顺序必须显式调用 `shutdown()`，不能依赖成员自然析构顺序猜测跨线程生命周期。

## 11. 可观测性

至少提供：

- `connections_active/accepted/rejected/closed`，按关闭原因分类；
- `bytes_in/out`、`frames_in/out`、协议错误、TLS/认证失败；
- 每 Reactor 连接数、epoll events、inbox 深度、loop lag；
- 全局/每连接在途数、pipeline 深度、输入输出缓冲字节；
- 按 opcode 的请求数、错误数、P50/P99/P999（直方图）；
- backpressure 次数、暂停读时长、slow-consumer 关闭数。

指标先在线程本地累加，低频聚合；日志只记录生命周期和异常，不逐条记录成功 CRUD。
