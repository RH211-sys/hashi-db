## 2. 已定方向

| 主题 | 决定 |
|---|---|
| 生产平台 | Linux 优先，`epoll` + 非阻塞 TCP；Windows 只保证纯协议单测，IOCP 后置 |
| 并发模型 | 1 个 Acceptor + N 个 Reactor；连接建立后终身绑定一个 Reactor |
| 事件模式 | 首版使用 level-triggered；每次读写有预算，必须处理到 `EAGAIN` 或预算耗尽 |
| 协议 | 自定义、二进制安全、长度前缀、24B 固定基础头；不宣称兼容 RESP |
| 请求顺序 | 同一连接严格按接收顺序执行和返回；跨连接并发 |
| 异步衔接 | I/O 线程绝不调用 `future.get()`；存储完成后回投所属 Reactor |
| 背压 | 连接、输入、流水线、输出、全局在途请求五级限额，所有队列有上限 |
| TLS | 默认强制；明文仅在显式开发/测试配置下允许，非回环明文还需单独放行 |
| 管理请求 | 本地管理直接进入命令/执行层，不混入“网络本地优先队列” |
| 分布式扩展 | 协议预留版本/特性/请求 ID；首版不实现路由、复制或一致性协议 |

## 3. 编码前置条件

当前存储层的模板 `addData/modData` 和 `SelResult{resCode, entity}` 不能完整承接网络请求；
`std::future` 也没有 C++20 标准续延能力。正式写网络层前必须先完成三项小范围接口适配：

1. 为 Controller 增加回调式异步入口，保留现有 future 接口作为兼容包装；
2. 查询结果补充 `typeName`（以及协议需要的 TTL 元信息）；
3. 增加运行时类型编解码注册表和动态 CRUD 入口，网络层不得硬编码业务类型。

具体契约见《架构设计》“跨层接口”和《可行性分析》“前置改造”。

## 4. 分阶段实施门槛

| 阶段 | 交付 | 进入下一阶段的条件 |
|---|---|---|
| 0. 接口适配 | 回调 API、运行时类型、结果元信息 | 原存储功能/性能测试无行为回归 |
| 1. 协议核心 | FrameCodec、Buffer、协议单测/模糊测试 | 拆包、粘包、畸形帧、大小端全通过 |
| 2. 单 Reactor | TCP、连接生命周期、CRUD 闭环 | I/O 线程无阻塞等待，断连无悬空回调 |
| 3. ReactorGroup | 多 I/O 线程、背压、超时、优雅关闭 | 压测下内存有界、无饥饿、无请求错序 |
| 4. 安全与管理 | TLS、认证、ACL、连接查询/踢出 | 安全用例与降级策略通过 |
| 5. 性能收尾 | 指标、基准、参数定型 | 达到《测试与验收》的分级目标 |

设计评审通过前，不进入阶段 0 的代码修改。
