# 网络层可行性分析

## 1. 结论

方案可行，但“先写 epoll server”不是可直接开工的状态。需要先完成存储层运行时接口适配，
再按协议、单 Reactor、多 Reactor、TLS/认证、压测顺序实施。首版目标是 Linux 长连接高并发，
不是跨平台网络抽象和百万连接承诺。

## 2. 平台选择

### 2.1 Linux 首发

- 使用 `epoll`、`accept4`、`eventfd`、非阻塞 socket；`EPOLLIN/EPOLLOUT/EPOLLERR/EPOLLRDHUP` 覆盖普通关闭与半关闭；
- `SO_REUSEADDR`、`TCP_NODELAY`、`SO_KEEPALIVE`；按需调节 keepalive；
- 启动时检查 `RLIMIT_NOFILE`，实际 `max_clients` 留出 listener、epoll、eventfd、日志和 TLS 资源。

### 2.2 Windows 处理

开发机是 Windows + VS2022，但当前文档不承诺 Windows 服务端使用 epoll。协议、codec、状态机、
fake poller 和 handler 单测应保持可编译；Windows 网络实现后置为 IOCP 适配层。公共头文件不得散落 Linux socket 类型。

## 3. 依赖策略

首版使用 POSIX socket + epoll + OpenSSL，业务层只依赖自有小型抽象。当前仓库没有 Boost/Asio/libevent 网络运行时依赖，
自定义协议和连接状态机也需要可控的 buffer/错误路径。OpenSSL 隔离在 `Transport`，明文构建必须仍可用。

建议 CMake 目标：

```text
mydb_net_core       # protocol/状态机/接口，不含平台 socket
mydb_net_linux      # epoll/socket/OpenSSL
mydb_net_tests      # codec/状态机/背压/虚拟 transport
```

Linux 使用 `Threads::Threads` 和 `OpenSSL::SSL/OpenSSL::Crypto`。网络目标应单独加入，不能把网络源文件无条件塞进旧存储测试目标。

## 4. 与存储层的兼容性风险

### 4.1 最大风险：future 阻塞

现有 Controller API 返回 `std::future`，网络 Reactor 不能 `.get()`。等待线程池或 `wait_for(0)` 都会制造额外队列和生命周期问题。

**必须改造**：存储层提供 callback completion 或可注入 executor 的异步入口，现有 future API 用兼容包装保留。

### 4.2 运行时类型

当前 `addData/modData` 是模板接口，网络收到的是字符串/字节，无法调用未知 `T`；当前 `SelResult` 也没有 typeName，
不能安全编码任意 `std::any`。

**必须改造**：建立 `WireTypeRegistry` 和动态 CRUD facade；自定义类型显式注册 wire codec，磁盘 cereal 仍是内部格式。

### 4.3 存储现有线程模型

网络层不新增业务线程池去包住 Controller。请求进入现有读池/写线程/磁盘线程，完成后回投 Reactor。
存储层已有 `AsyncResult` 的“只投递不等待”思想，应扩展为对外 completion。

## 5. 风险清单与缓解

| 风险 | 影响 | 缓解/门槛 |
|---|---|---|
| 完成回调晚于连接关闭 | UAF/错误响应到新连接 | ConnectionId+generation+weak_ptr；断连压测 |
| 输出队列无界 | RSS 爆炸、慢客户端拖垮服务 | high/low/hard 水位；slow-consumer 测试 |
| handler 返回慢 | pipeline 堆积、请求超时 | 全局 in-flight 上限；BUSY/暂停读取 |
| callback 未兑现 | 客户端永久等待 | handler 契约“一次且仅一次”；超时 watchdog |
| TLS WANT_READ/WANT_WRITE 错 | 握手卡死/忙循环 | Transport 状态机 + fake TLS + 边界测试 |
| epoll 预算不当 | 热点连接饿死其它连接 | read/write/frame/inbox 预算和 loop-lag 指标 |
| fd 复用 | 旧完成写入新连接 | 不以 fd 为身份，generation 校验 |
| 长度解析溢出 | 崩溃或超额分配 | 先校验 `uint32` 长度与乘法，fuzz |
| 认证日志泄密/刷爆 | 安全与磁盘问题 | 脱敏、限频、聚合摘要 |
| 停机顺序错误 | 丢响应/悬挂线程 | 先 drain 网络，再停存储，显式 shutdown |
| 误称 RESP 兼容 | 客户端行为错误 | 文档明确自定义协议；另做 adapter |

## 6. 性能可行性估算

连接内存至少包括 Connection、输入/输出 buffer、pipeline 元数据、TLS 状态、epoll/eventfd、
内核 socket buffer 和 allocator 碎片；必须实测空闲、半包、满输出三种状态。

缓存命中时，解析、编码、syscall、TLS 和 Reactor 调度是主成本；缓存 miss 时，现有磁盘单线程可能成为主瓶颈；
大 payload 的复制/编码/输出排队是另一瓶颈。网络层报告不得把存储裸接口的 80 万 QPS 直接等同于端到端 QPS。

## 7. 实施可行性分级

| 级别 | 内容 | 判断 |
|---|---|---|
| P0 | FrameCodec + fake transport + core 状态机 | 立即可做，无外部依赖 |
| P1 | Linux plain TCP 单 Reactor + PING/HELLO | 可做，验证事件循环 |
| P2 | Controller callback bridge + CRUD | 依赖前置接口适配 |
| P3 | ReactorGroup + 背压 + 管理踢出 | 可做，重点是生命周期 |
| P4 | OpenSSL TLS + AUTH/ACL | 可做，需要证书与安全用例 |
| P5 | 复制/路由/多键事务 | 不属于首版，另立设计 |

## 8. 不应提前承诺

1. “支持 Redis 客户端”——协议和命令语义尚未兼容；
2. “百万级并发”——缺少目标硬件、fd、TLS、payload 和连接内存数据；
3. “请求一定执行一次”——客户端断连后的提交确认语义还需命令层定义；
4. “TLS 开启即安全”——证书验证、密码哈希、ACL、限频和默认值同样是安全面；
5. “多线程等于多核存储”——当前存储瓶颈仍可能在单磁盘线程。
