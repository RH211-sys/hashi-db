# 网络层测试与验收

## 1. 测试原则

网络层测试必须把协议、连接、调度、存储、TLS 和资源上限分开测，再做端到端压测。
每次性能报告固定记录：硬件/内核、编译模式、I/O 线程数、TLS、payload、连接数、命中率、
QPS、P50/P99/P999、CPU、RSS、错误率和存储队列深度。

## 2. 单元测试

### 2.1 FrameCodec

- 固定头 24B：一次完整、逐字节、随机分片；
- body：空 body、1B、边界值、包含 0/CRLF/非 ASCII 的 bytes；
- 粘包：1 次读 2/100 个 frame；
- 长度：`0`、`max_frame_bytes`、`max+1`、u32 最大值、header+body 加法溢出；
- magic/version/flags/header_len/reserved 错误；
- 未知 opcode、重复字段、缺少必填字段、嵌套深度超限；
- 每个非法输入都应有确定结果：返回错误、丢弃剩余输入或关闭，不得进入执行层。

### 2.2 Connection 状态机

- plain/TLS 两条握手路径；
- WAIT_HELLO、WAIT_AUTH、READY 下命令白名单；
- 认证成功、失败、超时、失败次数上限；
- pipeline 顺序、重复 request_id、响应序列门；
- FIN、RST、半包关闭、输出硬限、管理踢出；
- fd 复用模拟：旧 completion 不得写入新连接。

### 2.3 背压与定时器

- 输入高水位暂停读、恢复读的滞回；
- pipeline 和全局 in-flight 达限返回 BUSY 或暂停读；
- 慢客户端输出 hard limit 关闭；
- timer wheel 迟到一个 tick 可接受，不能漏掉 deadline；
- stop/close 控制消息在普通 completion 填满时仍能执行。

所有 core 测试使用 fake poller、fake clock、fake transport，避免单测依赖 Linux epoll。

## 3. 协议模糊测试

对 FrameCodec 提供字节流 fuzz target，要求：

1. 任意输入在资源上限内终止；
2. 不崩溃、不死循环、不超额分配、不触发未定义行为；
3. 解析器输出的 frame 满足长度/字段不变量；
4. 解析错误后状态可关闭或安全丢弃，不能继续读出伪造 request；
5. seed 覆盖每个 opcode、字段类型、TLS record 边界和历史回归样本。

## 4. 存储集成测试

使用已有功能测试中的 User/Score/BenchData，并新增 runtime `WireTypeRegistry`：

1. HELLO/AUTH 后 GET/ADD/UPDATE/DELETE 成功与错误码映射；
2. 缓存命中、磁盘 miss、TTL 过期、淘汰回填、MEMO_OUT、TYPE_NOT_REGISTERED；
3. handler 异步 completion 不阻塞 Reactor；
4. completion 在断连、踢出、服务 drain 后到达，不能 UAF 或写入新连接；
5. 存储线程停止/异常时请求必然收到错误或连接被确定关闭，不能永久悬挂；
6. 原有存储层测试继续通过，网络测试不能依赖“多调用一次 future.get()”来掩盖接口问题。

## 5. 故障注入

- `accept/read/write/epoll_ctl/epoll_wait/eventfd_write` 返回 `EINTR/EAGAIN/EMFILE/ENFILE/ECONNRESET`；
- TLS 握手中断、证书错误、`WANT_READ/WANT_WRITE` 交替；
- handler 延迟 1ms/100ms/超时/抛异常/不回调；
- inbox、pipeline、输出队列达到上限；
- listener 达 fd 上限；
- Reactor 线程被请求洪峰占满；
- 服务停止期间仍有新连接和晚到 completion。

每个注入点都要验证：连接是否泄漏、计数是否闭合、线程是否可退出、客户端是否得到稳定错误。

## 6. 端到端功能验收

### F1：基础连接

客户端连接、HELLO、AUTH、PING、QUIT；错误顺序和状态码正确。

### F2：CRUD

验证 `ADD -> GET -> UPDATE -> GET -> DELETE -> GET`，包含拆包、粘包、pipeline 与不同类型。

### F3：长连接与多连接

单连接 10k pipeline、1k 并发连接、连接反复建立/关闭；同连接响应严格按 request_id 顺序。

### F4：管理

CLIENT_LIST 返回连接快照；CLIENT_KILL 只关闭指定 connection ID；普通用户无权调用维护命令。

### F5：安全

明文非回环拒绝、TLS 证书校验、过期认证、密码脱敏日志、畸形长度和未授权命令。

## 7. 压力与性能分级

以下是首版验收门槛，不是最终产品 SLA；以同一台机器的明文短 value 基线为主：

| 档位 | 场景 | 通过条件 |
|---|---|---|
| P0 | 1 连接 PING/GET | 无错误；P99 不出现周期性 1s 级尖峰 |
| P1 | 1k 长连接，10% 活跃 | 30 分钟无泄漏、无连接丢失 |
| P2 | 10k 空闲连接 | RSS 增长可解释，事件循环无忙等 |
| P3 | 1k 连接 pipeline CRUD | 连接级顺序正确，错误率 0 |
| P4 | 10k 连接 + 5% 慢消费者 | 内存有界，slow-consumer 按策略关闭 |
| P5 | 50k/100k 空闲连接探索 | 只记录实测，不作为必须承诺 |
| P6 | TLS 与明文对照 | 给出吞吐/延迟/CPU 差异，不混报 |

端到端 QPS 目标先用存储层裸接口结果作参考，不预设固定数字。第一轮报告应回答：网络新增的 CPU、
延迟和内存成本是多少；miss 场景是否仍由 DiskThread 主导；背压是否保护了其他连接。

## 8. 验收证据

每个阶段至少保留：

- CTest/单测结果与 sanitizer 输出；
- fuzz 运行时长、覆盖率和崩溃样本归档；
- 端到端客户端脚本及服务端日志摘要；
- 压测原始 CSV/JSON（不只贴平均 QPS）；
- 配置、commit、编译器、内核和机器信息；
- 已知失败项与下一阶段是否允许继续。
