# 开源项目网络层调研

> 调研日期：2026-09-19。本文只提炼可验证的设计思想，不以“像某项目”代替本项目自己的约束分析。

## 1. Redis：协议与连接保护

参考：

- [Redis serialization protocol specification](https://redis.io/docs/latest/develop/reference/protocol-spec/)
- [Redis client handling](https://redis.io/docs/latest/develop/reference/clients/)

可复用思路：

1. RESP 的 bulk string 使用长度前缀，二进制安全，解析 payload 时无需扫描分隔符或转义；
2. 一个连接可发送多条流水线请求，降低 RTT 和 syscall 开销；
3. 新连接设为 non-blocking，启用 `TCP_NODELAY`，用可读事件驱动读取；
4. `maxclients` 必须与操作系统 fd soft limit 一起检查，配置值不等于真实可承载值；
5. 输入和输出缓冲都必须有限额，慢消费者达到硬/软水位后应断开；
6. 空闲超时可以近似、增量处理，无需为每条连接维护高精度定时器。

本项目采用：长度前缀、二进制安全、流水线、连接/缓冲限额、非阻塞 socket、近似超时扫描。

本项目不直接采用 RESP：现有存储支持服务端注册的 C++ 类型，协议还需要明确版本、请求 ID、
类型名和 wire codec 版本。做“半兼容 RESP”会让现有 Redis 客户端仍无法理解命令语义，反而形成错误承诺。
以后若需要生态兼容，应单独做 RESP gateway/adapter，而不是污染核心协议。

## 2. muduo：Reactor 与连接线程亲和

参考：[chenshuo/muduo](https://github.com/chenshuo/muduo)

muduo 是面向 Linux 多线程服务端的 Reactor 网络库。对本项目最有价值的不是复制其类名，
而是“一个连接由一个事件循环负责”的所有权模型：

- 主监听者接受连接；
- 连接分派到某个 I/O loop；
- 该连接的读、写、关闭和事件修改都回到所属 loop；
- 跨线程只传消息，不让多个线程同时操作一个 socket/Connection。

本项目采用 `Acceptor + ReactorGroup + Connection affinity`，并用 `eventfd + MPSC inbox` 唤醒目标 Reactor。
这能把 Connection 大部分状态做成线程内状态，避免在热路径堆锁。

## 3. Dragonfly：连接亲和与 shared-nothing 的适用边界

参考：[Dragonfly Architecture](https://github.com/dragonflydb/dragonfly/blob/main/docs/df-share-nothing.md)

Dragonfly 文档明确描述：连接接受后整个生命周期绑定一个线程；数据库再按 shard 分给线程，
连接协调者通过线程间消息访问目标 shard。这证明“连接亲和 + 消息传递”可扩展到很高吞吐。

本项目只采用前半部分，不照搬 shard-per-core：

- 当前 `cache_db` 是共享 `unordered_map`，由读写锁保护；
- 写操作由单写线程串行；
- `inDisk`、文件句柄和空洞索引由单磁盘线程拥有；
- 直接按网络线程切 shard 会改变 key 所有权、淘汰、持久化、压缩和恢复语义，等于重写存储层。

因此首版保持网络与存储两个独立调度域：网络线程只做 I/O，命令通过异步接口进入现有存储执行者。
未来只有在存储层先完成分片设计后，才讨论“网络线程与数据 shard 共置”。

## 4. Linux epoll：先正确、再优化触发模式

参考：[epoll(7)](https://man7.org/linux/man-pages/man7/epoll.7.html)

`epoll` 同时支持 level-triggered（LT）和 edge-triggered（ET）。首版选择 LT：

- 更容易验证半包、TLS `WANT_READ/WANT_WRITE` 和动态开关 `EPOLLOUT`；
- 连接已经线程亲和，不需要用 `EPOLLONESHOT` 防止多线程同时处理同一 fd；
- 热点连接用每轮字节/帧预算限制，不依赖 ET 获得公平性。

即便使用 LT，read/write 也应循环到 `EAGAIN` 或预算耗尽。若基准证明事件重复通知是瓶颈，
再以同一 `Poller` 接口增加 ET 模式，并补齐 ET 专项测试。

## 5. 方案对比

| 方案 | 优点 | 主要问题 | 结论 |
|---|---|---|---|
| 每连接一线程 | 编程直观 | 线程栈、调度和上下文切换无法支撑高连接数 | 否决 |
| 单 Reactor | 最简单、顺序天然明确 | 单核上限，TLS/编码容易拖住全局 | 仅用于阶段 2 验证 |
| Acceptor + N Reactor | 连接亲和、可用多核、锁少 | 需要跨线程完成队列和生命周期协议 | 首版目标 |
| Reactor + 通用业务线程池 | 可隔离 CPU 工作 | 与现有存储线程池重复，易多一层无界排队 | 命令层只做轻量适配 |
| shard-per-core | 多核扩展强 | 与现有共享存储模型冲突 | 后置到存储分片重构 |
| `io_uring` | 批提交/完成潜力 | 复杂、TLS/生态与调试成本更高，当前无瓶颈证据 | 暂不采用 |
| 直接用 JSON | 易观察 | 非二进制安全需 base64，扫描/转义/分配较重 | 仅可用于调试工具 |
| 直接实现 RESP | 客户端生态大 | 类型与命令不兼容，无法“免费兼容” | 核心协议不采用 |

## 6. 本土化结论

最终方案不是三个项目的拼装，而是按现有存储层约束收敛：

1. 用 Redis 的协议/缓冲保护原则，解决边界与过载；
2. 用 muduo/Dragonfly 的连接线程亲和，解决 socket 所有权；
3. 保留现有存储层的异步续延模型，不在网络层增加第二套业务线程池；
4. 用自定义小型二进制帧承载运行时类型和请求 ID；
5. 把未来分布式所需的兼容点放在协议版本与 handler 接口，不提前实现数据分片。
