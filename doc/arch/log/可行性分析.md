# 日志层可行性分析

> 状态：设计阶段。本文分析当前项目结构下的实现可行性，不代表代码已经存在。

## 1. 当前基础

项目使用 C++20，存储层已经具备：

- ReadPool、WriteThread、DiskThread 三类后台执行者；
- std::future 异步接口；
- Disk 独占的 inDisk、文件句柄和 holes；
- CHECK_VALID/CHECK_DELETED/CHECK_BROKEN 三种记录状态；
- 记录头中的 dataSize 和固定字段；
- reWrite() 对文件进行整体整理。

因此日志层可以使用标准库线程、条件变量、队列、文件流和文件系统接口，不需要先引入新的第三方依赖。

## 2. 异步文本日志可行性

### 2.1 线程模型

每个进程使用一个日志工作线程，生产者只创建 LogRecord 并投递到有界队列。工作线程负责：

1. 按目标文件分流；
2. 格式化为一行文本；
3. 批量写入；
4. 按时间或批量大小 flush；
5. 在关闭时排空队列。

日志写入不会占用现有 ReadPool、WriteThread 或 DiskThread，也不会在正常日志路径上持有缓存锁。

### 2.2 队列满载

队列采用分级策略：

- FATAL/ERROR：不能静默丢弃。队列满时旁路同步追加并 flush；
- WARN：优先保留，无法保留时丢弃并累计丢弃数；
- INFO：队列满时优先丢弃。

旁路同步写只用于错误和恢复失败等低频路径，不应放在高频 CRUD 热路径中。

### 2.3 可行性结论

该方案不会改变现有存储线程模型，内存开销由队列上限控制，日志文件写入吞吐可以通过批量 flush 提升，适合当前项目。

## 3. 数据文件恢复可行性

### 3.1 数据文件作为唯一权威

空洞索引不单独写文件。启动时扫描数据文件：

- CHECK_VALID：校验后加入/更新 inDisk；
- CHECK_DELETED：校验后加入 holes；
- 同名记录后出现的版本覆盖之前的偏移；
- CHECK_BROKEN 或不可验证记录：在该记录起点停止；
- 扫描成功后更新 curSize。

这样即使进程在任何时刻丢失内存索引，仍可从数据文件重新得到运行状态。

### 3.2 中间损坏

当前磁盘层允许原位覆盖和空洞复用，因此损坏可能出现在文件中间。没有可靠同步点时，恢复器不能安全跳过未知长度的中间区域。

安全策略是：

1. 找到第一个无法验证的记录起点；
2. 把该点之后的内容视为不可信；
3. 先保留原文件；
4. 生成只包含有效前缀的新活动文件；
5. 重新扫描并建立索引。

这可能丢弃损坏点之后仍然完整的记录，但不会把错位数据继续暴露给查询路径。

### 3.3 备份和恢复文件

改名保存原文件的方式不会复制整个文件，正常情况下只涉及同一文件系统内的重命名。恢复活动文件时仍需考虑：

- 备份改名失败；
- 有效前缀复制失败；
- 新文件 flush 或替换失败；
- 进程在恢复流程中再次崩溃。

任一步骤无法确认安全完成，都应保留原文件并返回恢复失败，不能直接截断原文件。

## 4. magic/version 和 CRC32C

### 4.1 目标

新格式计划增加：

- 固定 magic；
- 格式版本；
- CRC32C 完整性校验。

用途是检测头部、长度字段或实体内容的意外损坏，避免把错误偏移继续传递到 selData。

### 4.2 开销

- 每条记录增加少量固定字节；
- 写入时对已有 recBuf 计算校验，不需要额外复制实体；
- 读取/恢复时增加一次顺序校验；
- 大实体的固定字节开销很小，小实体的固定开销更明显；
- 具体吞吐损失必须在目标机器上用真实记录大小进行基准测试。

CRC32C 只能发现大多数意外损坏，不能保证防篡改，也不能解决日志未 flush 或两个文件同时损坏的问题。

### 4.3 未决协议点

本阶段只冻结“加入 magic/version/CRC32C”这一方向，以下内容在实现前必须单独确定：

- CRC 放在固定头、记录尾，还是两处都放；
- CHECK_BROKEN/CHECK_VALID/CHECK_DELETED 是否排除在 CRC 覆盖范围之外；
- 空洞记录是否需要完整校验；
- 新记录头的精确字节布局和版本号。

## 5. 与当前磁盘优化的关系

日志层恢复设计不要求立即废弃当前原位覆盖、空洞复用和原地压缩模型。它接受以下限制：

- 原位覆盖可能破坏旧版本；
- 恢复只承诺有效前缀；
- 逐条历史回溯需要后续完整文件备份；
- holes 是扫描结果，不是独立权威文件。

如果未来需要更强的逐条回滚能力，应另行评估追加版本记录、WAL 或“新文件写入后原子替换”模型。

## 6. 总体可行性结论

错误日志和生命周期日志可以在现有工程中独立实现。数据恢复也可以在 Disk 内实现、由 Controller 提供同步入口。

真正的实现风险集中在：

1. 新记录格式和 CRC 覆盖范围；
2. 中间损坏时的活动文件替换流程；
3. 恢复阶段和现有 DiskThread、常驻文件句柄的协调；
4. Windows 文件重命名、打开句柄和失败回滚行为。
