# 日志层实现方案

> 状态：设计阶段。以下接口和流程是后续实现的目标，不代表当前代码已经提供这些接口。

## 1. 模块边界

建议新增独立日志模块，暂定放在：

~~~text
project/log_level/
~~~

日志模块不依赖 Cache、Disk 的私有结构。管理层同时持有 Controller 和日志对象，按照调用结果记录事件。

存储恢复仍属于存储层：

~~~text
管理层
 ├─ Logger                 错误/生命周期日志
 └─ Controller::recover()
      └─ Disk::recover()   扫描文件、重建 inDisk/holes
~~~

日志层不保存或解释空洞索引。

## 2. 日志接口草案

### 2.1 基本类型

~~~cpp
enum class LogLevel {
    INFO,
    WARN,
    ERROR,
    FATAL
};

struct LogRecord {
    LogLevel level;
    std::string role;       // server / client
    std::string module;     // controller / disk / network ...
    std::string event;      // 稳定事件名
    std::string message;
    std::vector<std::pair<std::string, std::string>> fields;
};
~~~

时间戳由 Logger 统一生成，使用本地时区 ISO 8601，精确到毫秒。

### 2.2 Logger 目标接口

~~~cpp
class Logger {
public:
    // 投递普通日志；不等待文件 IO
    bool submit(LogRecord record);

    // 高优先级事件的显式同步路径
    bool submitCritical(LogRecord record);

    // 等待队列排空并 flush
    bool flush();

    // 停止接收、排空队列、flush、关闭文件
    void shutdown();
};
~~~

实际实现可以用构造参数配置日志目录、角色、队列上限和 flush 周期。

## 3. 文本文件格式

文件名：

~~~text
server_log.log
client_log.log
~~~

每行一条记录，字段采用带转义的 key=value，字段之间使用制表符分隔。例如：

~~~text
time=2026-09-13T21:30:12.345+08:00	level=ERROR	role=server	module=Disk	event=RECOVERY_TRUNCATE	offset=1048576	message=record\ checksum\ failed
~~~

至少需要转义：

- 反斜杠；
- 制表符；
- 回车；
- 换行。

密码、令牌、完整认证报文和实体值不得写入日志。需要关联对象时只记录 key、用户标识、请求 ID 或摘要。

## 4. 队列和刷盘

### 4.1 工作线程

Logger 内部使用一个工作线程和有界队列。生产者只完成：

1. 补充时间和默认字段；
2. 复制/移动必要字符串；
3. 尝试入队。

工作线程完成格式化和文件写入。

### 4.2 优先级策略

| 级别 | 正常路径 | 队列满载 |
|---|---|---|
| INFO | 异步入队 | 优先丢弃 |
| WARN | 异步入队 | 计数后丢弃 |
| ERROR | 异步入队 | 旁路同步写并 flush |
| FATAL | 异步入队 | 旁路同步写并 flush，失败时写备用错误流 |

丢弃数量不能在每次丢弃时再次写普通日志，否则会形成递归；队列恢复后可以合并写一条丢弃摘要。

### 4.3 flush 和关闭

普通日志按“达到批量大小或到达时间周期”触发 flush。具体默认值需要基准测试后确定。

关闭顺序：

1. 停止接受新日志；
2. 唤醒日志线程；
3. 排空队列；
4. flush；
5. 关闭文件；
6. 汇报无法写入的剩余数量。

## 5. 恢复接口

### 5.1 RecoveryResult

目标结构如下：

~~~cpp
enum class RecoveryStatus {
    NO_FILE,
    CLEAN,
    RECOVERED,
    FAILED
};

struct RecoveryResult {
    RecoveryStatus status;
    bool fileExisted = false;
    bool truncated = false;
    long long firstBadOffset = -1;
    long long fileSizeBefore = 0;
    long long fileSizeAfter = 0;
    long long validRecordCount = 0;
    long long deletedRecordCount = 0;
    long long holeCount = 0;
    std::string backupPath;
    std::string reason;
};
~~~

### 5.2 Controller 入口

~~~cpp
RecoveryResult Controller::recover();
~~~

该接口为同步启动接口。管理层必须在接受客户端请求、提交普通 CRUD 之前调用并检查结果。

### 5.3 Disk 恢复流程

1. 确认当前没有其它磁盘任务；
2. 关闭现有文件句柄；
3. 清空 inDisk、holes，重置 curSize；
4. 从偏移 0 顺序读取记录；
5. 校验 magic、version、状态码、长度和 CRC；
6. VALID 记录加入/更新 inDisk；
7. DELETED 记录加入 holes；
8. 遇到 BROKEN 或首个不可验证记录，记录 firstBadOffset 并停止扫描；
9. 若无需修复，直接重新打开文件；
10. 若需要修复，先将原文件改名保留，再生成有效前缀活动文件；
11. 重新扫描有效文件并设置 curSize；
12. 返回结构化结果。

恢复扫描不强制反序列化实体。未知类型仍可以建立偏移索引，后续查询时按现有规则返回 TYPE_VALID；完整性由记录格式和 CRC 负责。

## 6. 损坏文件修复

备份命名暂定为：

~~~text
<db>.corrupt.<本地时间戳>
~~~

活动文件只包含第一个坏记录之前的完整字节前缀。备份改名、前缀生成、flush 或替换任一步骤失败时：

- 不截断原始文件；
- 保留原文件和已生成的临时文件；
- 返回 FAILED；
- 由管理层记录 FATAL 并决定是否退出。

损坏备份不计入 Disk::maxSize，但会占用操作系统磁盘空间。

## 7. 数据格式方向

新格式计划在现有固定头基础上加入：

- magic；
- version；
- CRC32C。

旧 86B 格式不兼容。具体字段排列、CRC 覆盖范围和空洞记录的校验方式必须在开始改代码前单独冻结。

## 8. 管理层接入

启动：

1. 创建 Logger；
2. 写入服务启动事件；
3. 创建/初始化 Controller；
4. 调用 Controller::recover()；
5. 记录恢复结果；
6. FAILED 时拒绝开放服务；
7. 成功或可接受的 RECOVERED 时继续启动。

运行：

- 只记录关键生命周期和错误；
- 不把每次成功 CRUD 自动变成日志；
- 管理层消费 future 后，根据失败码记录错误事件。

关闭：

1. 停止接收新请求；
2. 等待存储任务按现有线程模型排空；
3. 写服务关闭事件；
4. 调用 Logger::shutdown。
