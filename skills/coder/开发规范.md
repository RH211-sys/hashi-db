# 开发规范

## 概述

当被认定为`开发者`或`重构者`或`修改者`，需要明确当前项目的开发规范

原则：正常流程优先、错误集中处理、模块职责单一

## 1. 注释要求

每个类的注释：

```
/*
	地位：参与xx工作
	功能：xxx
*/
class xxx
```

每个变量的注释（包括全局变量，局部变量，成员变量等等）：

```
type var;			// 用于xxx
```

每个函数/方法的注释：

```
/*
	功能：xxx
	传参：xxx
	返回值：xxx
*/
function
```

每个文件/模块 开头

```
/*
	模块名：
	模块地位(处于哪个关系)
	模块功能描述：
*/
```

每个if

```
if(xxxx) {
	// xxx条件，需要执行xxx
}

比如
if(total == 0) {
	没有商品了，返回false
	return false
}
```

如果封装某个代码过程发现过程很长，需要在代码中添加阶段注释：

```
	 /*
		1: xxx(描述这个阶段的过程流程)
	*/
	代码段
	/*
		2. xxx(描述这个阶段的过程流程)
	*/
	代码段
	......

```

> 尽量用模块架构 ，分层架构已经好了，就整个项目的那几层，每一层为一个模块架构

均使用 UTF-8编码，中文编写

## 2. 变量/常量名规范

1. 变量名和函数名用 **snake_case**（全小写 + 下划线）
2. 类名，结构体名，类型名用大驼峰
3. <u>协议/字段</u> 的`constexpr`常量名，宏定义用全大写 + 下划线
4. 其他的编码规范参考`Google C++ Style Guide`
5. 不要使用魔数，如偏移量（相对位置），字段大小等应该定义为<u>协议/字段</u>`constexpr`常量，

### 3. 编程规范（非常重要）

编写代码时应遵守以下普适规则：

1. **编写前先定义职责**

   编写一个模块或函数前，先明确：

   - 它接收什么数据；
   - 谁调用它；
   - 它必须检查哪些条件；
   - 检查通过后向调用方保证什么；
   - 检查失败后返回什么结果；
   - 哪个线程访问它；
   - 哪个对象拥有它使用的资源。

   如果这些内容无法说明清楚，先整理接口设计，不直接编写实现。

2. **每项检查必须有唯一责任模块**

   每项条件由一个明确模块负责检查。例如：

   - 协议字节格式由帧编解码模块检查；
   - 命令字段规则由命令解析模块检查；
   - 会话阶段由连接模块检查；
   - 存储结果由执行模块转换；
   - socket 返回状态由传输模块处理。

   检查通过后，该模块把符合约定的数据交给调用方。调用方**不重复执行相同检查**，只检查自己新增的条件。

   如果同一个检查必须出现在多个公共入口中，必须说明这些入口可以绕过同一个前置函数；否则视为重复检查，应该删除或调整接口。

3. **函数按固定顺序组织**

   一个函数的主要结构应当是：

   ```
   检查输入 ( /* ============ 检查输入 ============ */)
   → 转换数据 ( /* ============ 转换数据 ============ */)
   → 执行核心流程 ( /* ============ 核心流程 ============ */)
   → 提交状态 ( /* ============ 提交状态 ============ */)
   → 返回结果 ( /* ============ 返回结果 ============ */)
   ```

   核心功能代码应当连续可读。不要写成“执行一步功能、检查一个无关错误、再执行一步功能、再重复清理”的杂糅结构。

   > 防御代码，核心执行，结果返回等逻辑在整个函数中杂糅在一起，这是不可取的

   复杂检查应提取成有明确职责的函数，例如 `validateFrame`、`parseFields`、`handleTransportResult`。提取后，调用位置必须能看出主流程。

4. **区分四种检查**

   - 外部输入检查：客户端数据、配置文件、用户参数，必须保留。
   - 系统调用检查：socket、文件、线程和第三方库返回值，必须保留。
   - 资源控制检查：队列容量、缓冲区、连接数和内存上限，必须保留。
   - 内部状态检查：模块自己应该保证的不变量，优先通过类型、生命周期和调用契约保证，避免在每个函数重复检查。

   不能因为看到大量 `if` 就直接删除检查，也不能因为“防止崩溃”就无限增加检查。每个检查都必须明确失败后的动作：返回错误、等待、重试、排队、回滚、关闭或转换结果。

5. **失败路径必须集中且只执行一次**

   每种失败结果应有明确的处理责任人。一个操作只能有一个最终结果：

   ```
   一个请求 -> 一次提交 -> 一次完成回调 -> 一个响应
   ```

   禁止在对象已经移动、任务已经提交或回调已经调用后，再进入另一条路径重复使用同一对象或重复回调。禁止使用空的 `catch (...)` 隐藏错误；跨线程入口可以统一捕获异常，但必须转换成明确结果，并保证清理和回调只执行一次。

6. **状态和资源必须有唯一拥有者**

   一个状态只能由负责该状态的对象修改。一个 socket、线程、锁或异步任务只能有明确的资源拥有者。使用 RAII、智能指针和不可复制对象表达所有权，不用多个模块分别关闭或释放同一资源。

   并发代码必须说明：任务在哪个线程运行、谁可以修改状态、队列由哪个锁保护、结果如何返回、对象销毁后迟到任务如何处理。

7. **执行的注释必须说明原因和结果**

   注释不翻译代码，而说明：

   - 为什么要执行这项检查；
   - 通过后建立什么条件；
   - 失败后采取什么动作，失败的意义是什么；
   - 为什么需要某种线程、队列或状态转换。

   按项目要求，每个 `if` 都应有简短注释，但注释应描述分支的业务目的，不能只写“条件成立”或重复表达代码。

8. **提交前必须自查**

   Agent 交付前逐项回答：

   - 正确性

   - 正常流程能否连续读懂？
   - 每项检查是否有唯一责任模块？
   - 是否重复检查前一个模块已经完成的条件？
   - 每个失败分支是否有明确结果？
   - 是否可能重复提交、重复回调或重复释放？
   - 状态修改和资源释放是否由唯一对象负责？
   - 跨线程任务的生命周期是否明确？
   - 注释是否解释原因而不是复述语句？
   - 是否存在尚未实现却被描述为已实现的功能？

核心原则是：

> **每个模块只检查自己负责的条件；检查通过后，把符合约定的数据交给调用方；调用方继续执行自己的功能，不重复前一个模块已经完成的检查。**
