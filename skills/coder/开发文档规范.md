# 开发文档规范

## 概述

当明确需要在某个位置写开发文档，需要注意规范

## 总体框架

关于文档编写：一般要写两个文档：

1. 核心逻辑：用户在这类文档中不能看到代码细节，**只从哲学思想设计上去讲实现方式**，不要写成教程，这个文档的**目的是让用户尽快理解该层的实现逻辑**，因此字数也不要太多，以避免因为阅读文档影响项目推进。注意表达方式
2. 细节实现（实现阶段中需要）：在核心逻辑的基础上，**去讲部分逻辑结点中的细节如何实现（比如一些边界控制，并发竞争等）**，这里可以带一点源代码，但是要尽可能少，**目的是用户快速理解一些编写代码时需要注意的点**

这两个文档不要集成为一个文档，最好分开写

在README.md中添加好索引

## 编写要点

`实现阶段`：在每一轮实现后，需要创建一个子目录，并编写如下文档：

1. README.md：格式如下

   - feature：完成了xxx功能 + 描述
   - fix：修复了xxxbug
   - improvement：优化了xxx

2. 核心逻辑：每个实现点的思路是什么，使用核心逻辑 + 细节实现（这里的核心逻辑和细节实现不要分文档）的方式

   - feature：核心逻辑 + 细节实现（这里的核心逻辑和细节实现不要分文档）
   - fix：之前错误点（思路问题 + 细节问题），如何修复（思路 + 细节）
   - improvement：之前低效点（思路 + 细节），如何修复（思路 + 细节）

3. 细节实现：基于**当前实际实现**梳理该负责层的功能流程，不抄代码，也不把设计稿当成已实现事实，写好所有功能链的执行流程。每条功能链分别写两种说明：

   - **思想逻辑模块**：按职责和先后顺序说明模块如何协作。

   - **代码逻辑模块**：对应到实际类、函数和文件，说明代码中的实现位置与调用关系。
